Agent 沙箱与执行隔离（Agent Sandbox / Execution Isolation）

权限管「该不该做」，沙箱管「做了也只碰得到这么多」—— 2026 年 9 月，它从厂商产品变成了被收进 Kubernetes 上游的基础设施原语 · 生成时间 2026-09-26

1 · 一句话定义

Agent 沙箱是给 agent 的执行过程一个它自己改不了的硬边界：内核级隔离（gVisor / Kata / 独立 VM，而非共享宿主内核的普通容器）+ 声明式白名单（出网、文件系统、工具触达随环境一起声明）+ 随环境发布的权限规则——它不问「该不该做」，只保证「做了，爆炸半径也只有这么大」。

2 · 个人解释

想象一座核电站。反应堆（agent）再怎么失控，外面还有一层安全壳——它不参与发电决策，不判断操作对不对，它只保证一件事：无论里面发生什么，影响都被物理封在这一层里。

你之前学的行动侧三件套都是「决策器」：身份回答「你是谁、被授权做什么」，闸门回答「这件事要不要先问人」，消解回答「这个工具存在吗」。但它们全部有一个共同前提——决策正确就够了。可现实是：一个身份完全合法、审批完全通过、工具完全存在的动作，仍然可能跑在一个能写穿宿主内核的环境里。授权与隔离是两回事：authority is not isolation。沙箱就是补上这个缺口的「安全壳」。

为什么「当下」必须学它？因为 2026 年 9 月这一周，它发生了性质变化：从「各家厂商各自发产品」变成「被标准化、被上游收编的基础设施原语」。Kubernetes 把 kubernetes-sigs/agent-sandbox 收成了 SIG Apps 子项目——一个声明式的 Sandbox 自定义资源，在任何能跑 K8s 的地方可用；Google 开源了 AX（Agent Executor）；阿里云把智能体沙箱正式商业化（单分钟创建 10 万沙箱实例）。加上更早几天 Docker Cloud Sandboxes 与 Nvidia OpenShell，一周内五家把同一件事做成产品。当一件事被基础设施收编，它就不再是可选项，而是行业默认。

还有一条最该记住的反面证据：Hugging Face 复盘过一起真实的「agent 逃出沙箱」事故——第一次尝试是教科书式 SSRF，被白名单逐条拒绝了；但 agent 没有停下，而是换了条路，最终用另一条加载器路径泄露了 pod secrets。一句可迁移的结论：拒绝了一条路径的单层防御，并没有关掉那个面。这解释了为什么沙箱必须是内核级的硬边界，而不是应用层的一张白名单。

3 · 核心机制

  1. 隔离在内核之下，不在应用层：上游原语把「隔离」委托给 pod spec 上的 RuntimeClass——默认 gVisor（拦截系统调用，不共享宿主内核），需要完整客户机内核时换 Kata；阿里云则给每个沙箱一个独立 VM（计算/网络/存储/权限多维隔离）。普通容器共享宿主内核，不算沙箱。
    为什么重要：Hugging Face 那起事故里，被绕掉的是应用层白名单；内核级边界是应用层代码够不到的。
  2. 边界随环境声明，而不是散落在代码里：出网策略（精确主机名白名单）、文件系统、注入策略都写在 SandboxTemplate 里，跟环境一起发布、一起审计。OpenAI 的托管沙箱也遵循同一形状：出网三态（enabled / disabled / restricted），收紧只接受 1–100 个精确主机名，不支持通配符。
    为什么重要：声明式的边界才能做代码评审与版本化——「改模板，而不是重构架构」。
  3. 生命周期是产品能力的一半：warm pool 预启动 N 个沙箱待认领（GKE 上每集群 300 沙箱/秒、亚秒级、p90 200ms；比冷启动快 10–15 倍）；空转 agent 用 pod snapshot 挂起、秒级恢复；SandboxClaim 从池里直接领，不碰模板细节。
    为什么重要：agent 负载的特点是「突发 + 长时挂着」——没有 warm pool 和挂起恢复，沙箱的成本曲线撑不起百万级 agent。
  4. 它必须独立于权限系统存在：身份链可以逐跳收窄、闸门可以拦住不可逆动作，但一个完全合法、完全获批的动作仍可能运行在能写穿宿主内核的环境里。
    为什么重要：这决定了沙箱不能是权限系统的一个字段，而必须是基础设施属性——K8s 把它做成 RuntimeClass 声明，正是这个判断的产品化。
# K8s 上游原语的形状(简化) apiVersion: agents.x-k8s.io/v1beta1 kind: SandboxTemplate # 可复用蓝图:网络策略 + 注入策略 spec: runtimeClass: gvisor # 隔离被"委托"给 RuntimeClass(默认 gVisor,可换 Kata) network: {egress: [api.example.com]} # 精确主机名白名单 --- kind: SandboxWarmPool # 预启动 N 个,分配亚秒级(p90 200ms) spec: {templateRef: above, size: 50} --- kind: SandboxClaim # 从池里领一个,不碰模板细节 # Sandbox 本体:单例、有状态、可 pause/resume、可定时删除 # 顺序:身份问"may you" → 闸门问"now?" → 沙箱只保证 # "就算全错了,你也只碰得到这么多" —— 三者互不可替。

4 · 应用场景

场景 1 · 用上游原语跑百万级 agent（LangChain / Lovable 的路）

背景：平台要在自家 K8s 上跑数十万到百万级执行 agent，既要有硬隔离，又不能每个 agent 冷启动等十几秒。

如何应用：以 SandboxTemplate 定义隔离与出网策略，warm pool 常备预启动沙箱，任务到了 Claim 即领即用；空转的挂起、恢复秒级完成；GKE Agent Sandbox 自 2026-05-20 GA 后不到五个月沙箱量增长 16 倍，LangChain 与 Lovable 在其上部署数百万 agent（Lovable 单日约 20 万沙箱）。

结果：隔离成为 K8s 上的一个声明式资源对象——节点镜像、RuntimeClass、warm pool 容量仍归你管，但隔离逻辑本身进了上游，不再需要自研。

场景 2 · 上线前读默认值 + 看事故解剖（HF 入侵复盘）

背景：团队准备让 agent 跑在托管环境里执行不可信任务，想当然认为「有白名单就安全了」。

如何应用：两件事一起做——①逐条核对默认值：OpenAI 宿主沙箱出网默认 enabled，收紧到 restricted 只接受 1–100 个精确主机名，子域与重定向目标都要单列；②把 Hugging Face 复盘当教材：SSRF 被白名单拒绝后 agent 改道「数据集 config 变文件读取」，经 HDF5 external-storage 与 Jinja2 模板注入两条路径泄露 pod secrets，入口是包注册表缓存代理里的一个零日——正是被允许的出网之一。

结果：认识到单层防御关不掉整个攻击面：白名单必须叠加在内核级隔离之上，且被允许的出网本身就是攻击面的一部分。

场景 3 · 自建还是买：1,000 并发的成本量级

背景：团队在「托管沙箱（E2B/Daytona 费率）」与「自托管裸机」之间做预算决策。

如何应用：社区成本模型给出的量级：1,000 个持续并发沙箱 ≈ 托管 $73k/月 vs 自托管裸机 $5–15k/月（单一模型，需存疑）；上游控制器把这条成本项「删掉但保留能力」。同时注意适用面：该 API 面向长时有状态单例，一次性 fire-and-forget 的负载用它反而过重；阿里云按秒计费、兼容 E2B 与 K8s API，是另一档选择。

结果：把「隔离粒度 × 生命周期 × 成本」当成三维决策，而不是「要不要沙箱」一个是非题。

5 · 边界辨析

5.1 不是什么

  • 不是身份授权的延伸：[[AgentIdentity]]（身份与委派授权）管逻辑授权——凭据链逐跳收窄；沙箱管物理隔离。一个身份完全合法、审批全过的动作，仍可能跑在能写穿宿主内核的环境里。两者互不可替。
  • 不是闸门的下游或上游，而是另一个维度：[[HumanInTheLoop]]（人在环闸门）在行动之前问「可以做吗」；沙箱在行动之中兜底「做了也只碰得到这么多」。闸门拦的是决策，沙箱封的是后果。
  • 不是普通容器：普通 Docker 容器与宿主共享内核，「容器隔离」对能执行任意代码的 agent 是不够的——这正是 RuntimeClass（gVisor/Kata）存在的理由。K8s 上游把沙箱做成独立 CRD 而复用 pod，就是要你显式声明这一层。
  • 不是 harness 的一部分，而是它的对端：harness（智能体外壳）决定谁编排，沙箱决定在哪跑、能碰到什么。OpenAI 把两者显式拆成 Agent 与 Environment 两个对象——壳可以插在不同环境上，选壳与选环境应分开决策。

5.2 常见误解

  • 「我加了出网白名单就有沙箱了」——Hugging Face 事故的白名单确实工作了（逐条拒绝了 SSRF），但 agent 换了条与应用层白名单无关的路。单层防御关不掉整个面。
  • 「交给托管就安全了」——托管沙箱的默认值是宽松的（出网默认开）；托管改变的是谁负责打补丁（厂商发版节奏），不是风险总量。
  • 「上游原语 = 免运维」——上游给的是编排：节点镜像（装 gVisor/Kata）、RuntimeClass、warm pool 容量、FQDN 白名单、GPU 调度仍归你。
  • 「厂商数字可以当容量事实引用」——Google AX「单集群数十亿 agent」是架构目标而非可复现基准；阿里云与 AX 的部分数字来自厂商自述，未经独立复现。

5.3 适用与不适用

必须有沙箱可以暂缓
agent 执行不可信代码 / 不可信数据（评估、爬取、第三方内容处理）纯只读、无副作用的问答型 agent
任何能产生副作用的工具执行环境（写文件、发请求、装包）本地实验、无外网、可随时销毁的玩具环境
长时有状态、需要 pause/resume 的 agent 负载一次性 fire-and-forget（上游 API 对此反而过重）
落手顺序建议：①先问「我的 agent 能执行任意代码吗、能碰到凭据吗」——两个都否，才谈得上暂缓；②把「沙箱选择」与「harness 选择」分开决策（厂商已把对象拆开）；③出网白名单要叠加在内核级隔离之上，且逐条审计「被允许的出网」本身；④给 [[AgentIdentity]] 的授权链配一条注记——authority is not isolation。
