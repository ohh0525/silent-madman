上下文工程（Context Engineering）

把「每一步该让模型看见什么」当作一门工程 · 生成时间 2026-09-16

1 · 一句话定义

上下文工程是在模型推理的每一步，决定往有限的上下文窗口里放入哪些 token 的一整套取舍方法——目标是找到能产出目标结果的「最小高信号 token 集合」。

2 · 个人解释

想象你要开一场决定预算的项目评审会。提示词工程（prompt engineering）关心的是你开口那句开场白怎么说；而上下文工程关心的是——整张会议桌上到底摆了哪些材料。

直觉上你会想：「信息越多越保险」，于是把去年财报、上周测试报告、客户投诉、竞品截图统统堆上桌。但真实情况恰好相反：桌上纸越多，评审人越找不到最关键的那一页。Anthropic 把这个现象命名为 context rot（上下文腐坏）——随着上下文里 token 数量上升，模型从中准确取回信息的能力持续下降。注意它不是一个断崖，而是一段缓慢的斜坡：模型并没有「崩溃」，只是越来越容易在长文里看走眼。

所以上下文工程的核心动作是取舍，不是堆砌。它把"上下文"从一件「传进去就不管了」的输入，变成一个需要反复修剪的预算：每一轮推理之前都要重新问一遍「这一步真正需要看见的是什么」。Anthropic 自己就是这么干的——为了让新一代模型跑得更好，他们把 Claude Code 的系统提示删掉了 80% 以上，在编码评测上没有可测量的损失。不是加了新东西让它变强，而是拿掉了旧东西。

举个具体场景：你让一个编码助手修一个支付回调重复扣款的 bug。它先去读了全量日志（几万 token），又跑了三次测试（每次结果都留在上下文里），还读了一堆边缘情况的代码。到第四轮时，真正重要的「第一次失败断言在哪」已经被压到注意力边缘了。做过上下文工程的版本会怎么做？它只保留一份日志的存放地址而不放原文，测试结果只留「通过/失败 + 证据路径」，旧的读文件记录在接近上限时被自动清掉。同样的模型、同样的任务，结果是它能一路修到底——Anthropic 的内部评测里，光这项「自动清理过时工具结果」就让完成率提升了 29%，叠加记忆工具后达到 39%。

3 · 核心机制

  1. 约束来自架构：注意力是有限预算。Transformer 让每个 token 都能与其它所有 token 建立关联，n 个 token 就是 n² 组关系；上下文越长，模型能抓住这些关系的「注意力」被摊得越薄。
    为什么重要：这从根上解释了「把窗口开到 1M 就能装下一切」为什么是伪解法——窗口是容量上限，不是有效容量，装得下 ≠ 用得上。
  2. 按信息的「保鲜期」分层，而不是一次全给。把材料分成三类：稳定边界（API 兼容性、审批要求）在任务开始时给一次；当前状态（分支、diff、服务健康、最新测试结果）在关键步骤之前重读；原始大件（完整日志、调用链、设计文档）只留摘要与地址，需要时再取。
    为什么重要：它把「预加载」换成「即时检索（just-in-time retrieval）」，token 才会花在当下真正用得到的地方。
  3. 长任务靠三根支柱保住状态。任务跨到几十分钟甚至几小时，上下文一定装不下，于是：压缩（compaction）把历史总结后重新开始，只保留架构决策、未解决问题和最近访问的几个文件；结构化笔记让 agent 把进度写到上下文之外的文件里（Claude Code 的 todo 列表就是这一种）；子智能体（sub-agent）让专门 agent 在干净的窗口里深挖，只把 1,000–2,000 token 的高密度结论交回主 agent。
    为什么重要：这三条都在解决同一件事——「状态没必要都留在对话里」，留在对话里就会变成噪音。
  4. 每轮做一次裁剪与再注入。工具返回默认给摘要＋证据地址，而不是原样倾倒；接近上限时清掉已处理完的原始工具结果；把稳定的东西前置、易变的靠近使用点。
    为什么重要：这一步是「渐进披露」在上下文层面的落地——按需展开，而不是一次摊开。

4 · 应用场景

场景 1 · 编码助手（Claude Code 类）

背景：仓库规模大到无法整体塞进上下文，而任务（改造登录页、修支付回调）需要反复读文件、跑测试。

如何应用：启动时只加载 CLAUDE.md 这类稳定说明，其余靠 glob/grep 即时检索；测试与日志只回传「结论＋证据路径」；接进上限时自动清理旧的读文件与测试结果，并把架构决策、未解 bug 压成摘要继续。

结果：在内部评测的 100 轮网页检索任务中，自动清理让 agent 能跑完原本会因上下文耗尽而失败的长流程，同时 token 消耗降低 84%。

场景 2 · 多智能体研究系统（Anthropic Research 类）

背景：一个市场/技术调研需要并行拆解十几个子问题，单 agent 的上下文会被探索过程淹掉。

如何应用：主 agent 先存战略到外部记忆（因为超过 200K 会被截断），再派多个子 agent 各占一个干净窗口并行深挖；每个子 agent 可能烧掉几万 token，但只回传 1,000–2,000 token 的浓缩结论；最后由引用 agent 逐条标注来源。

结果：Opus 4 作主 agent、Sonnet 4 作子 agent 的组合，在研究评测上比单 agent Opus 4 高 90.2%；代价是 token 用量约为普通对话的 15 倍，只在高价值任务上划算。

场景 3 · 工具结果的「代码执行」模式（MCP）

背景：接了几个 MCP 服务器之后，光是工具定义和中间数据返回就把上下文吃掉一大半。

如何应用：不再把每个工具的完整结果灌回上下文，而是让 agent 在沙箱里用代码去调用和处理这些结果，只把最终的少量结论带回对话。

结果：某实现里工具定义负载从 150,000 token 降到 2,000 token（−98.7%），省下的预算全部让给了真正需要模型判断的部分。

5 · 边界辨析

5.1 不是什么

  • 不是「更高级的提示词工程」：提示词工程处理的是「怎么把一句指令写好」，是一次性的、离散的；上下文工程处理的是「整轮推理里所有进模型的 token 怎么配比」，是迭代的、每一步都要重做的。Anthropic 的原话是「context engineering 是 prompt engineering 的自然演进」，而不是它的同义词。
  • 不是「窗口越大越好」：窗口是容量上限，context rot 说明有效容量另有一条更低的曲线。把窗口当目标去堆内容，只会让取回精度下滑。
  • 不是「少给信息」：目标是高信号，不是短。某些任务确实需要长背景或多组示例，盲目压缩反而会拉低准确率。判断标准应该是任务成功率与错误类型，而不是 token 数字本身。
  • 不是 RAG 的别名：检索增强只是上下文工程里「即时检索」这一条手段；工程还包括分层、压缩、笔记、子智能体隔离等，RAG 只覆盖其中一角。

5.2 常见误解

  • 「把规则写死、把边界情况列全最保险」——恰恰相反。过约束（over-specification）会让提示变脆、难维护，而且一旦工具或任务变化就得重写。Anthropic 建议的是「顶级模型上先跑最小版本，等真实失败模式出现再补」，而不是预防性地写满 if-else。
  • 「系统提示是能力的来源，当然越全越好」——Claude Code 针对新一代模型删掉 80% 以上系统提示，编码评测无可测损失。旧一代模型需要的重复叮嘱，对新一代反而是干扰。
  • 「压缩一定会丢信息，所以能不压就不压」——过度压缩确实会丢掉微妙信息，但完全不动手更糟：上下文一旦接近极限，agent 会直接失败。正确做法是先追求召回（别漏），再迭代提升精度（去冗余）。

5.3 适用与不适用

值得做上下文工程不必大动干戈
多轮、长时程的 agent 任务（编码、研究、数据分析）单轮问答、一次性分类或摘要
工具数量多、结果体积大（MCP、日志、全量数据）工具只有一两个、返回结果很小
上下文反复接近上限、需要跨会话延续对话短到根本碰不到窗口限制
已观测到具体失败模式，知道该修剪哪一块纯凭猜测「先优化一下上下文」

7 · 一句话回顾

上下文工程不是往窗口里塞更多，而是每一步都重新决定「什么值得被看见」——因为对模型来说，更少的高信号 token 往往比更多的低信号 token 更强。
