Skill（技能）

一项把「领域经验」打包成可被模型按需加载的能力单元 · 生成时间 2026-09-05

1 · 一句话定义

Skill 是组织好的指令、脚本与资源文件夹，Claude 在任务相关时按需加载，从而把通用模型变成某个领域的专家。

2 · 个人解释

把 Claude 想象成一位新入职的聪明同事——通识很强，但不了解你公司的报销流程、品牌字体、Excel 模板。一份「Skill」就相当于你为这位同事准备的入职手册 + 工具箱：手册里写了规矩，工具箱里放了脚本和模板。新人遇到相关任务时，会自己去翻这本手册。

最精妙的设计叫渐进式披露（Progressive Disclosure）：Claude 一开始只会看到桌面上每本手册的「目录卡」——也就是 SKILL.md 文件最开头那段 YAML 元数据（name + description），用来判断「这本手册要不要打开」。只有真正相关时，它才会去读 SKILL.md 正文；正文里再点出更细的参考文件，按需加载。这样既能让 Claude 拥有庞大的组织知识，又不会因为「全塞给模型」而撑爆上下文窗口。

所以 Skill 不是一个「让模型更聪明」的咒语，它是一种组织工程经验的方式——把你已经知道的最佳实践、流程、合规要求、可执行脚本，打包成一份可复用的目录，让任何新会话都能在需要的时候调用。

假设一个虚拟场景：你为团队做了一个「品牌物料生成」Skill，里面有 logo 模板、调色板、PPT 母版、Logo 安全距离规则。同事让 Claude 做季度汇报 PPT，Claude 看到任务描述里出现「汇报」「PowerPoint」，自动加载 Skill——它知道往哪儿放 logo、用哪几种颜色、字体规范是什么，输出一份符合品牌规范的 PPT，而不是「默认白底微软雅黑」的版本。

3 · 核心机制

  1. 三层披露，按需加载：第一层是所有 Skill 的 YAML 元数据（始终在系统提示里），第二层是 SKILL.md 正文（相关时整篇加载），第三层是脚本和参考资料（被正文引用后再读）。
    为什么重要：突破「上下文窗口是上限」的束缚，让一个 Skill 能装下任意多的资料。
  2. 任务相关性自动判断：Claude 在推理时扫描元数据描述，决定是否要加载某个 Skill，整个过程对用户透明。
    为什么重要：用户不需要「选择」Skill，模型自己挑，调用链路自然出现在思维链里，可观测。
  3. 可执行代码作为一等公民：Skill 目录里可以放脚本，让 Claude 在需要时调用它跑确定性的逻辑（排序、读 PDF、生成图表）。
    为什么重要：很多任务靠模型吐 token 比不上执行代码，「程序更可靠的部分交给代码」是 Anthropic 的明确建议。
  4. 跨产品同格式：同一个 Skill 文件夹可用于 Claude 应用、Claude Code、API、Agent SDK，2025-12 后被作为开放标准发布。
    为什么重要：避免「在三个产品里重复维护三份知识」的工程负担。

4 · 应用场景

场景 1 · 团队品牌规范落地（Marketing Skill）

背景：设计部每张 PPT 都跑出来不一样，调色板字体混乱。

如何应用：做一个「Brand Skill」：SKILL.md 写品牌守则，assets/ 放 logo、调色板、母版，scripts/ 放一键生成脚本。任何同事让 Claude 做 PPT，模型自动调用。

结果：所有输出默认符合品牌规范，设计师从「逐张审稿」变成「维护 Skill 资产」。

场景 2 · 内部 SaaS 工作流定制（Linear / Jira Skill）

背景：工程团队在 Linear 里有一套独特的 ticket 分类规则，但模型默认不知道。

如何应用：做一个「Ticket Skill」：放团队的项目代号、标签体系、SLA 模板，附上调用 Linear API 的小脚本。Claude 帮工单分类时直接按团队规范走。

结果：新成员用 Claude 处理 ticket 一上手就符合团队约定，不必再单独培训。

场景 3 · PDF 表单批量处理（PDF Skill）

背景：财务部门每周要人工填写 200 份 PDF 报销单。

如何应用：用 Anthropic 自带的 PDF Skill，它内部封装了 PDF 读取、表单字段识别、值回填的指令与脚本。让 Claude 读 CSV → 调 Skill 批量生成填好的 PDF。

结果：原本人工 2 天的工作缩短到 10 分钟，且字段错误率显著下降。

5 · 边界辨析

5.1 不是什么

  • 不是提示词模板：提示词是一次对话中的指令；Skill 是跨对话可复用的目录，结构化、可版本化、可被多个产品共享。
  • 不是模型微调：Skill 不改变模型参数，只是把额外知识按需塞进上下文。模型本身的能力不变，变化的是它此刻被告知的「规矩」。
  • 不是 MCP（Model Context Protocol）：MCP 把外部数据/工具接口标准化，是「接通工具」；Skill 是「教模型怎么用工具」，两者经常配合使用。

5.2 常见误解

  • 「越多 Skill 越好」——并不。每个 Skill 都会消耗少量上下文（描述常驻），十个不相关的 Skill 会持续拉高成本和延迟。
  • 「Skill 等于万能插件」——Skill 依赖代码执行环境（API / Claude Code 开启 beta），且会执行脚本，必须只信任可信来源。
  • 「写得越详细越好」——Skill 的描述决定它会不会被加载。写得糟糕的描述会让模型永远不调用，或在最不该调用时被加载。

5.3 适用与不适用

用 Skill用提示词 / 项目
跨团队、多产品复用的领域流程一次性、临时性的输入要求
