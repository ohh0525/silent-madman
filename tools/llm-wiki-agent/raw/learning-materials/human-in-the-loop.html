人在环审批闸门（Human-in-the-Loop / Escalation Gate）

在不可逆的动作之前，把刹车交回人手里 · 生成时间 2026-09-22

1 · 一句话定义

人在环审批闸门，是把 agent 的动作按「影响大小 × 可逆程度」分级，在不可逆或有后果的写动作之前插入一个写在代码里、可审计、可超时的检查点，等人批准之后才允许执行。

2 · 个人解释

想象你在公司管报销。没有人会给新来的实习生一张无限额的公司卡，让他在没人监督的情况下决定所有付款；现实做法是：小额、常规的报销自动通过，超过某个金额、或者涉及合同条款这类错了很难挽回的，必须有人签字。签得多少不是"越严越好"，而是看两件事 —— 错一次的代价有多大、这个动作有多难撤销。

给 agent 加审批闸门，用的就是这个朴素逻辑。之所以在 2026 年突然变得重要，是因为 agent 从"回答问题的"变成了"动手办事的"：它可以发邮件、改客户记录、提交订单、动生产环境。而这类动作有个讨厌的性质 —— 错了以后，你来不及撤回。邮件发出去收不回，钱付出去要追讨，删除的记录可能没有备份。模型出错的比例也许不高，但只要其中一次落在"写"动作上，损害在任何人注意到之前就已经发生了。

所以业界正在收敛出一条相当简洁的规则：读放开，写留人。让 agent 尽情地读、搜、总结、给出建议 —— 摘要有错，代价便宜、也容易被发现；但凡动作会"发送 / 付款 / 提交 / 删除 / 改动一条作为记录的数据"，就必须经过检查点。这样 agent 仍然干掉了 95% 的活（把信息从各个系统里捞出来、把动作拟好草稿），人只在真正要紧的那一下花几秒钟点头或改一下。

一个具体的画面：客服 agent 判断某客户的投诉符合退款条件，拟好了一笔 ¥3,200 的退款单。系统里写着一条规则 —— 退款金额超过 ¥500 必须人工确认。于是它没有直接执行，而是把「原订单、政策条款、拟退款金额、它的判断依据」打包推给人工队列。客服同事看一眼上下文，十秒内点"批准"或改成 ¥1,800。整个过程 agent 没有停下来等人聊天，它只是把那一个不可逆的决定让了出来。这就是闸门：不是让 agent 变笨，而是让它把最关键的一步交给对的人。

3 · 核心机制

  1. 先给动作分级：列出 agent 能做的每一个动作，按「影响 × 可逆性」分组，再为每一组指定监督方式：人在环（人先批）/ 人在环上（人可否决）/ 全自动（事后抽检）。
    为什么重要：对低影响高频动作硬塞人工复核，只会得到橡皮图章 —— 加了延迟和成本，风险一点没降。分级才是让闸门有用的前提。
  2. 把"提方案"和"执行副作用"拆成两件事：模型只负责生成提案（要做什么、参数是什么、为什么），真正调用副作用工具的是另一条路径，且这条路径必须通过闸门。
    为什么重要：只要模型还能直接调副作用工具，任何闸门都只是装饰 —— 它可以被绕过，或者根本不经过。
  3. 闸门判定必须是确定性的、写在代码/配置里：用动作类别、金额/数量阈值、置信度、输入新颖度等可测信号做判断，并且这份规则要在代码或配置里，不能只写在提示词里。
    为什么重要："一条只写在政策文档、没有嵌进系统实际执行路径的阈值，不算阈值" —— 提示词里的规则会被忽略、会被覆盖、会被诱导绕过。
  4. 暂停要能被别的进程接起来，并留痕度量：一次人工复核可能持续数秒、数小时甚至数天，恢复流程的进程未必是最初暂停它的那个进程，因此暂停前必须持久化完整工作流状态，批准后的动作要幂等（重试不会重复扣款 / 重复发信）。同时要持续度量：automatic rate、override rate、escape rate（本该上报却漏报）、review latency。
    为什么重要：没有度量，闸门会随业务漂移而腐烂 —— 误报太高，团队就放弃响应；漏报太高，等于没有闸门。
# 闸门把一次不可逆动作切成"提案"与"执行"两段 proposal = agent.plan(action="refund", amount=3200, order=order_id) # 1) 确定性闸门:判据来自代码/配置,不是提示词 decision = gate.evaluate( action_class = "money_move", amount = proposal.amount, # > 500 -> 上报 confidence = agent.confidence, ) if decision == "auto_approve": idempotent_execute(proposal) # 幂等:重试不重复扣款 else: state.persist(before_pause=True) # 2) 暂停前持久化 human.notify(decision_payload = { "inputs" : proposal.inputs, # 人看到什么 "action" : proposal.action, # 要做什么 "reason" : proposal.reasoning, # 为什么 "controls": ["approve", "reject", "modify_and_execute"], }) # 3) 可能数天后、由另一个 worker 恢复 resume = human.await_decision(timeout="escalate") idempotent_execute(resume) audit.record(gate_decision=decision, reviewer=resume.reviewer, decided_at=resume.ts, model_version=agent.version)

4 · 应用场景

场景 1 · 保险理赔：自动化做重活，人签那一下

背景：理赔员每天要人工翻阅理赔单据、核对保单条款、再决定打款，平均每单 30 分钟。

如何应用：让 agent 负责分诊与证据收集，并把工具权限限制在"查保单 + 算金额"；超过设定阈值的赔付仍由理赔专员签核。

结果：处理时间从 30 分钟压到 5 分钟（降幅 83%），而"钱出去"这一步仍然握着人的签名 —— 速度来自缩小决策范围，不是放开全流程。

场景 2 · 面向公众的服务 agent：不可答就转人

背景：运输安全部门与演出场馆分别上线了回答旅客 / 观众常见问题的服务 agent。

如何应用：把"要不要转人"做成显式规则：乘客明确要人，或问题落在 agent 知识范围之外，就走转出路径（其中一家是把会话经 Slack 路由给监控这批 agent 的团队，而不是直接掉线）。

结果：约 96% 的常规问询由 agent 自行解决、场馆侧约 95% 的问题无需人工；剩下 5% 不被丢弃 —— 闸门让"自动"与"有人兜底"同时成立。

场景 3 · 中台运维：高风险变更的升级网关

背景：cloud 运维 agent 可以调整生产环境配置、开通权限、改配额。

如何应用：把升级网关做成架构里的一层微服务，而不是一个"确定吗？"的弹窗：按置信度阈值与金额/范围阈值自动触发，给操作者一份决策载荷（agent 读到的原始输入、它准备做的动作、它的推理路径、以及"批准 / 拒绝 / 改后执行"三个按钮）；未决的请求必须带超时与升级路径。

结果：常规变更照常自动执行，而"超额开通权限""动生产配置"这类动作被强制过一次人的判断，且每一步留痕可供复盘与合规检查。

5 · 边界辨析

5.1 不是什么

  • 不是弹一个"确定吗？"的对话框：真正的闸门是架构里的一层，会测量风险、能暂停执行、并且给操作者足够的上下文（原始输入 + 拟执行动作 + 推理依据）。如果批准一个动作需要人再去打开三个系统核对，那说明闸门放错了位置或少了信息 —— 结果一定是无脑点"批准"。
  • 不是"把规则写进提示词"：审批规则属于可执行策略，要在代码或配置里。写在提示词里的阈值可被忽略、被覆盖、被诱导越过，因此不构成控制。
  • 不是 agent 的自我约束：这一点最容易混。像「证据不足就拒答」「只许引用真正打开过的材料」这类机制，主语是模型自己，管的是"说"；审批闸门的主语是系统与人，管的是"写 / 付 / 删"。前者是诚实机制，后者是控制机制，两个层次，缺一不可。
  • 不是沙箱：沙箱约束的是"agent 能碰到什么"（能力边界、物理隔离）；闸门约束的是"碰到之前要不要问人"（决策边界、流程控制）。一个被沙箱严格限制的 agent 仍然可能做出需要人批准的决定。

5.2 常见误解

  • 「加人工复核一定更准」——不一定。设计糟糕的复核会引入自动化偏见（人倾向于顺着系统给出的建议点同意），还附带延迟和成本。HITL 的收益必须用指标验证，不能靠"有个人在看"就假定发生。
  • 「整个系统配一种监督模式」——应该按动作类分别选。低影响、可撤销的高频动作适合全自动 + 定期抽检；中等影响、能可靠回滚的可能只需要人可否决；高风险不可逆动作才需要人在环前置批准。
  • 「闸门会拖慢速度」——真正拖慢速度的是不设分级：把所有输出都送人，队列会随业务量一起爆掉，最后没人认真看。加上置信度分流之后，人工负载只随"真正的不确定性"增长，这也是闸门能规模化的唯一方式。
  • 「批准过了就结束了」——每次复核的编辑与否决都应该回流到评测数据集与阈值调优里；闸门不只是刹车，也是一个持续校准的信号源。

5.3 适用与不适用

该设闸门不必设闸门

动作不可逆或撤销成本极高（发对外邮件、删除记录、改生产环境）纯读取、查询、总结、建议（提高自动通过率即可）
受监管或需对外解释责任归属（需"谁在何时批了什么"）复核者几乎一律点头的场景 —— 那只是在给流程加成本
校准提示（来自实践，非研究结论）：先用偏保守的阈值跑一段时间，再逐类往外推：把收到的升级分成"团队真的处理了"与"其实没改动就放行"两类，如果误报占比过高，就抬高最常误触的那条规则的阈值；如果发现本该上报却漏了，就单独下调那一类的阈值。然后重复。同时给每条转出规则设定复核节律 —— 规则会随业务变化而失效。

7 · 一句话回顾

审批闸门不是让 agent 变慢，而是把"不可逆的那一下"从模型手里收回来 —— 读让它放开做，写留给人点头，并且这条规则必须写在代码里、能被度量、能被另一个进程接起来。
