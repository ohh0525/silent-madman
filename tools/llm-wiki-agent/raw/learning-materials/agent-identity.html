智能体身份与委派授权（Agent Identity & Delegated Authority）

让「谁在动手、代表谁、被允许做什么」变成可验证的事实 · 生成时间 2026-09-22

1 · 一句话定义

智能体身份与委派授权，是让 agent 在被调用时能证明「我是谁、我代表谁、我被允许做什么」，并让这份授权在 agent 之间传递时只能变窄、不能变宽的一套可验证机制。

2 · 个人解释

先想一个你熟悉的场景：你去银行代办一笔业务，柜员不会问「你是哪家的人」，而会要求你出示两样东西 —— 你自己的身份证明，以及一份写清授权范围的委托书。这两样缺一不可：只有身份证明，柜员不知道你能替谁办事；只有委托书，柜员不知道拿着它来的是不是本人。而且委托书上一定会写明「只能办这一笔」「只能取这个额度」「有效期到今天下午五点」。

智能体身份要解决的，是同一件麻烦事，只不过「来办事的」从人变成了软件。过去企业里给程序开权限，常见做法是发一个 API key，或者干脆用一个共享的服务账号 —— 这相当于给助理配了一把万能钥匙，门都能开，出了事也说不清是谁开的。当 agent 开始替你打电话、改记录、下单付款时，这个做法就彻底不够用了：商户需要确认「来办事的这个 AI 是谁」，平台需要确认「它代表哪位用户」，而用户需要知道「它到底被允许花我多少钱」。

所以这套机制的核心产物不是「一个账号」，而是一条可验证的链条：agent 的运行实例有身份（换台机器也能被验证），它手里拿的不是用户的原始凭据，而是一张写着「我是 X，代表用户 Y，范围只读/上限 N，30 分钟内有效」的凭据；当这个 agent 又派生出子 agent 时，子 agent 拿到的是一份全新的、比父级更窄的凭据，而不是父级令牌的复印件。

举个具体的：你对一个差旅 agent 说「帮我订下周三去上海的高铁」。这个 agent 背后可能连着订票服务、酒店服务和报销系统。它自己不具备付款权，但可以带着「代表你、只读你的行程、可写入订单草稿」的凭据去订票；到了真正付款那一步，系统看到的凭据里写的是「代表你，付款上限 ¥0」—— 于是它必须回头找你要一次明确的批准。整个过程里，每一跳都留下了「谁在什么时候、代表谁、用了什么范围」的记录，任何一环的授权都能被单独撤销。

3 · 核心机制

  1. 建立负载身份（workload identity）：给跑 agent 的那个软件实例发一个可被依赖方验证的身份，而不是复制一份人类账号。
    为什么重要：名字写在提示词里不是身份 —— 一个自称「我是财务助手」的 agent 无法被任何服务验证；身份必须由受信任的运行时或身份系统签发。
  2. 以「代表用户」的方式换取短期凭据：agent 从不持有用户的原始凭据，而是通过令牌交换（OAuth 2.0 Token Exchange，RFC 8693）拿到一张用户委派而来、受众受限、短时效的访问令牌。
    为什么重要：这把「一次泄露 = 全部权限」压缩成「一次泄露 = 单个用户在当次范围内的临时权限」，同时天然产生"每个动作都能映射回一个人类负责人"的审计线索。
  3. 每一跳收窄（attenuation）：父 agent 派生子 agent 时，子 agent 必须得到一份新签发、更窄的凭据，其范围 / 幅度 / 有效期 / 委派深度只能逐跳变小。
    为什么重要：这是「权限不能越传越大」从口号变成机制的唯一手段；没有它，一条调用链跑几跳之后，末端的实际权限就没人能说得清。
  4. 双主体记录 + 撤销可传播：每个请求的凭据里同时保留「执行的负载」与「被代表的用户」，并接入撤销传播机制（如 OpenID Shared Signals），让一次撤销能抵达所有还握着旧令牌的 agent。
    为什么重要：只记用户可以，就丢掉「是哪个 agent 在动」；只记负载，就丢掉用户的授权与撤销上下文。这两者合并就没人能问责。
# 一次被正确委派的 agent 动作 user_token = idp.issue(user=U, scope="read:trips") agent_identity = runtime.attest(agent="travel-agent", pod="...") # 1) 交换成 agent 代表 U 的短期令牌(双主体) delegated = oauth.token_exchange( subject_token = user_token, # 代表谁 actor = agent_identity, # 谁在动 audience = "booking-service", expires_in = 1800, ) # 2) 派生更窄的子凭据 —— 只许收窄 child = delegate(delegated, scopes=["read:trips", "write:draft"], pay_limit=0) # 3) 依赖方自行校验:签发者 / 受众 / 有效期 / 本地策略 assert verify(child) and child.audience == "booking-service" # 4) 双主体 + 动作留痕(不是只记 prompt) audit.record(actor=child.actor, on_behalf_of=child.sub, scope=child.scopes, target="booking-service")

4 · 应用场景

场景 1 · 企业把 agent 纳入 IAM（身份治理）

背景：一家公司内部已经跑着几十个 agent，分别接 CRM、邮件、日历、财务系统，此前都用共享服务账号。

如何应用：给每个 agent 一个独立身份（微软 Entra Agent ID 于 2026-05-01 随 Agent 365 正式可用，Okta for AI Agents 于 2026-04-29 正式可用），把最小权限下沉到工具边界：读日历的 agent 不会因此获得发邮件或改文档的权限。

结果：agent 清单、权限范围、撤销流程与员工身份走同一套治理；一条授权可以在不动其他 agent 的前提下单独收回。

场景 2 · 跨平台办事：身份要能"带证上岗"

背景：用户让 AI 帮自己安排出差，中间要经过商户、订票、支付等多个平台。

如何应用：采用在 2026 外滩大会发布的 APASS（围绕「Agent 是谁、代表谁、被允许做什么、行为是否可信」提供身份注册、持续核验、意图安全与可信存证）与 ASL 互联协议：授权凭证保存在手机端，只开放当前任务所需权限，可随时收回；多智能体接力时用户指令不能被改动、权限不能越传越大，涉及花钱仍需用户点头。

结果：据披露 APASS 已接入超过 100 万个智能体、覆盖 442 家服务供给方 —— 也就是说"持证上岗"已从演示走进真实业务链路。

场景 3 · MCP server 的授权：不止于"自述身份"

背景：你接了一个第三方 MCP server，它需要访问你的内部资源。谁来决定它有没有这个权限？

如何应用：按 MCP 自己的授权 profile 来做 —— 走 HTTP 传输的 server 需作为 OAuth 2.1 资源服务器并实现 OAuth 2.0 Protected Resource Metadata（RFC 9728）让客户端发现授权服务器；客户端必须实现 PKCE 的 S256，并在元数据显示不支持 PKCE 时拒绝继续。

结果：调用方身份由外部专用授权服务器签发（短时效、受众受限），而不是靠 MCP 协议报文里的自述字段 —— 后者只能说明"它说自己是谁"。

5 · 边界辨析

5.1 不是什么

  • 不是 API key / 共享服务账号：静态密钥既没有委派语义（不能表达"代表谁"），也没有按动作留痕与撤销能力。把 agent 塞进一个共享人类账号，还会带来一个隐蔽后果：人一离职，agent 的访问权跟着静默失效。
  • 不是协议里的"自述身份"：MCP 在 2026-07-28 修订后把协议层做成无状态，每个请求都带版本与客户端身份；但自述不等于可验证。身份（谁在调用）/ 委派（代表谁）/ 授权（允许做什么）/ 运行期策略（此刻是否放行）是四件不同的事，任何一件都不能替代另一件。
  • 不是沙箱 / 执行隔离：身份回答「你是谁、能做什么」（逻辑授权），沙箱回答「你物理上跑在哪」（物理隔离）。两者不可互相替代：一个身份完全合法的 agent 仍然可能跑在一个能写穿宿主内核的环境里。
  • 不是权限清单本身：把工具权限列成表是必要动作，但清单是输入，不是机制。机制是这份清单如何被签发、如何逐跳收窄、如何被撤销、如何被依赖方独立校验。

5.2 常见误解

  • 「agent 是我的数字分身，用我的账号最方便」——最方便也最危险：一旦被诱导，攻击者拿到的就是你的真实权限，而且这条路径能绕开"这个用户本来够不到的数据"这一层保护。委派模型的价值恰恰是让下游按用户真实权限 + 更窄范围来做检查。
  • 「给 agent 的身份就是给它起个名字」——名字不是身份。生产级身份必须由受认证的运行时或身份系统签发、可被依赖方验证；否则它只是一段自我描述。
  • 「定好权限就一劳永逸」——agent 身份需要和人类身份一样有生命周期：签发、轮换、暂停、撤销。企业实践里最常见的缺口正是没有撤销流程，以及 agent 默默继承共享账号的常驻权限。

5.3 适用与不适用

适合引入完整身份与委派不必上这套
agent 会写数据、花钱、动权限，或跨组织边界调用单工具、单用户、本机短期运行的实验脚本
需要"每个动作映射回人类负责人"的审计（受监管行业尤甚）纯读取、可随时重建、无副作用的查询型 agent
多个 agent 接力完成一个任务（委派链必须收窄）还没上生产、权限范围一句话就能说清的小范围试点
一条好用的判据：如果一个 agent 的工具权限无法用一句话说清，那它就是过宽的。此外，成本并不高 —— 云上负载身份通常免费或几美元/月；把身份做在第一次上生产之前，比事后给一个已经在 5 个 SaaS 里留了活跃凭据的 agent 补身份，便宜得多。

7 · 一句话回顾

Agent 的身份不是一个账号，而是一条「我是谁 + 我代表谁 + 我只被允许做这些」的链条 —— 它的价值不在开头签得全，而在每一跳都只能变窄、且随时收得回。
