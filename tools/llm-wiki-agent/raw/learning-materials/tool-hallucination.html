工具幻觉与封闭世界消解（Tool Hallucination & Closed-World Resolution）

agent 会调用根本不存在的工具 —— 而任何权限门控都拦不住它 · 生成时间 2026-09-22

1 · 一句话定义

工具幻觉，是指 agent 调用了注册表里根本不存在的工具，或给真实工具传了任何 schema 都没声明过的参数；而因为这种调用在构造上不是任何门做过的决策，所以必须在所有权限门控之前先做一次「注册表成员资格 + 签名」的封闭世界消解。

2 · 个人解释

先打个比方。公司前台给每个员工发了一本内部电话簿，簿子上有各部门的分机号。你吩咐实习助理"给财务的张三打个电话，说报销单我签好了"。助理翻开电话簿 —— 但没有"张三"这个人，于是它自己编了一个分机号拨出去；或者簿子上有"报销"这个分机，它却顺手加了一句"顺便帮我把额度改成五万"，而那个分机从来没有"改额度"这个功能。

这就是工具幻觉。它跟我们平常担心的"agent 选错工具"不是一回事：选错工具，是它从电话簿里挑了一个不该挑的号码；工具幻觉，是它拨了一个电话簿上根本没有的号码，或者说了那个分机听不懂的话。

为什么这件事格外麻烦？因为我们现在防 agent 出错的两道防线，都建立在同一个前提上 ——「这次调用指向一个真实存在的工具」。一道防线负责"帮你挑对工具"（工具选择），一道防线负责"约束你能用真工具做什么"（权限门控）。可如果那个工具压根不存在，门控在逻辑上就没有对手可判：它只能判断"你有没有权限用 我放出来的 工具"，而一个不存在的工具从来就不在它放出来的名单里，所以这一条调用根本不是任何一道门做过的决策 —— 门也就无法拒绝它。

这不是"防得不够细"，而是一处结构性盲区。2026 年 9 月 16 日的一篇论文把它量化了：在 10 个托管模型、两种调用面上，一共捕捉到 322 次真实幻觉；更反直觉的是，模型规模帮不上忙 —— 一个 675B 参数的模型和一个 7–8B 的模型，在这一点上表现相当。指望"下一代更大的模型自己长出免疫力"，这条路走不通。

所以正确的做法非常朴素，甚至有点"不够聪明"：在最前面装一道很笨的闸 —— 查一下注册表里到底有没有这个工具、签名对不对得上。论文把它称作 Resolution Rung（消解阶），并强调它的价值不在算法而在位置：它只能装在最上游，必须早于任何权限门控。因为门再密，也拦不下一件它从未被问过的事。

3 · 核心机制

  1. 幻觉是怎么产生的：模型见过大量形如 delete_file 的调用轨迹，于是很自然地在需要时生成一个形如 wipe_disk 的"同类工具名"；它知道转账工具需要一个金额，就会顺手续上一个 schema 里从未存在的 override 开关。
    为什么重要：这说明幻觉来自"语言的顺畅补全"，而不是来自配置错误 —— 改文档、改提示词都治不了它，只能靠外部事实核对。
  2. 为什么门控拦不住它：门控的判定对象是"被它放进可见集合的工具"；而幻觉工具按定义不在这个集合里，因此这次调用不会成为任何一次门控决策，门根本没有机会拒绝它。
    为什么重要：它把这条防御从"加固我的门"变成了"在门前加一级事实核对"，是架构位置的问题，不是策略强度的问题。
  3. 消解阶：查成员资格 + 验签：在分发任何调用之前，先做两件免训练的事 —— ①这个工具名是否在封闭注册表里；②它的契约签名是否与可信来源一致。通过之后，才轮到权限门控、最小权限、审计这些下游机制。
    为什么重要：顺序错了等于没做。论文给出的结论很干脆：幻觉防御必须先于任何因果门。
  4. 为什么会话面会新增幻觉面：当多个 MCP server 被合并进同一个命名空间时，会出现单个注册表无法表达的新问题 —— 名称碰撞（collision）与遮蔽（shadowing）。论文在真实 MCP 调用面上又测到 154 次幻觉，其中包括在"单注册表"表面上表现干净的前沿模型。
    为什么重要：这说明工具数量一多，幻觉面是"合并"这个动作本身带来的，不是某个模型变差了 —— 你越是用 MCP 把工具拼起来，越需要这一级消解。
# 顺序就是全部:消解在最上游,门控在其后 call = model.emit() # {"tool": "wipe_disk", "args": {...}} # ---- 第 1 级:封闭世界消解(免训练,只做事实核对)---- rung = resolve(call, registry) # 注册表成员资格 + 签名校验 if rung == "UNRESOLVED": return reject(call, reason="no such tool") # 幻觉在此终止 if rung == "SIGNATURE_MISMATCH": return reject(call, reason="contract not tamper-evident") # ---- 第 2 级:到这里才轮到权限门控 ---- if not policy.allows(call, principal=delegated_token): return reject(call, reason="out of scope") execute_idempotent(call) # 幂等执行 + 审计 # 注意:第 2 级永远拦不住第 1 级的失败 —— # 幻觉调用不是任何门做过的决策,门对它没有判定权。

4 · 应用场景

场景 1 · 接了三四个 MCP server 之后（命名空间合并）

背景：为了功能齐全，同一个 agent 同时挂了文件、数据库、支付三个 MCP server，工具名被并到同一张清单里。

如何应用：在工具分发层前加一级封闭世界消解：先按注册表核对名称归属与签名，再处理同名/近名遮蔽问题（例如两个 server 都提供 search 时的歧义）。

结果：挡住一类"模型本身没问题、合并之后才出现"的调用失败 —— 论文在真实 MCP 面上测到的 154 次幻觉正属于此类，其中包含在单注册表面完全干净的模型。

场景 2 · 让模型直接吐自由 JSON（最宽的调用面）

背景：为了让模型灵活，调用格式不做 schema 约束，直接解析一段自由 JSON 当工具调用。

如何应用：两件事同时做 —— 把调用面收窄（改用未声明参数就发不出来的受约束格式），并且仍然保留最上游的消解阶，因为收窄只是降低概率，不会归零。

结果：伪造工具名会明显集中出现在最自由的调用面上，这是论文的测量发现之一：接口的自由度直接放大幻觉空间。收窄接口 + 最上游核对，两条一起才有效。

场景 3 · 生产环境的工具网关（"想对了、名字写错"）

背景：agent 在生产里要删一条测试记录，它"想对了"，但把工具名写成了一个曾在训练数据里见过的近义名。

如何应用：把消解阶放在工具网关最前面，与权限门控、幂等执行、审计串成固定顺序；未消解的调用直接拒绝并记一条"模型幻觉"指标，而不是让它落到下游变成一次真正的破坏性动作。

结果：一次幻觉从"对一个 agent 而言是无界动作"降级为一次可统计的解析失败 —— 这类失败会持续发生，但你至少知道它发生了、发生了几次、集中在哪个调用面。

5 · 边界辨析

5.1 不是什么

  • 不是"工具选择"问题：工具选择问的是"该用哪个真工具"（在真工具之间排优先级）；工具幻觉问的是"这次调用指向的工具存在吗"。前者优化排序，后者是一条事实前提 —— 论文明确指出选择类方法都以"调用指向真工具"为前提，因此对幻觉无能为力。
  • 不是"权限门控"问题，也不在它的上游被替代：门控约束真工具的使用边界（最小权限、契约完整性校验）。它和消解阶是上下游关系：先消解，后门控。顺序反了就漏掉一整类失败。
  • 不是普通的解析错误 / 格式错误：JSON 写坏会被解析器拦下，代价是一次重试；而一个格式完全合法但指向不存在工具的调用，格式校验是拦不住的 —— 对会动手的 agent 来说，"执行一次幻觉调用不是无害的解析错误，而是一次无界动作"。
  • 不是"等更强的模型就能解决"：测量显示规模不给免疫力，675B 与 7–8B 在这一点上相当。把它当作能力问题会导致错误的路线选择（继续换更大的模型）而非正确的（在架构里加一级事实核对）。

5.2 常见误解

  • 「我把 schema 写清楚就不会幻觉了」——收窄接口确实显著降低概率（论文也观察到两种调用面之间的巨大差距），但不会归零：还有一类"借来的参数"在 schema 上与合法调用无法区分，是论文明确说明的消不掉的残余。所以约束是必要的，但它是概率手段，不是终极防线。
  • 「我加了权限门控就安全了」——门控防的是越权使用真工具，防不住调用不存在的工具。真正能拦住它的位置，比门控更靠前。
  • 「工具多了只是管理麻烦一点」——合并命名空间会新增幻觉面（碰撞与遮蔽），这是结构性的，不是数量带来的线性增长。

5.3 适用与不适用

必须加消解阶可以暂时不加
任何能产生副作用的工具调用（写、发、付、删）纯离线实验、工具集固定且极小、没有人身损害的玩具环境
多个 MCP server / 多家供应商的工具被合并进同一命名空间只挂一个 server、且工具名互不冲突的极简集成
调用面较自由（自由 JSON、动态生成工具名）已用强约束格式把调用面收得很窄（仍建议保留，只是优先级可降低）
落手顺序建议：①先问一句"我有没有一张封闭的工具注册表"（没有就先立这张表，它是消解的前提）；②把消解阶放在分发路径的最前面，并断言它早于权限门控；③给"未消解"单独记一个指标（哪类工具名最常被编造、集中在哪个调用面）；④合并 MCP server 时，把名称碰撞/遮蔽当作一次需要评审的变更，而不是配置细节。

7 · 一句话回顾
