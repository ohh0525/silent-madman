## Summary
A concept-learning HTML document (7-section format) generated by the silent-madman concept-explainer skill on 2026-09-22 — the first of three "actor-side" materials. Defines agent identity & delegated authority as the set of verifiable mechanisms by which an agent proves *who it is, on whose behalf it acts, and what it is permitted to do* — and by which that authority may only **narrow** as it propagates between agents. Grounds the concept in OAuth 2.0 Token Exchange (RFC 8693), the IETF `draft-klrc-aiagent-auth` work, MCP's own authorization profile, and enterprise IAM products that reached GA in 2026.

## Key Claims
- **A name in the prompt is not an identity.** An agent that says "I am the finance assistant" cannot be verified by any service. A production identity must be issued by a trusted runtime or identity system, and be checkable by the relying party.
- **The agent never holds the user's raw credentials.** It exchanges them — OAuth 2.0 Token Exchange, RFC 8693 — for a short-lived, audience-restricted token that carries a **dual subject**: the *actor* (which agent is acting) and the *subject* (which user is being represented).
- **Attenuation is per hop, and it is not free.** A child agent must receive a **freshly issued, strictly narrower** credential — scope / magnitude / validity / delegation depth may only shrink. RFC 8693 records delegation but does **not** guarantee per-hop attenuation; that needs a separate mechanism (the material points at *Verifiable Attenuated Delegation* draft-00, 2026-08-27). Without it, a chain of a few hops has an authority nobody can state.
- **Four things that are not substitutes:** identity (*who is calling*), delegation (*on whose behalf*), authorization (*what is allowed*), runtime policy (*is it permitted right now*).
- **MCP's own profile is the concrete instance.** HTTP-transport servers must act as **OAuth 2.1 resource servers** and implement **OAuth 2.0 Protected Resource Metadata (RFC 9728)** so clients can discover the authorization server; clients must implement **PKCE S256** and must **refuse to continue** when metadata indicates PKCE is unsupported. Caller identity is issued by an external, dedicated authorization server — **not** asserted in MCP protocol messages, which can only ever say "it claims to be X".
- **Not a sandbox.** Identity answers *what you may do* (logical authority); a sandbox answers *where you physically run* (isolation). Neither substitutes for the other: a fully legitimate agent can still run in an environment that can write through the host kernel.
- **Not a permission list.** Enumerating tool permissions is necessary but it is an *input*; the mechanism is how that list is issued, narrowed per hop, revoked, and independently verified downstream.
- **2026 adoption is real, not a demo.** Microsoft **Entra Agent ID** GA'd **2026-05-01** (with Agent 365); **Okta for AI Agents** GA'd **2026-04-29**; **APASS** (announced 2026-09-11 at the Bund Conference) reports **>1,000,000 agents** registered across **442** service providers, with credentials held on-device, scoped to the current task, revocable at any time — and money movement still requiring the user's explicit approval.
- **The governance gap is traceability and revocation.** Only **28%** of organizations can trace agent behaviour back to the human initiator; the most common enterprise gap is the **absence of a revocation process**, plus agents silently inheriting a shared account's standing privileges.
- **The timing asymmetry matters:** adding identity *before* first production is roughly **1–2 engineer-weeks**; retrofitting an agent already holding live credentials in five SaaS systems is roughly **3–6 weeks**.

## Key Quotes
> "智能体身份与委派授权，是让 agent 在被调用时能证明「我是谁、我代表谁、我被允许做什么」，并让这份授权在 agent 之间传递时只能变窄、不能变宽的一套可验证机制。"

> "名字写在提示词里不是身份。生产级身份必须由受认证的运行时或身份系统签发、可被依赖方验证；否则它只是一段自我描述。"

> "Agent 的身份不是一个账号，而是一条「我是谁 + 我代表谁 + 我只被允许做这些」的链条 —— 它的价值不在开头签得全，而在每一跳都只能变窄、且随时收得回。"
