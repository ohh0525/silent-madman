## Summary
A concept-learning HTML document (7-section format) generated by the silent-madman concept-explainer skill on 2026-09-16. Defines Context Engineering as the discipline of deciding, at every inference step, which tokens to place into the bounded context window — targeting the *minimal set of high-signal tokens* rather than maximal volume. Positions it as the natural evolution of prompt engineering, grounded in the observation that retrieval accuracy degrades (context rot) as token count grows.

## Key Claims
- Context engineering ≠ prompt engineering: the former governs the composition of *all* tokens in a turn (iterative, per-step), the latter only how a single instruction is phrased (one-shot, discrete).
- **context rot** — as token count in the window rises, the model's ability to retrieve information accurately declines continuously (a slope, not a cliff). Window size is a capacity ceiling, not effective capacity.
- "Bigger window solves everything" is a false solution: the constraint is architectural — Transformer self-attention costs n² in token-pair relationships, so attention is a finite budget.
- Long-horizon tasks survive on three techniques: **compaction** (summarize history and restart), **structured notes** (write state to files outside context; e.g. Claude Code's todo list), and **sub-agents** (isolated clean windows that return only 1,000–2,000 high-density tokens).
- Just-in-time retrieval replaces pre-loading: keep identifiers/addresses instead of raw payloads; reread authoritative state right before key steps.
- Anthropic removed 80%+ of Claude Code's system prompt with no measurable coding-eval loss — *less* context, *better* results.
