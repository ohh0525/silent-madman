### 推送:修了一次 `.api_push_state.json` 陈旧 → 422 not a fast forward

- 现象:`python output/_tools/api_push.py` 报 `HTTP 422 Update is not a fast forward`(待推送 56 个,第 1 个就要重建)
- 根因:**本地历史里存在「成对重复」的提交链**。上一轮 API 重建过 commit(push 后又被 merge 回本地),于是 `rev-list BASE..HEAD` 同时列出:①**原始本地提交**(26 个,state 里已记录映射)与 ②**API 重建版孪生提交**(27 个,它们**本身就是远端 sha**,state 里没有记录)。脚本看到②不在 `pushed` 里 → 试图在远端重建,并把 main 指回一个**祖先**,自然非快进 → 422
- 诊断关键:`git rev-parse <sha>^{tree}` 对比 → `tree(merge)=tree(14d3cc50)=tree(b5e20182)=f095c4a2…` 三者完全一致,证明**合并后除了当天提交,其余内容早已在远端**
- 修法(仅改**机器本地的检查点**,未动任何被跟踪文件):备份 state → 给②这 27 个孪生提交加**自映射**(`local sha -> 同一个 sha`,因为它们就是远端提交)→ 给 merge 提交映射到当前远端 head(`6fc16766 -> b5e20182`,二者 tree 相同)→ 只留当天提交待推
- 结果:远端 main = `7e4089d9`,**远端 tree = 本地 tree = `62fb3775…`**(TREE MATCH True),三个文件在远端均已可见;脚本打印的 `本地主提交一致 = False` 是已知的 SHA 假警报
- **教训(长期有效)**:凡是从远端「merge 回本地」之后,`.api_push_state.json` 必然出现「成对孪生」缺失映射,**下一次推送前要先按 tree 比对补映射**,否则必撞 422。判据永远是 **tree 哈希**,不是 SHA
