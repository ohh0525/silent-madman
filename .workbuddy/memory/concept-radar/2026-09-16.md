### 候选 1 ⭐ 首选:上下文工程(Context Engineering)

**一句话定义**:不是「怎么写好一条 prompt」,而是「怎么决定每一轮到底往上下文里放哪些 token」——系统提示、工具定义、Skill、记忆、工具返回结果都是它的材料,核心目标是**找到能产出目标结果的最小高信号 token 集合**。

**为什么是"当下"最有价值**:
你的知识网里已有 [[Agent]] / [[LLMContext]] / [[ProgressiveDisclosure]] / [[Skill]] 四个节点,但**缺了把它们统起来的那层框架**——Anthropic 在 2026-07 正式把它命名为 context engineering,而你的 `overview.md` 里那句"On-demand loading is the dominant solution shape"其实已经是这个框架的一半结论了,只差一个正式的名字和量化标尺。

**关键事实(tool-verified)**:

| 结论 | 数字 | 来源 |
|---|---|---|
| 更大窗口 ≠ 更好 | 性能随上下文装满而**渐变下降**(gradient,不是断崖),Anthropic 称之为 **context rot** | Anthropic Engineering / besthub 解读 |
| 新模型不该被过度约束 | Claude Code 系统提示**删掉 80%+**,编码评测无可测损失 | Anthropic 官方博客(2026-07-24) |
| 上下文瘦身能提准确率 | 工具定义 **77K → 8.7K tokens(−85%)**,Opus 4.5 准确率 **79.5% → 88.1%** | brettsanders 对 51 篇工程博客的综述 |
| 极端案例 | MCP 代码执行模式把 **150K → 2K tokens(−98.7%)** | 同上 |

**与已有概念的边界辨析**:

| 容易混淆 | 区别 |
|---|---|
| Context Engineering vs [[LLMContext]] | LLMContext 是**容器**(token 预算,受 Transformer n² 成本约束);Context Engineering 是**往容器里装什么的决策方法**。一个是约束,一个是策略。 |
| Context Engineering vs Prompt Engineering | Prompt 只占上下文的一小块。Anthropic 原话:你不发消息时,上下文仍由系统提示、Skill、CLAUDE.md、记忆组装而成。 |
| Context Engineering vs [[ProgressiveDisclosure]] | Progressive Disclosure 是 context engineering 的**一种具体手法**(按需加载);后者是上位框架,还包含 just-in-time retrieval、compaction、sub-agent 隔离等。 |

### 候选 2:带溯源的智能体长期记忆(Provenance-Aware Agent Memory)

**为什么是"当下"最有价值**:

### 候选 3:MCP 无状态化(Stateless MCP / MCP 2026-07-28 规范)

**一句话定义**:MCP 协议层**去掉了会话(handshake)**——删掉 `initialize`/`initialized` 交换与 `Mcp-Session-Id` 头,每个请求自带协议版本、客户端身份与能力,于是 MCP server 变成**普通 HTTP 服务**,可以直接挂在 round-robin 负载均衡后面。

**为什么是"当下"最有价值**:
这条**首先是一个维护发现**:你 wiki 里的 [[MCP]] 页描述的仍是「连接工具的协议」这个旧图景,但 2026-07-28 是 MCP 发布以来**最大的一次修订**,你的页面已经过时了。其次它对你的 Agentic Workflow 实践有直接影响——GitHub 自己的 MCP Server 在新规范落地前就删掉了 Redis 会话存储、停止了逐请求 payload 检查。

**关键变化(tool-verified)**:

| 变化 | 内容 |
|---|---|
| 无状态核心 | 移除 `initialize` / `initialized` 交换与 `Mcp-Session-Id`;请求独立 |
| MRTR | Multi Round-Trip Requests——无状态下仍能中途向用户确认(如"这个查询会删数据,确认?") |
| 路由头 | `Mcp-Method` / `Mcp-Name` 成为 Streamable HTTP 必需项,网关不必解析 body 即可路由与限流 |
| 缓存 | list 结果新增 `ttlMs` / `cacheScope` |
| Extensions | Tasks / MCP Apps / Enterprise Managed Authorization 正式成为一等扩展 |
| 生态落地 | GitHub 删 Redis 会话存储;Cloudflare 每请求跑新无状态实例;Manufact 包体 **−83%**、速度 **+25%** |
| 风险 | 仍 import `mcp.server.fastmcp` 的 server 停在 1.x 线、说着已退休的握手——**因为有回退兼容,不会有任何报错提示你** |

**与已有概念的边界辨析**:

| 容易混淆 | 区别 |
|---|---|
| 无状态 MCP vs 有状态 MCP | 不是「有没有数据」,而是「协议层要不要持有会话」。server 仍可有自己的状态,只是不再依赖协议会话。 |
| Tasks 扩展 vs 同步调用 | Tasks 是为「跑几分钟的活」设计的;它和 subscriptions、progress notifications 的整合理由,正是 roadmap 里「三个答案不能各说各话」那个问题。 |

**建议下一步**:不必单独开 HTML。**优先做的是更新 wiki 的 `concepts/MCP.md`** 并在 `raw/tools/` 补一份规范摘要作为可溯源的新源材料——这属于下次 ingest,需要你确认。
