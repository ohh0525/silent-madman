### 11-23A 学习式上下文保留 / Learned Context Retention（CarryOn） ⭐⭐⭐

**一句话**：用一个轻量上下文管理器把「**紧凑的执行状态**」与「**细粒度的、带来源链接的证据**」配对，由**学习出来的选择器 + 自适应保留策略**决定留什么，**不额外调用 LLM 做上下文管理**；另提两个互补指标——`Sα`（在计入资源使用下优先任务成功）与 `NCS`（normalized cost per success，每次成功所耗资源）。在 AppWorld / OfficeBench / Tau2 Telecom 上配三个 LLM Actor，取得 **75.7%** 宏平均任务成功率，超最强基线 **6.7 个百分点**，两指标平均得分均最佳。

- **概念名（中英）**：学习式上下文保留 / Learned Context Retention（CarryOn）
- **为什么"当下"最有价值**：overview 的 [[ContextEngineering]] 回答「谁决定放什么进窗口」，但本库记过的答案只有「按生命周期分层 + 即时检索 + 压缩」（方法层）与「全留 + grep」（11-22B GrepMem）——CarryOn 给出**第三种**：**学出来的选择性保留**，且证据**带来源链接**（[[Provenance]] 在上下文保留层的新形态）。它正面顶到 [[Compaction]] 的默认（摘要会丢掉后续动作需要的精确细节），又用 `Sα` / `NCS` 把「成本」正式计入成功度量——直接呼应第 4 条「资源定价盘点」（见 `SCAN-LINES.md`）。与用户当下主线（Agent 记忆/上下文）接缝最紧。
- **来源链接（均 [verified]，一手 abs 已 WebFetch 直开核验）**：
  - https://arxiv.org/abs/2611.17808 [verified] —— 一手 abs（直开）：标题、八作者（Lihuan Li / Ruiyi Yang / Jiru Wang / Yifan Duan / Xiachong Lin / Hao Xue / Yang Song / Flora Salim）、v1 2026-11-13、cs.CL+cs.AI、全部量化结论出自此页摘要
  - https://arxiv.org/pdf/2611.17808 [verified] —— 一手 PDF（abs 页 View PDF 链接）
  - https://arxiv.org/html/2611.17808v1 [verified] —— 一手 HTML 全文（abs 页 HTML 链接）
- **一句话定义 + 边界辨析**：定义——把上下文管理本身交给一个学习出来的选择器，保留紧凑执行状态 + 源链接证据，用「成功优先且计成本」的指标评判。边界：① vs [[Compaction]]——那条是**有损压缩**（改内容、丢细节）；本条是**选择性保留 + 证据留链**，且明确「更短的上下文不必然支持更好的决策」。② vs 11-22B GrepMem——GrepMem 是**无损全留 + 正则召回**（不选择）；CarryOn 是**学出来的选择性保留**，两者是「不选择 vs 学会选择」的两端，共同反对摘要式压缩。③ vs [[ContextEngineering]]——那是总原则；本条是该原则的一种**可学习实现**。
- **⚠️ 证据边界**：预印本、单团队、自报；`Sα` / `NCS` 是作者新提指标，非公认基准；「无额外 LLM 调用」成立了成本结构，但选择器本身需训练，训练成本摘要未提；一手 abs 未提代码开源。成篇前须开 PDF 核训练设置与三基准分表。

### 11-23B 决策效用记忆 / Decision-Utility Memory（MemCredit） ⭐⭐⭐

**一句话**：把记忆选择从「**语义相关**」换成「**决策效用**」——通过**受控反事实干预**估计单条记忆在「状态 / 参考上下文 / 策略」条件下的**边际贡献**，蒸馏成一个轻量效用估计器；推理时语义相关只用于高召回候选生成，**真正决定留哪些的是预测效用**，且不改 agent 策略、不需额外环境交互。ALFWorld 上 500-token 历史记忆预算下 **86.57 SR@50**，对比 BM25 检索 **65.67%**；反事实分析显示记忆效用**稀疏、强状态依赖、且语义相关抓不住**。

- **概念名（中英）**：决策效用记忆 / Decision-Utility Memory（MemCredit）
- **为什么"当下"最有价值**：这是 11-20B BRIDGE「**基准测的是检索到了什么，不是让 agent 做成了什么**」的**操作化答案**——BRIDGE 指出缺口，MemCredit 直接把「做成什么」做成可计算的边际贡献，并拿它**当记忆选择的判据**。它同时给 overview 的 [[LongTermMemory]]「按语义检索 + 溯源」补一个反例：最相关的记忆不等于最能改善行动的。与 11-22A PACE（协作的边际价值）、11-22B GrepMem（不选择）同属「**边际价值**」线，但第一次把边际价值**落到单条记忆的选择上**——与用户主线（记忆系统）接缝最紧。
- **来源链接（均 [verified]，一手 abs 已 WebFetch 直开核验）**：
  - https://arxiv.org/abs/2611.15600 [verified] —— 一手 abs（直开）：标题、七作者（Quanjiang Guo / Sijie Wang / Qianyang Zhu / Ben Zhang / Jinchuan Zhang / Ke Yan / Zhao Kang）、v1 2026-11-11、cs.AI、全部量化结论出自此页摘要
  - https://arxiv.org/pdf/2611.15600 [verified] —— 一手 PDF（abs 页 View PDF 链接）
  - https://arxiv.org/html/2611.15600v1 [verified] —— 一手 HTML 全文（abs 页 HTML 链接）
- **一句话定义 + 边界辨析**：定义——以「这条记忆对当前决策的边际贡献」而非「与当前状态多相关」为保留判据，用反事实干预训出效用估计器。边界：① vs [[LongTermMemory]]——那条按语义检索 + 溯源取可信事实；本条主张**语义相关只是候选生成器，效用才仲裁去留**。② vs 11-22B GrepMem——GrepMem 靠**正则查询**（agent 要自己知道搜什么）；MemCredit 靠**学出来的效用估计器**（不需 agent 构造查询），是「主动选择 vs 被动检索」之别。③ vs [[ContextEngineering]]——「按信号质量选组件」那条原则在这里被反驳：**信号质量（相关性）不是行动价值（效用）**。
- **⚠️ 证据边界**：预印本、单团队、自报；ALFWorld / WebShop 两个基准，效用估计器依赖离线反事实干预（成本与规模未明）；「效用稀疏且状态依赖」是作者实测结论，能否跨模型/跨任务迁移未证；一手 abs 未提代码开源。成篇前须开 PDF 核干预设计与 WebShop 分表。

### 11-23C 运行时上下文驱逐 / Runtime Context Eviction（Contexture） ⭐⭐⭐

**一句话**：一个 **harness 无关、模型无关**的运行时上下文驱逐架构——把 harness 的**完整对话历史**与模型的**执行上下文**分离，通过「把 token 溯源到产生它的工具操作」发现**后续操作会 supersede 早先输出及其轮次**，据此识别 **64%** 的最终历史 token 为可移除候选；再结合**全局共享 KV 压力与前缀驻留状态**决定何时移除值得牺牲已缓存计算。两模型 / 两 harness / 两基准上，SLO 内吞吐比「不驱逐 / harness compaction / AgentDiet / Continuum 之最优」提升 **20–73%**，八配置中五配置比 observation masking 高 **7–63%**，每完成会话 GPU 能耗最多降 **11%**；H100 上比单用 LMCache 高 **23%**。实机 agent 实验：平均准确率比「不驱逐」**+1.4 个百分点**（最差 -3.7），而 observation masking 掉 **3–28** 点。

- **概念名（中英）**：运行时上下文驱逐 / Runtime Context Eviction（Contexture）
- **为什么"当下"最有价值**：这是本库**上下文层的空白宿主**——`concept-relationship.md` 的上下文节点全在「模型这一轮看见什么」（token 预算 / 窗口 / 压缩 / 检索），**完全没有「承载它的服务系统」这一层**：KV cache 占 HBM、重复发送增长的历史拖垮吞吐。Contexture 把 [[AgentHarness]]「治理窗口（automatic compaction）」那一格从**模型侧**搬到**服务侧**，且证明驱逐的判据应是「**工具操作溯源 + 全局 KV 状态**」而非内容相关性。它给 `overview.md` 的 [[AgentHarness]]「harness 是循环宿主」补上**它脚下的机器**；与 [[Compaction]] 的分工是「**harness 管记什么、服务系统管缓存什么**」。最锋利的证据是 observation masking 掉 3–28 点而它 +1.4 点——**粗暴按内容抹除是错的，按操作溯源才对**。
- **来源链接（一手 abs 已 WebFetch 直开核验 [verified]；其余为搜索返回的可达页）**：
  - https://arxiv.org/abs/2611.26980 [verified] —— 一手 abs（直开）：标题、十作者（Colin Hong / Bryan Shan / Wei Siong Pang / Chengzhi Lu / Xu Guo / Nitin Shivaraman / Tao Luo / Esha Choukse / Kisson Lin / Dmitrii Ustiugov）、v1 2026-11-20、14 页 / 15 图、cs.DC+cs.AI+cs.MA+cs.OS、全部量化结论出自此页摘要
  - https://arxiv.org/pdf/2611.26980 [verified] —— 一手 PDF（abs 页 View PDF 链接）
  - https://arxiv.org/html/2611.26980v1 [verified] —— 一手 HTML 全文（abs 页 HTML 链接）
- **一句话定义 + 边界辨析**：定义——在服务系统层，按「工具操作的 supersession 关系 + 全局 KV 压力」决定驱逐哪些 token，把完整历史留给 harness、把精简上下文交给模型。边界：① vs [[Compaction]]——compaction 在 **harness 层有损压缩、改的是模型看到的文本**；本条在**服务层驱逐、不改 harness 历史也不改模型执行**，两者不同宿主层，可叠加。② vs [[AgentHarness]]——harness 是「谁跑循环」；本条是「**跑循环的这台机器怎么缓存**」，是它的下层而非并列项。③ vs 11-22B GrepMem——GrepMem 管**召回精度**（存得全、找得到）；本条管**服务成本**（KV/吞吐/能耗），一个在准确性轴、一个在资源轴。
- **⚠️ 证据边界**：预印本、单团队、厂商背景（作者含云基础设施研究者）；「64% 可移除」是该文 tracing 口径下的候选比例，不等于真的可以全删；+1.4pp 是**无负载对照**下的实机均值，最差掉 3.7 点，不能读成「驱逐无损」；吞吐/能耗数字为作者自测且依赖具体硬件（H100）与 harness；一手 abs 未提代码开源。成篇前须开 PDF 核 supersession 判定与实机设置。
