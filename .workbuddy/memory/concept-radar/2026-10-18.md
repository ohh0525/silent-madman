## 候选 1 ⭐ 记忆删除的实效 —— 「删得掉吗」从未被测量

### Whether Memory Deletion Actually Works (Bemula · MemCut)

### 为什么「当下」最有价值

1. **它把 wiki 里最贵的一句话打回了「未验证」。** `[[MemoryGovernance]]` 把记忆治理写成四个会各自失败的动作(Capture → Update → Recall → QA),并把 **DELETE** 放进可训练策略的动作空间(ADD · UPDATE · DELETE · NOOP);它的四条底线之一是 **可回滚(rollbackable)**。可是**从来没有人测过「删」这个动作到底生不生效**——直到本周两份互为独立的基准在同一周出现。
2. **它昨天刚第二天替换了这个问题的边界。** 昨天(10-17)的结论是:连续载体没有地址,所以删不干净。今天补上更难受的一半:**就算每一个地址都在、每一条都能被逐条列举,也删不干净。** ⇒ 昨天可以说「那是载体的问题」;今天这条退路被封住了。
3. **它一次性给 `overview.md` 的一句推论配齐了两台仪器。** overview 在 2026-10-09 写下:「**『没忘掉』是扣分(FAMA)——『删了还在用的东西』也是扣分**」。Bemula 与 MemCut 恰好分别盯住这两侧:前者测「目标还在不在」,后者测「幸存碎片能不能被拼回来」。
4. **它的数字是灾难级的,而且是负结果。** 负结果天然不被广泛传播,所以很容易错过 —— 但正是 wiki 最需要收藏的那种证据。
5. **它与你最近的关注直接相邻。** 最近一份入库材料是 `memory-lifecycle.html`(记忆四动作 + 决定者);本行是那四个动作里**唯一既没有人写清楚规则、也没有人测量过实效的一环**。

## 候选 2 ⭐ 记忆形成的中毒界面 —— 内容干净也拦不住的那条管路

### Memory Formation Poisoning Interfaces (MemForm)

### 为什么「当下」最有价值

1. **它推翻了一道 wiki 从没明写、却一直在用的前提。** `[[Provenance]]` / `[[CitationLock]]` / `[[Abstention]]` 三条形影不离的纪律,全都在检查**内容**:来源对不对、是不是真的打开过、符不符合引用资格。MemForm 证明:可以**每一条记忆都真实、合法、来源正确、检索无误**,下游行为依然被扭曲——因为攻击落在**形成流程**里,不在内容里。
2. **它给出了一种「没有任何带毒产物可供检测」的攻击。** 保留下来的记忆集合**完全相同**,仅仅改变**整合顺序**,行为就变了。⇒ 你扫内容、扫来源、扫签名,全都干净。
3. **`[[MemoryPoisoning]]` 页现有的两条机制其实是同一个大类。** PMPA 的诱导自写、Darktrace 的伪造会话历史 —— 两条都是**内容攻击**。这一行证明「内容干净」不再是充分条件,并给出了一套新的切分维度(五个界面,而非两种攻击方式)。
4. **它把这句箴言推到了一个更硬的结论:** 本库 09-24 起的老教义是「**模型不是唯一可以放控制的地方**」;10-17 新增的是「**顺序是一等设计对象**」。本行把它们合到一起:**控制既不在模型里,也不在内容里 —— 它还在「你按什么顺序把东西定稿」这个顺序本身里。**

### 一句话定义

> **记忆投毒不该按「攻击方式」分类,而应按「持久记忆被生产与被定稿的界面」分类:内容(Content)、证据(Evidence)、作用域(Scope)、留存(Selection)、管路/顺序(Path)。其中留存与顺序两类可以做到「保留集合完全相同,行为完全不同」——没有任何一件带毒产物可供检测。**

### 与已覆盖概念的边界辨析

| 对比 | 差别 |
|---|---|
| vs **[[MemoryPoisoning]] 现有的两条机制** | PMPA / Darktrace 都是**内容攻击**(恶意载荷或伪造内容进了记忆)。MemForm 的 Scope / Selection / Path 三类**不依赖任何恶意内容** ⇒ 是同一页的**第三种形态**,不是重复 |
| vs **[[Provenance]] / [[CitationLock]] / [[Abstention]]** | 不是竞争关系,是**前提失灵**——三者审查的对象全都合法且来源正确,它们会给出「通过了」的结论。**它们不是被绕过,是它们的问题就问错了地方。** |
| vs **10-16A ToFu「顺序是框架实现的属性」** | 同形(顺序决定结果),但位置不同:ToFu 在**编排架**里(模型输出 ≠ 执行动作);本行在**记忆整合管道**里(同样的事实,不同的定稿顺序) |
| vs **10-17B FEB-30「supersede 仅 20% 判对」** | FEB-30 说系统**搞不定** supersede;本行说即使 supersede 做对了,**顺序**仍能改变结果 —— 相邻但不同层 |
| vs **候选 1(删除的实效)** | 候选 1 是「合法地想删却删不掉」(**留 de 一侧**);本行是「留下来的每一条都合法但顺序有毒」(**留的一侧**)。**两者合起来才是「留存不全 Guardianship 的全貌」,建议并列记录、勿写成雷同的一页** |

## 候选 3 上下文工程技法的条件性 —— 同一招只对一半 agent 有效(不标 ⭐)

### Conditional Effectiveness of Context-Engineering Techniques (arXiv:2610.20959)

> ⚠️ **为什么它不标 ⭐ 却是三条里唯一「直接结清 `overview.md` 一条开放问题」的**:`overview.md` 自 2026-09-09 起挂着一条——「上下文工程技法如何被**端到端**度量(超出单一厂商口径),需要一份独立评测」。今天这份工作就是那份评测。**它消掉的是一条挂了 39 天的开放问题,这一点比它自己的证据强度更值得注意。**

### 为什么「当下」最有价值

1. **它把 wiki 里一大类结论从「好东西」降回「对症的药」。** `[[ContextEngineering]]` 页把三种主要技法(semantic layer / orchestration / compaction)当作**改进**。今天的数据说它们是**修理补丁**:只对刚好患那种病的行为组有效。
2. **它的反结果正是 wiki 一直在收集的那种。** 对最强的那一组(investigators),三种技法**全部有害** —— semantic layer 使他们不再去查、orchestration 使其过度自信(**−5 个百分点**)、compaction 使其重复步骤。**你给最好的员工配工具,反而让他变差了。**
3. **它是 [[MultiAgent]] 那条老规则的第二次命中。** 09-26 起 wiki 有一条可移植规则:「**先找到便宜的正确性判据,再组队**」—— 「条件性」早在那里就被一次性验证过了。今天把它从多智能体**扩到上下文工程**本身。
4. **它给这个库一个便宜而实用的操作建议。** 与其先假设「我们应该上 RAG / Semantic Layer / Orchestration」,不如**先跑一轮无技法的基线,看 agent 落在哪个行为组**,再决定贴哪种补丁。
