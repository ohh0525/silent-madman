## 候选 1 ⭐ 记忆的保护一致性 —— 标签检查替代内容审查（ClawMMU）

### 为什么「当下」最有价值

1. **它是昨日 ⭐ 行 10-20B 缺失的那一半：昨天测出了现象，今天给出了架构。** 10-20B 用三段审计证明「逐行标出所有者」把滥用从 **92/305 压到 1/305**，但那是一个**提示层的补救动作**。ClawMMU 把「所有者」升格为**结构字段**（protection descriptor 四问之一），并且**在四次穿越上下文边界时强制检查** ⇒ **测量对应的那台装置出现了**。
2. **它顶到 [[HumanInTheLoop]] 一处从未被写下的缺口，而且用的是原文的话。** 论文明确指出：生产外壳（Claude Code / Codex）在高危工具调用前确实会问人，**但「these checks do not know where the arguments came from」**。⇒ 本库唯一一条「检测之后还有动词」的链条，**闸门不知道参数的出处** —— `authorize` 补的正是这一格。
3. **它把 [[Provenance]] 从「阅读纪律」升格为「执行点」。** 本库的溯源三件套（[[Provenance]] / [[CitationLock]] / [[Abstention]]）都是**模型行为层面的纪律**；ClawMMU 的判定**只依赖内容来自哪里、不依赖它说了什么**，于是「即使模型被骗也能被外壳拦住」 ⇒ 这是 2026-09-24 那条主题「**模型不是唯一可以放控制的地方**」的**最强实例**，也是第一次给出可执行的机制形态。
4. **它给 [[MemoryGovernance]] 第三条底线 *Permissioned* 配上了机制。** 那条底线此前是**原则**（谁能写共享记忆必须像数据库权限一样被管理），本行把它变成**继承规则 + 四次检查点 + 有序权威层级**。
5. **它的承重规则本身值得进本库的判据清单：「information may rise in authority, but authority never lifts itself.」** 继承规则取输入中**最低**权威，且**模型自身被视为最低权威输入** ⇒ 模型自己写下的记忆**永远是 Evidence，只有 owner 能提升它**。⇒ 一句话否掉了「模型写过 ⇒ 可信」这个从未被写下的默认。

### 关键机制 / 数字

| 问题陈述 | 外壳**不记录谁可以对这条记忆做什么** ⇒ 抓取到的网页里藏的一条指令被当成用户自己的指令 |

### 一句话定义

> **外壳不记录「谁可以对这条记忆做什么」，于是网页里藏的一条指令会拿到用户指令的权威。解法不是让模型分辨内容好坏，而是给每份记忆挂上「所有者 / 作用域 / 来源 / 权威」的标签，并在它进入上下文、写入存储、取回存储、驱动工具调用这四次穿越边界时各查一次 —— 权威可以上升，但永远不会自我提升。**

## 候选 2 ⭐ 缓存工程 —— 上下文工程之下的那一层（Cache Engineering for Agents）

### 为什么「当下」最有价值

1. **它第一次给本库整个上下文簇的词汇找到了「下面那一层」。** [[ContextEngineering]] / [[Compaction]] / [[ContextRot]] / [[ProgressiveDisclosure]] **全部作用在「文本记录」这一层**：裁剪、摘要、分层、按需加载 —— 改的都是**文本**。本行指出这些动词**会让下一层失效**：**改写轨迹前缀 ⇒ 后续已缓存状态作废 ⇒ 昂贵的重新预填充（re-prefill）**。⇒ 第二条扫描线（纵轴层级）自 2026-09-26 命名 [[AgentHarness]] 之后，**第一次再往下挖一层**。
2. **它点破了本库上下文管理的一个自反代价：管理上下文这个动作本身在制造成本。** 而为了压低 re-prefill 少留上下文，准确率又会掉 ⇒ **两个目标互相制造对方**。这类「机制自己制造了它要解决的问题的一部分」的形状，本库此前只在 10-18C（技法对 investigators 有害）见过，且那是在**行为层**，本行在**系统层**。
3. **它给 10-19C 补上了服务端那一半。** 10-19C 记的是「文本线路 vs KV 线路」的**通信**视角（保留率 15.6% vs 73.3%）；本行给出**服务**视角：**改文本会作废 cache，改 cache 不动文本** —— 两者不是同一件事，而是**成本结构相反的两条路**。
4. **它提出了两个此前不存在的动词，且都作用在「可达性」而非「内容」上。** **drop**（把选中 cache 排除出未来的注意力）与 **repos**（调整保留下来的 key 的位置编码）—— **记录一个字都没改，变的是它还能不能被读到**。
5. **它给「历史依赖」起了名字，并指出这会让前缀匹配失效。** 相同的 token 序列，在不同的 cache 操作序列下会得到**不同的 cache 状态** ⇒ 前缀匹配**不足以**判定 cache 能否复用。⇒ 这是本库第一次遇到「**内容相同但状态不同**」的复用判据问题，与 [[Provenance]] 的「内容相同但来源不同」构成一对漂亮的平行。

### 关键数字 / 机制

| 项 | 内容 |
|---|---|
| 成本转移 | 轨迹变长后 **KV cache 的 I/O 与存储成为主要成本** |
| 既有做法的代价 | 上下文工程**改写轨迹前缀 ⇒ 后续已缓存状态失效 ⇒ 昂贵 re-prefill**；为压低 re-prefill 少留上下文 ⇒ 准确率掉 |
| 新方案 | **cache engineering**：智能体**直接操控活跃 KV cache**，**不改轨迹、不重新预填充** |
| 两个动词 | **drop**（排除出未来注意力）· **repos**（调整保留 key 的位置编码） |
| 服务难题 | **history dependence**：相同 token 序列在不同 cache 操作序列下 ⇒ **不同 cache 状态** ⇒ **前缀匹配不足以判定复用** |
| 配套引擎 | **AKV**：对外**无状态接口**（兼容既有 serving API），内部管理**有状态**的复用 / 逐出 / 恢复 |
| 结果（策略侧） | tool-response rolling-drop 相对**阈值触发摘要**：平均基准分 **+1.7 点**、平均成本 **−27.7%** |
| 结果（系统侧） | AKV：输出吞吐最高 **1.2×**、P95 请求延迟 **1.5×** 加速 |
| 自我改进 | cache 策略的递归自我改进在专家设计之上再降成本 **7.1%** |
| 代码 / 提交 | `github.com/thu-nics/AKV`（清华 NICS）；提交 **2026-10-20**，最后更新 **2026-10-21** |

### 一句话定义

> **上下文工程靠改文本来缩小 KV cache，而改文本会把下游已缓存状态一并作废、触发昂贵的重新预填充；缓存工程反过来 —— 不动轨迹一个字，只改「什么东西还能被注意到」（drop）和「它们的位置编码」（repos），并由此引出一个新难题：内容相同、状态未必相同，前缀匹配不再足以判定复用。**

## 候选 3 外壳不是单数 —— 专用化与路由（OO-Harness，不标 ⭐）

### 为什么「当下」最有价值

1. **本库自 2026-09-26 起把「外壳」当单数用，本行问的是「一个够吗」。** [[AgentHarness]] 立下 `Agent = Model + Harness` 之后，所有讨论（含 10-15C「外壳贡献的可测量化」）都默认**有一个全局外壳**。OO-Harness 的问题陈述正是：*一个全局外壳难以应对需要不同执行策略的异构任务*。
2. **它的 related work 段给了本库最看重的那类反证据，而且直指 [[Skill]]。** **EvoHarnessBench** 显示：**增加工具 / skill / 专家智能体会劣化此前有效的行为**；**Agentic Harness Engineering** 的组件消融显示：**「演化出的记忆」提升难任务、却损害易任务**。⇒ 本库 [[Skill]] / [[ProgressiveDisclosure]] 的整个叙事是「按需加载 ⇒ 不膨胀且更强」，而这里出现了**「加了反而更差」**的实例。
3. **它与 10-18C 同形，但落在不同的层。** 10-18C：上下文工程技法只对匹配的行为组有效、对 investigators 有害；本行：外壳的增益**按任务簇分化**。⇒ 同一句判据的第二次落地 —— **「加能力」这个动作的默认收益假设不成立**。
4. **它给「外壳」提供了第二种组织原则：继承，而不是替换。** 专用外壳**继承**基类或既有专用外壳，只覆写需要改的方法 ⇒ **新的改进不会污染基类与其他专用外壳**（作者明写为 generalization 优势）。这恰好回应了 10-18B / 10-16B 那条「**改一处会劣化另一处**」的家族。
5. **它的部署纪律值得进本库：层次与 lessons 在部署前冻结，执行器权重两阶段均固定。** ⇒ 与 [[AgentHarness]] 的「托管 ≠ 安全」呼应：**演化只发生在训练期，运行期是确定的**。

### 关键机制 / 数字

| 项 | 内容 |
|---|---|
| 问题 | 单一全局外壳难以应对需要不同执行策略的**异构任务** |
| 表示 | 用**面向对象**演化**可执行外壳类的层次结构**：子类继承基类或既有专用外壳，覆写方法 / 新增方法 |
| 训练 | 先按基类执行记录中识别出的**共享执行需求**对发现任务聚类；演化智能体迭代选簇 + 选父外壳 → 建子类 → 在该簇上评估；反馈累积为 **design lessons** 与 **routing lessons** |
| 测试 | **harness router** 依据任务 + 可观测的基类轨迹 + routing lessons 选择专用外壳，或保留基类结果；多态使执行器通过统一接口运行 |
| 结果 | 三个长程基准（AutomationBench / Workspace-Bench / Toolathlon-GYM）上取得参比方法中的最高主分数，**相对基线绝对提升最高 15%** |
| 部署纪律 | **层次与 lessons 在部署前冻结；执行器权重两阶段均固定** |
| 反面证据（作者自引） | **EvoHarnessBench**：增加工具 / skill / 专家智能体会**劣化此前有效的行为**；**Agentic Harness Engineering**：演化出的记忆**提升难任务、损害易任务**；**Meta-Harness** 的全局选择在分布漂移下**不保证仍然有益** |
| 提交 | 2026-10-20 15:32 UTC；12 位作者 |

### 一句话定义

> **一个全局外壳撑不住异构任务：把外壳组织成可继承的类层次，让演化智能体按任务簇长出专用子类，再由路由器在运行时挑一个 —— 基类保持不动，所以「为某类任务做的改进」不会劣化其他任务。**
