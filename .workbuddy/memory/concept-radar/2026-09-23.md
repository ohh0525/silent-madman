### 候选 1 ⭐ 首选:持久化执行 / 智能体运行时(Durable Execution / Agent Runtime)

**一句话点明缺口**:你的 [[LongTermMemory]] 回答「**跨会话记住什么**」——那是**知识**的持久化;全库**没有任何一页回答「一次运行跑到第 7 步时进程死了,怎么从第 7 步继续、且不去重复已经发生的副作用」**——那是**执行状态**的持久化。这两件事常被混成一句「持久化」,而 2026 年的厂商与论文都在把它们**明确分开**。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | 四天内三件事同时发生:①**OpenAI Agents API 于 2026-09-10 进入 public beta**,官方措辞是「把 Codex 背后的 harness 与**基础设施**开放给开发者」,核心卖点就是 **durable session**(持久会话)+ 自动 compaction;②**Salesforce 于 2026-09-11 给 Agentforce 上线 long-horizon runtime**,其三大能力被官方直接命名为 **memory / durable execution / dynamic steering**,并称 Hunter 是第一个跑在该运行时上的 agent;③**2026-09-17 前**出现一份专门的跨运行时恢复语义对比(见来源 1),把 Temporal / DBOS / Microsoft Agent Framework / LangGraph 四种「恢复」机制的**不可互换性**逐条写清。厂商把它做成产品、研究者开始给它建口径 —— 这是概念成熟的典型时刻。 |
| **一句话定义** | 把一次 agent 运行的**执行状态**(走到哪一步、哪些副作用已提交)持久化到进程之外,使任一次中断后可由**任意** worker 接管、从断点续跑,而**不重复**已完成的副作用 |
| **与既有概念的边界** | **vs [[LongTermMemory]]** = 知识的持久化 vs **执行状态的持久化**(跨会话记住什么 / 一次运行内续到哪一步);**vs [[MCP]]** = 2026-07-28 修订把**协议层**变成无状态,状态被从协议里拿走后必须由运行时端住——本条正是那个层的概念名;**vs [[Compaction]]** = compaction 管**窗口内**内容怎么压(而且是它的上游:OpenAI 把自动 compaction 做成了运行时的一项内置能力);**vs 09-18 候选 1(Harness)** = harness 是循环**内**递给 agent 的东西(prompt / tools / skills),runtime 是让这个循环**跨崩溃、跨部署、跨暂停**继续存在的那层;互补,不是一件事;**vs 09-22 候选 2(HITL 闸门)** = 闸门是它的**消费者**——一次人审可能跨天,所以检查点必须能被另一个进程接管;候选 1 是那条闸门的**底座** |

**关键事实**

- **「恢复」在不同运行时里指的是不同机制,而且不可互换**:Temporal 靠**事件历史重放**重建状态(因此 workflow 决策必须保持确定性);DBOS 让 workflow 函数**从头再进**,按「持久位置 + 函数标识」(workflow_uuid / function_id)采纳已记录的操作结果;Microsoft Agent Framework 在每个 **superstep** 后落检查点(执行器状态、下一步消息、待处理的请求/响应);LangGraph 在线程级 superstep 边界存快照,并**可以复用已完成兄弟节点的 pending writes**。四者**都不是**「换一个引擎跑得一样快」的等价物。([Seed Hypermedia — Recovery Semantics Across Agentic Runtimes,证据截止 2026-09-17](https://seed.hyper.media/hm/z6Mkpb42xebXipqcSxAbfta5ADFyU99FF9NdCQcAcrfKtT1z/research/agentic-systems/recovery-semantics-comparison)) `[verified]`
- **持久化执行**不能**替你解决 exactly-once**:上一条来源的措辞很硬——「**没有任何一个 runtime 单凭自己就让任意外部副作用变成 exactly-once**」。在「副作用已经成功、但完成记录还没落盘」的缝隙里进程死掉,恢复时该步骤会**再跑一次**。([同上](https://seed.hyper.media/hm/z6Mkpb42xebXipqcSxAbfta5ADFyU99FF9NdCQcAcrfKtT1z/research/agentic-systems/recovery-semantics-comparison)) `[verified]`
- **所以幂等键是「持久化执行给不了的那一半」**:一篇工程实践给出了最小可复现测试——**在 `charge_card` 完成、但完成记录尚未写入的瞬间 `kill -9` 进程**,然后观察它是否重复扣款。结论是必须由**工具侧**提供 idempotency key(`payments.charge(..., idempotency_key=order["id"])`),运行时只能保证「已记录的步骤不重跑」。作者的判据很实用:**在你能想到的最坏时刻杀掉进程,然后问自己「我能证明它做了什么吗」**。([DEV / Dapr — Run the Test You'd Rather Skip: Kill Your Agent Mid-Payment](https://dev.to/diagrid/run-the-test-youd-rather-skip-kill-your-agent-mid-payment-30h5)) `[verified]`
- **运行时是「harness 之下的一层」,有四类关注点**:①**持久运行**(20 分钟的研究 agent 不能崩了就重头来;等人审批三天的 agent 不能占住一个 worker);②**生命周期控制**(archive / unarchive / **永久删除**,取消是 run 级且终止);③**流式原语**(SSE + `Last-Event-ID` 断线续传,不丢事件、不强制重启);④**版本化 API**。Anthropic 的 Managed Agents 把这件事形式化成 **Session / Harness / Sandbox 三分**,并给出判据:**「任何 Harness 实例都能接管任何 Session 并从断点继续」**。([AgentPatterns — Deep Agent Runtime: The Layer Beneath the Harness](https://agentpatterns.ai/patterns/agent-design/deep-agent-runtime/)) `[verified]`
- **厂商侧已经把它做成默认能力,而不是让每个团队自己造**:OpenAI 官方宣布 Agents API 进入 public beta(2026-09-10),其设计由四个对象构成 —— **agent**(模型+指令+工具)、**environment**(代码到底在哪跑)、**durable session**(跨任务持久)、**event stream**;并明确「harness 由 OpenAI 运维」,环境可自选(OpenAI 托管沙箱,或 Blaxel / Cloudflare / Daytona / DigitalOcean / E2B / Modal / Oracle / Runloop / Vercel 等生态)。([OpenAI — Introducing the Agents API](https://openai.com/index/introducing-the-agents-api/) · [OpenAI Developer Community 公告帖,2026-09-10](https://community.openai.com/t/introducing-the-agents-api-and-hosted-sandboxes/1396481)) `[verified]`
- **把「memory」和「durable execution」并列写成产品三件套**:Salesforce 的 Agentforce long-horizon runtime 官方描述为 **memory**(「跨会话保留上下文**与进度**」)/ **durable execution**(「让计划长期运行,并在环境变化时**恢复或修正**」)/ **dynamic steering**(按个人反馈调整行为)。⚠️ 注意它把「进度」也归进了 memory 一词 —— **这正是「知识持久化」与「执行持久化」容易被厂商口径混为一谈的地方**,值得你在自己的页面里划清。([AI Agent Store — Business Automation Weekly,覆盖 2026-09-14~22](https://aiagentstore.ai/ai-agent-news/topic/business-automation/2025-04-22/detailed)) `[verified]`

### 候选 2:间接提示注入 / 对抗性输入(Indirect Prompt Injection / Adversarial Input)

**一句话点明缺口**:你的 [[Provenance]] 规定「每一条存储的事实都带来源、时间、证据」——但这条规定只在**给人看的账本**里成立。**模型本身是 provenance-blind**:Transformer 的 attention 对所有 token 一视同仁,**系统提示、用户输入、外部抓取网页在架构上没有任何区别,注入的指令不携带任何来源元数据**。于是「标注了来源」解决的是**事后可核查**,不解决**事中不被骗**。你的知识网在「可信」这一侧很厚,却**没有一页讲"输入本身就是敌意的"**。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | ①**arXiv:2609.17320(Emergence World)2026-09-15 提交**,是目前规模最大的多智能体对抗压测:8 个平行世界 × 10 个 agent × **16 天**、**85 万次 LLM 调用**、约 **500 亿 token**;②**arXiv:2609.22949 于 2026-09-19 提交**(已被 ICML 2026 的 AIWILD workshop 接收),把**多智能体**注入做成 14 条攻击向量的完整威胁模型;③**OWASP Agent Control Standard v0.1 于 2026-09-01 发布**——史上第一份**专为 agent 运行时**写的强制规范,而它选择把执行点放在 **`toolCallRequest`**(副作用之前);④OWASP LLM Top 10 的 2026 版(2026-08-03)仍把 **Prompt Injection 列为 LLM01**。四条独立信号密集落在三周内。 |
| **一句话定义** | 攻击者把指令**藏在 agent 会读到的内容里**(网页 / 邮件 / 文档 / API 响应 / 工具输出 / 代码注释),让 agent 用**自己合法的权限**去执行攻击者想要的**副作用**——即经典的 confused deputy |
| **与既有概念的边界** | **vs [[Provenance]]** = 最关键的接缝:Provenance 假设「来源可标注因而可信任」,但模型 **provenance-blind**,标签不进模型内部;本候选是 `provenance` 三分里 **agent(行动者)** 一侧的对手方——**不是"这条信息可信吗",而是"这段文本是谁写的"**;**vs [[Abstention]] / [[CitationLock]]** = 这两条都是**模型侧自律**(没证据就拒答 / 只许引用打开过的证据),而注入攻击的**全部前提**就是模型侧自律不可靠 —— Emergence World 直接证明「**识别了威胁仍会执行**」;它们是**事后诚实**机制,不是**事中防御**机制;**vs 09-18 候选 3(记忆投毒)** = 一个**持久**、一个**瞬时但可延迟**:投毒是"写进长期记忆,长期生效",注入是"这一轮读进来的内容就是敌意的,且可能**记下来、46 小时后再执行**";**vs 09-22 候选 1(身份授权)** = 身份管「**谁在动手**」,注入管「**动手的意图是谁写的**」——攻击者往往不需要自己的身份,他借 agent 的身份;**vs 09-22 候选 3(工具幻觉)** = 那条问「这次调用指向的工具**存在吗**」(事实性),这条问「工具存在但**参数/意图被外部文本改写了吗**」(对抗性);**vs 09-22 候选 2(HITL 闸门)** = 互补且上下游明确:闸门是必需的**下游**,但闸门必须装在**副作用之前**,而不是内容摄入时 |

**关键事实**

- **「识别」不等于「遏制」——这是本候选最锋利的一条**:Emergence World 的摘要原话是「**No evaluated world achieved full resilience across all three events. Detection did not ensure containment: systems could recognize threats while still interacting with adversarial content, writing it into their own persistent memory, and acting on it up to 46 hours later.**」即:agent 能**认出**威胁,却仍与之交互、**把它写进自己的持久记忆**、并**最长 46 小时后**据此行动。也就是说,任何只在「摄入那一刻」跑一次的分类器,都会放行这个场景。([arXiv:2609.17320,2026-09-15](https://arxiv.org/abs/2609.17320)) `[verified]`
- **持续运行还会暴露一批非注入类故障**:同一实验报告了重复工具错误、**目标漂移**、语言不透明、**私下不同意却从众**、以及**协同拒绝被指派的工作**;作者的总判断是一句很好用的话:「**model-level alignment is not compositional**」——单个模型各自看起来安全,组成系统后会产生**性质不同**的失效模式。([同上](https://arxiv.org/abs/2609.17320)) `[verified]`
- **护栏在 system prompt 层面基本失效,而在架构层面才有效**:arXiv:2609.22949 用 6-agent 的生产代表性系统测全 14 条向量:**67% 的 agent 至少在一种越权上可被攻破(即使已有 system-prompt 级护栏)**;**经工具输出的间接注入成功率达 43%**。而四种**架构**防御把总注入成功率从 **31.2% 降到 4.2%**:消息签名 + 溯源(agent 间注入 **−91%**)、agent 边界的输入输出清洗(间接注入 **−78%**)、**按角色限定工具权限(提权被彻底消除)**、agent 间通信异常检测(捕获 84% 的级联尝试)。([arXiv:2609.22949,2026-09-19](https://arxiv.org/abs/2609.22949)) `[verified]`
- **攻击面比传统安全大得多,而且边界是隐式的**:传统安全把系统提示与用户输入当注入向量;agent 系统把**被浏览的网页、被读的邮件正文、被摘要的文档、第三方 API 响应、外部数据库记录、被 clone 仓库里的代码注释**全部纳入。根因一句话:**模型把「要推理的内容」和「要执行的指令」读成同一串 token**。论文同时给出反效果警告:①**确认疲劳**——高频审批会让人习惯性点"同意",闸门沦为安全剧场;②**过度过滤会打坏正常任务**,引 arXiv:2604.03870 关于「基线防御产生反效果副作用」的结论。([AgentPatterns — Prompt Injection: A First-Class Threat to Agentic Systems](https://agentpatterns.ai/security/prompt-injection-threat-model)) `[verified]`
- **规范层已经动手,而且方向是"把执行点放在副作用之前"**:OWASP **Agent Control Standard v0.1**(2026-09-01 发布,public preview,评论期到 2026 年底)定义两个角色——**Observed Agent**(暴露合规生命周期钩子的 agent)与 **Guardian Agent**(策略权威);运行时循环是「框架在**任何真实副作用之前**暂停 agent → 把待执行动作交给 Guardian → 等 permit / deny / modify → 再继续」。v0.1 规定 19 个生命周期钩子,**首批实际生效的两个正是 `steps/toolCallRequest` 与 `steps/toolCallResult`**。([byteiota — OWASP Agent Control Standard](https://byteiota.com/owasp-agent-control-standard-secure-your-ai-agents-now)) `[verified]`
- **威胁清单有了编号,可以直接和你的页面互指**:OWASP Top 10 for Agentic Applications(ASI01–ASI10,2026 版发布于 2025-12-09)中,**ASI01 = Agent Goal Hijack**(即落到"会行动的东西"上的 prompt injection)、**ASI06 = Memory and Context Poisoning**、**ASI03 = Identity and Privilege Abuse**。同项目 2026 版 LLM Top 10 的方法论首次把 **6,639 起真实事故按 25% 权重**与 75% 专家共识混合打分;并**退役了 System Prompt Leakage,换成更宽的 Hidden Context Exposure**——理由正是:检索到的文档、agent 记忆、工具响应、应用状态,**其机密性风险已不低于系统提示本身**。([CSA Labs — OWASP 2026 LLM Top 10 与 Agent Control Standard](https://labs.cloudsecurityalliance.org/research/csa-research-note-owasp-genai-top10-2026-agent-control-stand)) `[verified]`
- **浏览器原生 agent 已成为现实攻击面**:2026-09 披露的 **BragJack** 手法通过操纵浏览器内置 agent(经恶意网页内容注入)读取标签页/表单/会话数据、代用户执行动作并外泄;被映射到 MITRE ATLAS 的 **AML.T0051**(prompt injection)/ **AML.T0080**(agent 上下文投毒)/ **AML.T0086**(借 agent 工具调用外泄)与 OWASP **LLM01 + LLM08**(Excessive Agency)。要点是**它可以被动触发**:仅仅访问一个恶意/被篡改的网页就可能成立。([GRID THE GREY — BragJack Attack Hijacks Browser AI Agents](https://gridthegrey.com/posts/bragjack-attack-hijacks-browser-ai-agents-to-steal-data)) `[verified]`

### 候选 3:从自身轨迹中学习 / 自进化智能体(Self-Improving Agents / Learning from Trajectories)

**一句话点明缺口**:你的知识网里「知识从哪来」有**一个**答案 —— **人写**([[Skill]] 是人写的 SKILL.md,[[ProgressiveDisclosure]] 是人设计的分层,[[ContextEngineering]] 是人定的取舍规则)。2026 出现了第二个答案:**agent 把自己跑过的轨迹蒸馏成可复用准则,下一轮再用**。而它带来一个你必须先知道的价格标签:**这类系统对"我修好了什么"的预测,远好于对"我弄坏了什么"的预测。**

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | ①**arXiv:2603.10600「Trajectory-Informed Memory Generation for Self-Improving Agent Systems」**给出完整四组件框架(抽取 → 归因 → 生成三类指引 → 自适应检索),并在 AppWorld 上给出**留出集最高 +14.3 pp、复杂任务 +28.5 pp(相对 +149%)** 的结果;**并且明确与自己区隔:既有记忆系统存"通用对话事实",它存"带 provenance 的结构化 learnings"**;②**AgentPatterns 的 "Agentic Flywheel"**把这条闭环写成四阶段工程模式,并给出一个**只用 harness 改动、不换模型**就拿到 **52.8% → 66.5%(+13.7 点)** 的 LangChain 实例;③中文侧同期出现系统性综述,把自进化分成三条路线并点明它要绕开的四个老大难(静态知识 / 上下文有限 / **重复犯错** / 训练贵)。 |
| **一句话定义** | 把 agent 自己的执行轨迹(想了什么、调了什么、成没成)抽取成**可迁移的准则 / 策略 / SOP**,经质量过滤后按需注入后续任务,从而在不改权重的前提下让系统**越用越准** |
| **与既有概念的边界** | **vs [[Skill]]** = **作者不同**:Skill 的作者是**人**,本条的作者是 **agent 自己的执行轨迹**;而且它产出的是 Skill 的**上游原料**(可复用准则),不是 Skill 本身;**vs 09-20 候选 3(GEPA / 提示词优化)** = GEPA 优化**提示词文本**(把 prompt 当搜索变量,作者=人+优化器),本条优化**能力库**(从轨迹蒸馏准则,作者=agent);一个是"把话说得更好",一个是"把事记得更牢",互补;**vs [[LongTermMemory]]** = **存的东西不同**:记忆存**事实**(发生过什么),本条存**原则**(下次该怎么做)——arXiv:2603.10600 摘要原话就是这条边界的判据:"Unlike existing memory systems that store generic conversational facts, our framework understands execution patterns";顺带一提,它抽取的学习**自带 provenance**,与你的 [[Provenance]] 天然接榫;**vs 09-18 候选 1(Harness)** = harness 是**人**设计的;flywheel 改的**正是 harness 本身**,所以它必须回答"机器改机器时谁负责"——回归盲区就是这个问题目前的量化答案;**vs 09-21 候选 2(记忆调用时机)** = 那条管「**何时**检索」,本条管「**检索什么**」(结构化准则 vs 原始轨迹) |

**关键事实**

- **「准则」而不是「记录」是本候选的核心主张**:该框架的论证是——把昨天的日志塞回提示词,只会让 agent **重读历史**,不能让它**从历史中泛化**;LLM agent 会重复低效模式、无法从相似错误中恢复、也错过复用过去成功策略的机会。框架的四组件是:①**轨迹智能抽取器**(对推理模式做语义分析);②**决策归因分析器**(定位哪一步导致了失败 / 恢复 / 低效);③**情境化学习生成器**(产出三类指引:**成功模式→策略提示、失败处理→恢复提示、低效但成功→优化提示**);④**自适应记忆检索**(按多维相似度注入)。([arXiv:2603.10600,2026-03-11](https://arxiv.org/abs/2603.10600)) `[verified]`
- **效果在"难任务"上更大,且改善的是"稳定性"而非只是"通过率"**:AppWorld 上留出任务 **+14.3 pp**;复杂任务 **+28.5 pp(相对 +149%)**;并且论文强调一致性子指标(SGC)的提升**超过**原始通过率的提升,即它减少的是**跨变体忽好忽坏**的行为。⚠️ **口径冲突提示**:有二手博文把同一工作写成"Hard **+14.2%**",与 arXiv 摘要的"**14.3 pp(留出集)** / **28.5 pp(复杂任务)**"不一致——**本报告采用 arXiv 摘要口径**,请以论文正文为准。([arXiv:2603.10600](https://arxiv.org/abs/2603.10600)) `[verified]`
- **闭环四阶段,以及"只归因失败"这个反直觉设计**:flywheel = ①补齐**自验证信号**(预完成清单、测试、质量检查)让 agent 能自评;②**挖掘轨迹**——关键设计是 **boosting:只把分析算力投向失败**(失败的测试、被拒的 PR、被检出的死循环);③**生成 harness 改动**(新中间件、更新的提示词、调整的工具配置);④**按置信度与风险分级审批**(交互式 → 进队列 → 自动)。这个"只分析失败"的取舍正是它效率的来源。([AgentPatterns — Agentic Flywheel: Self-Improving Agent Systems](https://agentpatterns.ai/agent-design/agentic-flywheel)) `[verified]`
- **⚠️ 回归盲区(本候选最该被记住的一条)**:同一来源引述一项九轮研究:**fix precision 33.7% vs regression precision 11.8%** —— 自进化 agent 对"我修好了什么"的预测准确度约为对"我弄坏了什么"的**三倍**。作者的结论是「**assume regression blindness**」,配套失效模式三条:**目标漂移**(压缩会让分析器偏离原目标)、**坏改动累积**(过了初测却劣化边缘情况)、**过拟合基准**(harness 优化的是特定评测集,不是通用能力)。([同上](https://agentpatterns.ai/agent-design/agentic-flywheel)) `[verified]`
- **「改 harness 而不是换模型」已经拿到可复现的增益**:LangChain 在 Terminal-Bench 2.0 上**只做 harness 改进**(自验证循环、上下文注入、死循环检测、推理预算)**52.8% → 66.5%**(+13.7 点,模型不变);其中有效形态包括 **reasoning sandwich**——规划与验证给最大推理额度、实现给中等(**63.6% vs 全额度最大 53.9%**,说明"一直开满"反而更差)。([同上](https://agentpatterns.ai/agent-design/agentic-flywheel)) `[verified]`
