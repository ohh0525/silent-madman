### 候选 1 ⭐ 首选:RAG / 检索增强生成(Retrieval-Augmented Generation)

**一句话定义**:在生成之前先**从外部语料检索相关证据、再拼进上下文**的模式;2026 年的形态已从「一次向量召回 + 拼 prompt」演进为**由 agent 自主决定何时检索、检索什么、检索几次、要不要改写查询**的 *Agentic RAG*。

**为什么"当下"最有价值(缺口/接缝)**:
你的 wiki 已经把 RAG **当成参照物用了很多次**——`overview.md` 写「RAG vs 带溯源的长期记忆 = 检索手段 vs 完整记忆系统」、`LongTermMemory.md` 说「单一向量库是错配」、`ContextEngineering.md` 把 just-in-time retrieval 当作核心手法——**但全库没有一个 `RAG.md`,也没有一份 RAG 学习资料**。它是你知识网里「被引用最多、却最没有根基」的节点,也是 `overview.md` Open Questions 里**挂了最久的一条(2026-09-09 起)**。

**关键事实(tool-verified)**:

| 结论 | 内容 | 来源 |
|---|---|---|
| 范式迁移 | 2026 年的共识是「RAG is inside agents」,RAG 从「问答前查一次」升级为 agent loop 里的**知识访问层**(planning / tool use / 执行后 / 跨会话均可触发) | dev.to `RAG is Not Dead` |
| 两代分野 | **Traditional RAG**(确定的单次 retrieve→generate,低延迟、易预测)vs **Agentic RAG**(agent 自主选查询/来源/多轮,控制更灵活但可能空转、误用工具) | Turing Post《20 Advanced RAG Types》 |
| 进阶形态 | **GraphRAG**(实体-关系图作为检索目标,适合多跳/全局总结)、**Self-RAG**(以 `[Retrieve]`/`[IsRel]`/`[IsSup]`/`[IsUse]` reflection token 自评)、**Reflective RAG**(ACL Findings 2026) | AICC 知识库《06-RAG 与检索》 |
| 与记忆的关系 | **RAG 给上下文,记忆给连续性**;RAG 正在成为 agent memory 的**检索引擎**而非替代品 | dev.to `RAG is Not Dead` |

**与已覆盖概念的边界辨析**:

| 容易混淆 | 区别 |
|---|---|
| RAG vs [[LongTermMemory]] | RAG 是**检索手段**(召回即用、通常用完即弃);长期记忆是**完整记忆系统**(持久化、会更新、带 [[Provenance]]/[[CitationLock]] 纪律)。你这页已有此辨析,缺的是 RAG 这一侧的正文。 |
| RAG vs [[ContextEngineering]] | RAG 是**往窗口里送材料的一个来源**;上下文工程决定**要不要检索、检索多少、如何裁剪再注入**(just-in-time retrieval 就是二者的交点)。 |
| RAG vs [[Skill]] / [[ProgressiveDisclosure]] | 两者都是「按需加载」,但 Skill 加载的是**指令/流程**,RAG 加载的是**证据/数据**。 |
| Agentic RAG vs 普通 Agent | Agentic RAG = 把 `retrieve` 当成一个 tool 放进 [[ReAct]] 循环,由 agent 决定调用时机;它复用你的 Agent 节点,不新增组织形态。 |

### 候选 3:多智能体共享记忆与记忆互操作(Multi-Agent Shared Memory / Memory Interoperability)

**一句话定义**:让**多个 agent**(常常还跨框架)读写同一份持久记忆时所需的那层规范——不只是「存哪」,而是**身份寻址、线上 schema、信任与溯源、一致性、权限**五个面都要定义。

**为什么"当下"最有价值(缺口/接缝)**:
你的知识网到目前**全是单 agent** 视角:[[LongTermMemory]] 讲的是「一个 agent 的外存」,[[MCP]] 刚被你更新成无状态——而 **MCP(agent↔工具)与 A2A(agent↔agent)都不定义「共享记忆」的语义**。这条正好落在 `overview.md` Open Question 第 4 条上:**「Multi-agent memory sharing and role-based access control on shared persistent memory」——一字不差**。而且它是既有节点的**横向延伸**:你已经有了 [[Provenance]](信任/溯源这一面),缺的是**互操作(schema / consistency / permissions)**这另外几面。

**关键事实(tool-verified)**:

| 结论 | 内容 | 来源 |
|---|---|---|
| 协议缺口 | A2A 只管 agent↔agent 协作(设计上明确「无需访问对方内部状态/记忆/工具」),MCP 只管 agent↔工具;**截至 2026-07 没有任何获批的 agent 记忆互操作标准** | Mnemoverse《The Missing Layer》 |
| 五个面 | 记忆互操作需要定义:**identity & addressing / schema on the wire / trust & provenance / consistency / permissions** | Mnemoverse |
| 协议没解决共享状态 | 「MCP 和 A2A 标准化了 agent 怎么说话,但都不管状态」;状态碎片化会引发**经典 lost-update**(一个 agent 覆盖另一个的有意修改) | Redis《Agent interoperability》 |
| 常见替代形态 | 实践多绕开协议层,改用**外部共享状态层**:blackboard / 分层记忆 / checkpoint / pub-sub;LangGraph 的短期记忆默认**困在单个 thread 内** | Redis |
| 草案动向 | 已有社区白皮书提议给 A2A 加「contribution layer」(shared memory + result provenance + 跨框架互操作),明确**不取代 A2A/MCP** | DEV `A Contribution Layer` |

**与已覆盖概念的边界辨析**:

| 容易混淆 | 区别 |
|---|---|
| 共享记忆 vs [[LongTermMemory]] | 前者是**跨 agent / 跨框架共享**的存储(必须定义一致性、权限);后者是单 agent 的外存,只需溯源纪律,不需一致性模型。 |
| 共享记忆 vs [[MCP]] / A2A | MCP = agent↔**工具**,A2A = agent↔**agent**,两者都**不**定义 agent↔**共享记忆**。这是你刚更新的 MCP 页的天然下一章。 |
| 共享记忆 vs [[Provenance]] | 你已经有了溯源这一面;候选 3 的新增部分是**schema on the wire + consistency + permissions(RBAC)**,正是 Open Q4 里点名的「role-based access control」。 |

**建议下一步**:不建议立刻开 HTML(它偏工程/协议、体量不小)。**优先**在 wiki 补一个概念页 `concepts/AgentMemoryInterop.md`(或 `MultiAgentMemory.md`),作为 [[LongTermMemory]] 与 [[MCP]] 之间的横向连接;等你真的开始做多 agent 实践(比如把 gh-aw 扩成多 agent 协作)时,再升级成学习资料。
