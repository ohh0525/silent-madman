### 候选 1 · MCP Tasks（长活工具调用的一等公民）⭐⭐

**为什么「当下」最有价值（一句话点明接缝）**
它同时命中三件事：**①** `overview.md` 的 Open Questions 里**原文写着**「MCP Tasks / MCP Apps / EMA extensions — now first-class; worth a dedicated page」；**②** 本库 `concepts/MCP.md` 覆盖 Elicitation 与 MRTR，**完全没有 Tasks**（实测 0 次）；**③** 台账 09-23 那条「备查」曾记「Tasks 明确**非核心原语**」—— **这条记录在 2026-07-28 后被推翻**，是本库**自己记错的一条**。⇒ 它不是新话题，而是**本库一个已知缺口 + 一条已知错误记录的交汇点**。

**一句话定义**
MCP Tasks 是官方扩展 `io.modelcontextprotocol/tasks`：服务端对长活工具调用**返回一个持久 handle 而非阻塞**，客户端随后轮询取结果。

**与已覆盖概念的边界辨析**

| 对比对象 | 边界 |
|---|---|
| [[MCP]] 现有 Elicitation / MRTR | MRTR(SEP-2322) 是**传输层**的多轮往返；Tasks 是**应用层**的持久状态机 ⇒ 不可合并 |
| [[AgentHarness]] 持久执行 duty | 协议级 handle vs 运行时级 duty ⇒ **分栏互指**（本行给那个 duty 一个协议层答案） |
| [[AgentSandbox]] pause/resume | 沙箱能力 vs 协议能力 ⇒ 并列 |
| [[HumanInTheLoop]] 审批闸门 | `input_required` 把「闸门」从提示词约定升级为**协议状态机的一个显式状态** |

**关键事实（均来自 [verified] 来源）**
- **两代不兼容**：2025-11-25 以核心实验特性引入（**SEP-1686**，Surbhi Bansal / Luca Chang，2025-10-20），含阻塞的 `tasks/result` 与 `tasks/list`；**2026-07-28 移出核心、成为独立版本化的官方扩展**（**SEP-2663**，Luca Chang / Caitie McCaffrey，2026-04-27 创建，PR 2026-05-15 合并；仓库 `modelcontextprotocol/ext-tasks`，README 标 2026-07-28 schema 为 **Stable**）。
- **五态**：`working` / `input_required` / `completed` / `failed` / `cancelled`（后三者终态）。
- **三方法**：`tasks/get`（轮询，取代阻塞的 `tasks/result`）、`tasks/update`（回应 `inputRequests`）、`tasks/cancel`。
- **服务端逐请求**决定是否返回 task handle；客户端只一次性声明能力。

⚠️ **必须同屏的限定**
- **task ID 可以是 bearer token**（须足够熵、每次 `tasks/get`/`update`/`cancel` 都要鉴权）⇒ **Tasks 引入一个新的凭证面**，正落在 [[AgentIdentity]] 那一侧。
- **结果活得比提出它的会话更久** ⇒ retention / TTL / **陈旧结果须当作不可信输入**。
- `tasks/cancel` **是协作式的**：返回空确认，工作仍可能以 `completed` 结束 ⇒ **取消 ≠ 停止**。
- SDK 支持不均：TS SDK v1 线仍是 2025 代实验 API；Python SDK 的 tasks 示例标 **deferred**。

### 候选 2 · 派生状态 —— 没有任何一条记录写下它，于是记忆系统里也没有它 / Derived State over Evolving Data（MemDerive）⭐⭐

**为什么「当下」最有价值（一句话点明接缝）**
本库记忆失效栏已积累五栏 —— **内容**（[[Provenance]] / [[CitationLock]]）· **动作**（四动作）· **归属**（10-20B）· **选择层**（10-24B）· **上游失效传播**（10-26A Tether）—— **五栏全都假设「那个状态是某条记录」**；MemDerive 的定义恰恰是 *no record states it*，它必须由多条记录按规则**算出来** ⇒ **派生态不在记录层，五栏没有一栏能看见它**。

**一句话定义**
派生状态 = 不由任何记录陈述、必须从演化历史的多条记录按规则推导出来的任务状态；MemDerive 是为它造的一份诊断型基准。

**与已覆盖概念的边界辨析**

| 对比对象 | 边界 |
|---|---|
| **10-17B（FEB-30）** | 那条说「**外在分数看不见操作层失败**」；本行说「**即使你直接查记忆库本体，也看不见『没算出来』这一层**」 ⇒ 同形但方向不同，**必须并列互指、不得合并** |
| **10-26A（Tether / 上游失效）** | 那条**有一条真记录、后来失效**；本行**从来没有记录** ⇒ 分栏 |
| **10-24B（治理态损坏）** | 那条**控制面被改了**；本行**控制面没动，只是没人算** ⇒ 分栏 |
| [[LongTermMemory]] | 存什么 vs **什么根本没被组装出来** |

**关键事实**
- `arXiv:2610.25373`，v1 提交 **2026-10-18 16:24:33 UTC**；Sen Gao 等 8 人（含 Bingsheng He / Ming Wu / Jason Zeng / Michael Heinrich / Shixuan Sun）；**cs.DB**。
- 现有记忆基准**只给最终答案打分、没有中间状态的参考** ⇒ 「错了」无法追溯到漏掉哪个状态，「某个状态悄悄过期了」检测不到。
- 构造：符号化定义场景 → **Datalog 推导精确金标** + 记录**金标推导 DAG** 与每个查询的支撑事件 → 自然语言渲染历史（虚构实体 + 干扰项）。
- 规模：**10** 个场景 / **4,692** 事件 / **1,503** 查询；难度沿 **access / evolution / composition** 三维变化。
- 🔴 **承重结果**：**在派生状态上，每一个被测记忆系统都输给朴素 BM25 检索**，而**同一个答题模型拿到支撑事件后能到 96.01%**。
- 失败形态：**绝大多数是 *ungathered*** —— 系统**持有**那个缺失的中间状态，**却没有为需要它的问题取回它**；且记忆系统很少传播**没有新记录陈述的隐式变化**。
- 三原则：沿推导收集输入 · 规则带版本存储 · 通过记录的依赖维护派生状态。

⚠️ **必须同屏的限定**
预印本（未见同行评议）· **单一基准 / 自建生成器** · 「输给 BM25」是在**派生状态子集**上，**不得读作「记忆系统整体不如 BM25」** · **96.01% 是给足支撑事件的上界**，不是记忆系统的成绩。

### 候选 3 · 记住对了，但用它做这个决定不合法 / Scientific Use Validity（SciValidityBench）⭐

**为什么「当下」最有价值（一句话点明接缝）**
[[HumanInTheLoop]] 的 **authority ladder**（Evidence 最低 = 工具输出与网页检索「读但绝不据此行动」→ 中档 = 用户偏好 / 队友指令 → Policy 最高 = 用户自己的话）是**静态的**：它给**内容**分等级。SciValidityBench 证明**同一个内容**的等级随**别处的治理状态**（分析计划是否预先锁定、停止规则、访问史）而变 ⇒ **本库的 ladder 缺一个「状态依赖」维度**；[[Provenance]] 也只记**出处**、不记**解释状态**。

**一句话定义**
**Scientific use validity** = 被记住的证据，在「支配其解释的那个状态」下，**是否有资格影响一个决定**。

**与已覆盖概念的边界辨析**

| 对比对象 | 边界 |
|---|---|
| [[HumanInTheLoop]] authority ladder | 内容分级 vs **状态依赖** ⇒ **增维，不替换** |
| [[Provenance]] | 记**出处** vs 记**解释状态** ⇒ 两个字段，不是同一个 |
| **10-24A（AMV-Guard）** | 那条按**动作后果**定价「要不要重查」；本行按**证据资格**判定「能不能用」 ⇒ 一个管「查不查」、一个管「用不用」 |
| **10-27B（MemDerive）** | 那条「状态**没被算出来**」；本行「状态算出来了但**没被用于判定资格**」 ⇒ **同一段的两半，须分栏互指** |

**关键事实**
- `arXiv:2610.34767`，v1 提交 **2026-10-26 03:12:57 UTC**（**昨日新增**）；Yuexi Pan（清华）+ Yongchao Chen（中国科大 / 清华）；cs.AI；GitHub `SciValidityBench/SciValidityBench`，站点 `scivaliditybench.github.io/SciValidityBench`。
- 判据例：同一个 `p=0.03` —— 预先注册结果、固定样本量、遵循停止规则 ⇒ 可支持**确认性**主张；从二十个被检视结果里挑出一个跨过阈值 ⇒ 只是**探索性**。**数字相同，证据地位不同。**
- 构造：可执行基准工厂，**64** 个 TaskSpec × **5** 个 validity 模块 × **6** 个科学域；含程序化决策 oracle、受控干预、自动打分；**SciStateForge** 编译器—阅读器把分散历史转成显式的**决策支配状态**。
- 🔴 **结果**：跨 **4 个模型族**，编译后的科学状态相对通用 Event Graph 提升有效决策 **9.2–18.8 pp**；**纯检索复现不出这个跨族增益**；内容相同的 flat / typed 视图对照 ⇒ 增益来自**暴露支配状态**，而非某种图序列化。
- 承重句：*shifts memory evaluation from **finding the right fact** to **deciding whether that fact should control the decision***。

⚠️ **必须同屏的限定**
**v1 昨日提交、预印本未同行评议** · 合成生成的实验史（64 TaskSpecs 规模有限）· 「9.2–18.8 pp」是相对 **generic Event Graph** 基线、**非绝对正确率** · 科学域为主，**外推到通用 agent 需谨慎**。
