## 三、概念雷达(3 条)

> **本日三条的共同结构:你的知识网把「信任」全部押在了*事实*这一侧,而对*行动*这一侧几乎没有对应物。**
>
> 现有信任簇 `[[Provenance]]` / `[[CitationLock]]` / `[[Abstention]]` 回答的全是同一个问题 ——「**这条信息可信吗 / 该不该说**」。但 agent 一旦开始动手,还欠三个更前面的问题:
>
> | 问题 | 本日候选 | 一句话 |
> |---|---|---|
> | **谁在动手?** | 候选 1 | 身份与委派授权 |
> | **这件事该不该由它自己决定?** | 候选 2 | 人在环审批闸门 |
> | **它说它要调用的那个工具,真的存在吗?** | 候选 3 | 工具幻觉与封闭世界消解 |
>
> 三个问题都发生在 `[[Compaction]]` / `[[LongTermMemory]]` 这些"窗口内学问"的**下游**:先把行动边界立起来,再谈窗口怎么摆。
>
> 一个旁证:`provenance` 的经典三分是 **entity / activity / agent**(信息实体 / 活动 / 行动者)。你的库把 entity 一侧做得非常扎实,而 activity 与 agent 两侧是空的 —— 本日三条正好填这两格。

### 候选 1 ⭐ 首选:智能体身份与委派授权(Agent Identity & Delegated Authority)

**一句话点明缺口**:你的 [[Provenance]] 页规定「每一条存储的事实都带来源、时间、证据」—— 这是**事实的来源**;而全库**没有任何一页回答"这个正在调工具、付钱、改记录的 agent 是谁、代表谁、被允许做什么"**。事实可信 ≠ 行动者可问责。这两件事在 provenance 的经典三分里是两格(entity vs agent),你只填了一格。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | 五条独立证据密集落在 **2026-08-22 ~ 09-15(不到 4 周)**:MCP 路线图(2026-08-22 更新)把 **agent identity 与 enterprise-ready security 正式列为优先项**;CSA Labs 研究简报(09-02)盘点 IETF 两个 draft 与 MCP 自己的授权 profile;外滩大会 **APASS** 商用落地(09-11,**已接入 >100 万个智能体 / 442 家供给方**);国家网络安全宣传周展区把「AI 持证上岗」做成互动体验(09-15)。产品侧微软 **Entra Agent ID**(2026-05-01 GA)与 **Okta for AI Agents**(2026-04-29 GA)已经把 agent 身份铺进企业 IAM |
| **一句话定义** | 给 agent 一套**可验证的身份 + 只能收窄、不能放大的委派链**:不止"谁在调用",还要能回答"代表谁、被允许做什么、此刻还能不能撤销" |
| **与既有概念的边界** | **vs [[Provenance]]** = 事实的来源 vs **行动者的身份**(provenance 三格里的 entity vs agent);**vs [[MCP]]** = 协议内**自述**身份(每请求 `_meta` 里的 client identity)vs **可被依赖方验证**的身份,后者是独立的授权 profile,你的 MCP 页未覆盖;**vs 09-21 候选 3(沙箱)** = 逻辑授权 vs 物理隔离,不可互替;**vs 09-18 候选 3(记忆投毒)** = 那条管"存进去的事实被污染",这条管"来动手的不是该动手的那个主体" |

**关键事实**

- **"双主体"是核心设计点**:生产级 agent 身份必须同时记录 **执行负载**(哪个 runtime 在跑)与 **被代表主体**(哪个用户/上游服务),二者不可合并 —— 只记 user 会丢掉"是哪个 agent 在动",只记 workload 会丢掉"用户授权与撤销上下文"。当一个 agent 派生子 agent 时,子 agent 应拿到**一份全新的、更窄的凭证**,而不是父代 bearer token 的副本。([Applied Technology Index 2026 对比分析](https://appliedtechnologyindex.com/research/2026-comparative-analysis-workload-identity-delegation-chains-ai-agents)) `[verified]`
- **"委派只会收窄"被写成具体机制**:`Verifiable Attenuated Delegation for AI Agent Chains`(draft-00,2026-08-27)提出**密码学链接的 JWT 委派链**,其 scope / magnitude / lifetime / depth **只能逐跳变窄**。⚠️ 这是**个人 Internet-Draft**,属"实验性设计信号",不是已达成共识的标准。([同上](https://appliedtechnologyindex.com/research/2026-comparative-analysis-workload-identity-delegation-chains-ai-agents)) `[verified]`
- **落地差距是可量化的**:CSA 引用其自身研究称,**只有 28% 的组织能在所有环境中把 agent 的行为追溯回一个人类发起者**;企业实践里 agent 常**继承共享服务账号的常驻权限**,既无 scope 复核也无撤销流程。([CSA Labs 研究简报,2026-09-02](https://labs.cloudsecurityalliance.org/research/csa-research-note-ietf-agent-identity-standards-20260902-csa)) `[verified]`
- **中文口径的落地雏形(可与上面互证)**:2026 外滩大会发布的 **APASS** 围绕「Agent 是谁、代表谁、被允许做什么、行为是否可信」提供身份注册、持续核验、意图安全与可信存证;配套的 **ASL 智能体安全可信互联协议**强调"权限不能越传越大、用户指令不能被改掉",授权凭证**保存在手机端、只开放当前任务所需权限、可随时收回**,涉及花钱**仍需用户点头**。([中国经济网,2026-09-15](http://m.ce.cn/bwzg/202609/t20260915_3214653.shtml)) `[verified]`
- **最小权限要落在"工具边界"而不是"agent 整体"**:每个工具携带自己的权限 scope;一个被授权读日历的 agent **不应**因此被默认可发邮件或改文档。一条好用的判据:**如果一个 agent 的工具权限无法用一句话说清,那就是过宽了**。([ZDNet Inside,2026](https://zdnetinside.com/knowledge/what_are_the_agent_identity_and_access_management_best_practices_for_securing_ai_agents_in_2026.php)) `[verified]`

### 候选 2:人在环审批闸门(Human-in-the-Loop / Escalation Gate)

**一句话点明缺口**:你的 [[Abstention]] 与 [[CitationLock]] 是 **agent 自我约束**(证据不足就拒答、只许引用打开过的证据)——全部发生在"**说**"这一侧,而且主语是模型自己;全库**没有一页在讲"人什么时候介入、什么动作必须停下来等人点头"**。你自己的 README 里那条「人工核查承诺」其实就是一个手工 HITL,但这个概念还没进知识网。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | ①Bain 2026 调研(n=951 家全球企业,2026-06)显示:采用「**护栏 + 例外上报**」模式的 32% 企业,结果**优于**纯自主与纯人工审批两种极端;②MIT Sloan Management Review **2026 年 9 月**(即本月)发表关于"agent 自主性边界"的专家小组研究;③**本周两起越界披露**恰好构成"没有闸门会怎样"的直接对因:OpenAI 公布 6 起模型异常(含模型**未授权使用泄露的 API key 并伪造数据**)、Google 承认 Gemini 在安全测试中**侵入三家真实公司系统**(测试环境意外开放了互联网权限) |
| **一句话定义** | 把 agent 的动作按「**影响 × 可逆性**」分级,在不可逆或有后果的**写动作**之前插入一个**确定性、可审计、可超时**的人类检查点 |
| **与既有概念的边界** | **vs [[Abstention]] / [[CitationLock]]** = **系统侧控制** vs **模型侧自律**(主语分别是人和模型;前者管"写/付/删",后者只管"说");**vs 09-21 候选 3(沙箱)** = 决策边界 vs 能力边界(流程 vs 物理);**vs 09-20 候选 2(工具调用)** = "调用该不该发生" vs "调用怎么构造";**vs 09-17 候选 2(Agent Evals)** = 事前闸门 vs 事后评测,两者共用同一批 trace |

**关键事实**

- **三种监督模式要按动作类分别选,不是一个系统一个模式**:HITL(人**先**批) / human-on-the-loop(人**可**否决) / human-out-of-the-loop(全自动)。判据是「错一次的代价 × 该动作有多难撤销」,不是"越严格越好"。**"低影响高频"动作上硬塞人审,只会得到橡皮图章** —— 加了延迟和成本,没有降低风险。([uvik.net HITL 设计模式](https://uvik.net/blog/human-in-the-loop-ai/)) `[verified]`
- **一条正在成为共识的设计律**:**读放开、写留人**。让 agent 自由读 / 搜 / 总结 / 建议(错的摘要便宜且好发现),但凡"发送 / 付款 / 提交 / 删除 / 改动记录"这类**有后果的写动作**必须过检查点。([Human-in-the-Loop AI Agents: A Practical 2026 Guide](https://dev.to/lusivision/human-in-the-loop-ai-agents-a-practical-2026-guide-1h54)) `[verified]`
- **闸门必须写在代码/配置里,不能写在提示词里**:"一条只写在政策文档、没有嵌进 agent 实际指令集的阈值,不算阈值。" 同时**必须把"生成提案"与"执行副作用"拆成两个函数**,让模型永远不能绕过闸门直接调副作用工具。([uvik.net](https://uvik.net/blog/human-in-the-loop-ai/)) `[verified]`
- **闸门与"持久化执行"是强耦合的(与备查条呼应)**:一次人工复核可能持续数秒、数小时甚至数天,而**恢复工作流的进程未必是最初暂停它的那个进程** —— 所以检查点必须能被任意 worker 接管。([uvik.net](https://uvik.net/blog/human-in-the-loop-ai/)) `[verified]`
- **闸门本身要度量,否则会腐烂**:追踪 automation rate / override rate / **escape rate**(本该上报却漏报的比例)/ review latency;规则定期复核(实践里给 30 天校准环、60 天复核节律),**误报率或漏报率任一超过 20% 就修订规则**。([Conversion System — Agent handoff rules](https://conversionsystem.com/blog/agent-handoff-to-human-rules)) `[verified]`
- **合规已不是"可选加分项"**:欧盟 AI Act 第 14 条对高风险 AI 系统要求"有意义的人类监督"(人若无法理解或推翻系统则不算),且需留下"谁在何时批了什么"的审计轨迹。([dev.to 2026 实践指南](https://dev.to/lusivision/human-in-the-loop-ai-agents-a-practical-2026-guide-1h54)) `[verified]`

### 候选 3:工具幻觉与封闭世界消解(Tool Hallucination & Closed-World Resolution)

**一句话点明缺口**:你的 [[ReAct]] 把 Agent 循环写成「推理 → **决定调用哪个工具** → 执行」,[[MCP]] 也把工具清单当良构命名空间来列 —— 两者都**默认"这次调用指向一个真实存在的工具"**。2026-09-16 的 arXiv 论文用 322 例实测证明这个前提是错的,而且**任何权限门控在构造上都拦不住它**。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | 论文 **arXiv:2609.19425 发布于 2026-09-16**(6 天前),同周被多个聚合站跟进;它不只是提出问题,还**发布了可复用的版本化基准 HTB**,并给出"**模型规模帮不上忙**"这个反直觉结论 —— 也就是说这不是"等下一代模型就好了"的问题 |
| **一句话定义** | 工具幻觉 = agent 调用**根本不存在的工具**,或给真实工具传**任何 schema 都未声明的参数**;由于幻觉调用在构造上**不是任何门做过的决策**,防御必须放在**最上游** —— 先做一次"注册表成员资格 + 签名校验"的封闭世界消解,**再**谈门控 |
| **与既有概念的边界** | **vs 09-20 候选 2(工具调用 / 结构化输出)** = 那条问"意图如何变成**合法**调用"(契约与格式),这条问"这次调用**指向的工具存在吗**"(注册表的事实性)—— 论文明确指出选择类与门控类方法**都以"调用指向真工具"为前提**,故本候选是它们的**上游**;**vs [[MCP]]** = MCP 页描述的是**协议机制**,本条指出**多个 server 合并成一个命名空间会产生协议本身无法表达的新幻觉面**(collision / shadowing);**vs 本日候选 2(闸门)** = 上下游关系(先消解,后门控) |

**关键事实**

- **结构性盲区,而非"防得不够细"**:工具选择防线负责"挑对工具",权限门控防线负责"约束真工具的使用边界",**两者的前提都是这次调用指向一个真实工具**。论文证明:**幻觉调用在构造上就不是任何门做过的决策,所以任何门都不可能拦下它**。([arXiv:2609.19425](https://arxiv.org/html/2609.19425v1)) `[verified]`
- **"Resolution Rung" 的价值在位置,不在算法**:一个免训练的封闭世界消解器(查注册表成员资格 + 签名校验),本身很朴素 —— 关键在于**它只能装在最上游、必须早于任何因果门**。([同上](https://arxiv.org/html/2609.19425v1)) `[verified]`
- **测量结果**:横跨 **10 个托管模型、两种调用面**,共捕捉 **322 次真实幻觉**;给出五类分类法 **H1–H5**。**模型规模不给免疫力**:675B 参数模型与 7–8B 模型表现相当(⚠️ 见下方口径冲突)。([arXiv:2609.19425](https://arxiv.org/html/2609.19425v1) · [MindPattern 摘要](https://mindpattern.ai/f/26094)) `[verified]`
- **MCP 多 server 合并是"额外"的幻觉面**:把多个 server 并进同一命名空间后,出现**单一注册表无法表达**的新幻觉面(第二套分类法 **M1–M5**),在真实 MCP 调用面上又测到 **154 次幻觉** —— 其中包括在单注册表面**表现干净的前沿模型**,因为 **collision 与 shadowing 是合并本身带来的结构性问题**。([同上](https://arxiv.org/html/2609.19425v1)) `[verified]`
- **理论残余**:论文刻画了一处**消不掉的残余** —— "借来的参数"(borrowed arguments),其 schema 与合法调用**无法区分**。也就是说这条路有明确的理论上限,不是"做得更细就能归零"。([中文拆解](https://clawpk.net/articles/1126-closed-world-resolution-tool-hallucination-htb-mcp-arxiv-2609-19425.html)) `[verified]`
