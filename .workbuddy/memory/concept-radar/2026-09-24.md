> **本日三条的共同结构:你的知识网把三个量当成了「常量」,而 2026 年的证据表明,它们都已经变成「策略变量」。**
>
> | 被当成常量的量 | 你库里的隐含假设 | 2026 的事实 | 候选 |
> |---|---|---|---|
> | **保留时长** | 记忆「记得越多越好」,只讲怎么记、怎么记得可信 | AWS 把「何时该忘」做成可配置策略(TTL / 衰减 / 合并) | 候选 1 |

>
> 三条都**不新增「知识内容」维度,而是把某个既有维度从定值改成变量**:记忆的**时间轴**、上下文的**空间**、执行的**主体**。这也解释了为什么你的库在这方面显得「密而偏」——[[ContextEngineering]] 一整簇把「窗口内怎么摆」讲透了,却不讨论「窗口外的另一半」(候选 2)、「记忆什么时候清」(候选 1)、「换谁来处理」(候选 3)。

### 候选 1 ⭐ 首选:智能体记忆的生命周期治理 / 遗忘(Memory Lifecycle Governance / Agent Forgetting)

**一句话点明缺口**:你的记忆簇([[LongTermMemory]] / [[Provenance]] / [[CitationLock]] / [[Abstention]],4 页)回答的全是「**怎么记得住、记得可信**」;而 AWS 官方那篇的第一句话就把问题翻到了另一面——**「核心问题不是记忆能不能存,而是什么时候该让它忘」**。你的知识网里**没有任何一页讨论删除**。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | **AWS 官方博客于 2026-09-04 发布《Designing lifecycle policies for AgentCore memory》**,把这件事从"提示词技巧"提升为**可版本化、可回滚、可审计的工程能力**:给出内存分类法 + 三条互补策略 + 夜间 Step Functions 工作流 + 可直接部署的 AWS CDK 栈。这不是观点文章,是**带代码与成本估算的参考实现**——一个概念被云厂商做成"标准件"的时刻,通常就是它成熟的时刻。 |
| **一句话定义** | 把「遗忘」当成与「存储」对称的一等公民:对持久记忆按**类型**设不同保留期(TTL)、按**价值**打分(创建/访问近度 + 访问频次)、把多条零散观察**合并**为一条权威事实并删除原件,从而同时控制**质量衰减**与**合规风险** |
| **与既有概念的边界** | **vs [[LongTermMemory]]** = 同一条生命周期的两端:那页讲「跨会话把知识存在窗口外」,本条讲「**这条知识什么时候该消失**」——你的记忆页只描述写入,从未定义**留存期**;**vs [[Provenance]]** = 最有张力的接缝:provenance 要求「每条事实都带来源/时间/证据」以支撑事后核查,而删除权(GDPR)要求「**把它连根抹掉**」——**两者会冲突**:删掉了事实,账本上的引用怎么办?AWS 的解法是把删除做成**带回执与失败清单的处理器**(`deleted_count` + `failed_memory_ids`),即"删除本身也要留痕";**vs [[Compaction]]** = 不同层面:compaction 压的是**窗口内**、当轮的内容;生命周期治理管的是**窗口外**、跨会话的持久记忆,且它以**天/周**为单位、离线批量跑(夜间工作流),不参与当轮推理;**vs 09-18 候选 3(记忆投毒)** = 记忆卫生的两端:**投毒**是"写进来的东西是恶意的",**遗忘**是"写进来的东西是陈旧的";前者是安全威胁,后者是质量+合规威胁,二者共享"记忆是可靠性子系统"这一前提 |
| **关键事实** | 见下 |

**关键事实**

- **三类记忆、三种保留期,不是一刀切**:AWS 把 agent 记忆分为 **episodic**(对话记录,时间戳/会话绑定/高容量,最优先过期)、**semantic**(从交互提炼的独立事实与偏好,如"该用户偏好 us-east-1",持久高价值、**合并的主要对象**)、**procedural**(学到的工作流与工具用法,如"问成本时先查 Cost Explorer 再汇总",容量最低但价值最高、**保留最久、修剪门槛最高**)。([AWS ML Blog,2026-09-04](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)) `[verified]`
- **三条互补策略,且有明确执行顺序**:①**TTL 过期**(默认 episodic 90 天;生产建议 summary 30–60 天、semantic 6–12 个月、procedural 不设 TTL)——它**最先执行**,先删掉"本来就该没了"的,避免浪费后续算力;②**相关性衰减打分**(三项加权:`W_RECENCY·e^(-λ·距创建天数) + W_ACCESS·e^(-λ·距最近访问天数) + W_FREQUENCY·min(访问次数/50, 1)`,权重 0.4 / 0.35 / 0.25);③**LLM 合并**(把低于阈值的记忆按批,默认 **10 条一批**,交给 Bedrock 合并成紧凑的 semantic 条目,然后**删除原件**)。([同上](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)) `[verified]`
- **它把"调参"收敛成了一个直观旋钮**:不暴露原始衰减常数,而是给 `pruneDays`——"一条不再被访问的记忆大约多少天后跌破阈值"。默认 `pruneDays=45 / threshold=0.3` ⇒ `decay_rate ≈ 0.02676`,部署命令就是 `npx cdk deploy -c pruneDays=45`。([同上](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)) `[verified]`
- **成本被明确算出来了,而且很小**:主要成本是合并时的 Bedrock 调用。**1,000 条记忆、其中 20% 低于阈值 ⇒ 每晚约 20 次 Bedrock 调用 ≈ $0.01–$0.02**;命名空间到 **100,000 条**时约 **$50–$100/月**。([同上](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)) `[verified]`
- **两件必须一起做、否则治理本身制造事故**:①**回归测试**——文章用 AgentCore Evaluations 验证「修剪没有降低回答质量」,因为**修剪太狠会删掉业务仍依赖的历史**,导致关键场景答不出来,所以必须保留**可回滚的快照/版本**;②**打分模型自身的偏见会被放大到修剪结果里**——若打分只依赖语义相似度或时间衰减,它会系统性地偏向某类记忆,带来**公平性/代表性风险**。([同上](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/) · [Spotech 编辑分析](https://www.spotech.online/en/designing-lifecycle-policies-for-agentcore-5mpk)) `[verified]`
- **两则真实故障,说明这不是理论问题**:一个客服 agent **把四个月前已解决的账单争议当作当前问题**引用;另一个 agent **因记忆里仍存着已被取代的运维手册而重复过时建议**。([AWS ML Blog,2026-09-04](https://aws.amazon.com/blogs/machine-learning/designing-lifecycle-policies-for-agentcore-memory/)) `[verified]`
- **一个必须知道的实现边界**:AgentCore memory **不提供内置的自动删除 TTL**——TTL 要靠系统时间戳字段(`x-amz-agentcore-memory-createdAt`)+ `BEFORE` 过滤操作符自己实现。(同上) `[verified]`

### 候选 2:上下文卸载 / 文件系统即上下文层(Context Offloading / Filesystem as Context Layer)

**一句话点明缺口**:你的 [[Compaction]] 把「窗口塞满怎么办」的答案**默认成了"摘要"**;而 2026 年生产 harness 的实际顺序是**先卸载、后摘要**——原话是「**只有当卸载也用尽空间之后,harness 才退回到摘要**」。也就是说:**压缩是兜底,不是首选**。你的库缺的正是这个"窗口外的工作区"层。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | 2026-09-12 的一篇工程综述把 **LangChain Deep Agents / Claude Code / Manus / OpenAI Codex / Bedrock AgentCore** 五家的真实阈值并列摊开(不是观点,是各家**线上发布**的数字),使"上下文卸载"第一次有了可比较的工程口径;同期 LangChain 官方在 2026-09-04 / 09-06 明确把 Deep Agents 的工作区描述为 **durable / inspectable / swappable**,并抽出 `BackendProtocol`(read/write/glob/grep)作为可替换的存储抽象。 |
| **一句话定义** | 把超出注意力预算的内容**从窗口里移出去、留在窗口外的持久层(文件系统/对象存储)**,窗口内只保留**指针 + 极短预览**,需要时再用 grep / 按行读**按需取回**——它是"上下文的位置"从窗口内变成窗口外的策略 |
| **与既有概念的边界** | **vs [[Compaction]]** = 最关键的接缝,而且是**有序关系**:compaction 是**有损**的(摘要会丢掉那条关键约束)、卸载是**无损**的(原文件还在,可 `read_file` 找回);实践中的顺序是**先卸载 → 卸载用尽 → 才压缩**;**vs [[ProgressiveDisclosure]]** = **作者与时点不同**:PD 加载的是**人预先写好**的知识(SKILL.md),卸载出去的是**运行期生成**的产物(工具输出、日志、中间文件);两者共用"按需加载"的形状,但一个是静态资产、一个是动态工作区;**vs [[LongTermMemory]]** = 存的东西不同:记忆是**跨会话的知识**,卸载层多是**任务级的工作区**(scratchpad)——它甚至更接近 09-23 候选 1「持久化执行」所依赖的那块存储,但**目的相反**:卸载是让模型**少看**,持久化执行是让进程**不死**;**vs 09-21 候选 1(压缩保真度)** = **互补而非重复**:那条暴露的是压缩的风险面,本条正是**绕开压缩**的那条路(所以两者一起落地效果最好);**vs [[LLMContext]]** = 那页描述的是"预算有多少",本条描述的是"预算不够时内容搬去哪" |
| **关键事实** | 见下 |

**关键事实**

- **阈值是硬的,而且先卸载后摘要的顺序是明写的**:Deep Agents 的两条卸载规则——①工具响应**超过 20,000 token** 就写入文件系统,窗口内只留**文件路径 + 前 10 行预览**;②会话上下文**越过模型窗口的 85%** 时,较早的 write/edit 工具调用(其完整文件内容本就在磁盘上)**截断成指针**。文章原话:「**Only after offloading runs out of room does the harness fall back to summarization.**」([MarkTechPost,2026-09-12](https://www.marktechpost.com/2026/09/12/context-engineering-inside-the-harness-4-mechanisms-that-beat-context-overflow-and-goal-loss-on-long-horizon-tasks/)) `[verified]`
- **Claude Code 把同一套预算用在了"进窗口之前"**:auto memory 上限 **前 200 行或 25KB**;MCP 工具 schema **默认延后**,只列工具名,全量 schema 按需通过 tool search 载入;compaction 之后任何**超过 5,000 token** 的重复读文件都转成路径引用。([同上](https://www.marktechpost.com/2026/09/12/context-engineering-inside-the-harness-4-mechanisms-that-beat-context-overflow-and-goal-loss-on-long-horizon-tasks/)) `[verified]`
- **卸载在架构层的收益可以量化**:官方文档里的模拟——一个研究子 agent **读入 6,100 token 的文件、只向父 agent 返回 420 token**;Anthropic 的口径是子 agent 可能烧掉数万 token 探索,但**只回吐 1,000–2,000 token** 的蒸馏摘要。([同上](https://www.marktechpost.com/2026/09/12/context-engineering-inside-the-harness-4-mechanisms-that-beat-context-overflow-and-goal-loss-on-long-horizon-tasks/)) `[verified]`
- **为什么必须这么做:规模是硬数据**——Manus 报告**一个典型任务约需 50 次工具调用**,且**输入:输出 token 比接近 100:1**;每个 observation 落进上下文后就一直待着,而**原始指令会漂移到窗口中部——恰恰是召回最差的位置**。所以文章的判断是:「**目标丢失不是模型 bug,而是未受管理的上下文在足够长的任务上的必然结果**」。([同上](https://www.marktechpost.com/2026/09/12/context-engineering-inside-the-harness-4-mechanisms-that-beat-context-overflow-and-goal-loss-on-long-horizon-tasks/)) `[verified]`
- **LangChain 官方把工作区形式化成可替换的存储抽象**:2026-09-04 强调 agent 工作区应当是 **durable / inspectable / swappable**,并指出 MongoDB 已支持 Deep Agents 的虚拟文件系统;`BackendProtocol` 暴露 read / write / glob / grep,底层存储可自选。Deep Agents 的定位是「用摘要**中间件** + 外部存储管理上下文,同时**保留工作史**」。([GenAI PM — Deep Agents](https://genaipm.com/wiki/concepts/deep-agents)) `[verified]`
- **生态侧已把它固化成一份 Skill**:一份被标注 Grade A 的 `filesystem-context` skill 明确写出了「**do not activate for adjacent work owned by other skills**」的边界——语义跨会话记忆归 `memory-systems`、对话摘要压缩归 `context-compression`、多 agent 拓扑归 `multi-agent-patterns`,**这条边界与你 wiki 里的页正好一一对应**。它还给出四种上下文故障模式(缺失 / 检索不足 / 检索过度 / 深埋)与各自的文件系统对策。([Agent Skills Directory](https://www.skillsdirectory.com/skills/muratcankoylan-filesystem-context)) `[verified]`
- **⚠️ 反直觉的代价项(必须一起记住)**:持久化不是免费的。MarkTechPost 引 ETH Zurich 研究(其 2026-02-25 报道)——**LLM 生成的仓库上下文文件在两项基准上让推理成本上升 20% 和 23%,开发者手写的文件最高上升 19%,而任务成功率并没有普遍提升**。所以 Claude Code 官方建议 `CLAUDE.md` **保持在 200 行以内**,把参考资料挪进 skills 或按路径生效的规则里,**只在需要时加载**。(同上 MarkTechPost) `[verified]`

### 候选 3:模型路由 / 成本-质量路由(Model Routing / Cost-Quality Routing)

**一句话点明缺口**:你全库都在**默认"处理这段上下文的模型是常量"**——[[Token]] 讲 token 单价、[[LLMContext]] 讲窗口大小、[[ContextEngineering]] 讲窗口里放什么,三者**都没问过"换成另一个模型会怎样"**。2026 年的产业事实是:**模型选择本身是运行时的策略变量**,而且 Cognition 用实验证明了"在会话开始按 prompt 判难度"这条路走不通。

| 项 | 内容 |
|---|---|
| **为什么是"当下"** | ①**Cognition 于 2026-09-11 发布 Devin Fusion**,并联合 **Artificial Analysis** 与 **Vals AI** 给出跨基准的成本/质量表(官方页可直接打开);②**GitHub Copilot 在 2026-09-14** 给 Auto 模型选择上线 **efficiency / balance / intelligence** 三档(09-23 备查已记录,本期确认它延续);③2026 年被称为 **"Inference Flip"**——企业 AI 预算的主体已从训练转向推理,而 **agentic 工作负载每任务消耗的 token 是传统 chatbot 的 5–30 倍**。三件事把"路由"从优化技巧推成了**架构决策**。 |
| **一句话定义** | 在**运行时**为每个请求/子任务决定"交给哪个模型处理"——既包括按复杂度分级与按供应商健康度兜底,也包括**会话中途在两个并存的 agent 之间委派与回收**,目标函数是**每任务成本**(而非每 token 价格) |
| **与既有概念的边界** | **vs [[Token]]** = 最直接的接缝:那页隐含"token 单价是定值",而路由让**单价与效率同时成为变量**——Cognition 的实测结论是「**2026 年,应该按每任务价格而非每 token 价格来评估模型(与模型-harness 组合)**」;**vs [[LLMContext]]** = 窗口大小是**按模型**定的,所以"路由"字面意义上就是"**换一个预算**";**vs [[ContextEngineering]]** = 分工清晰:CE 决定"窗口里放什么",路由决定"**哪个窗口来处理它**";**vs 09-20 候选 1(提示缓存)** = **一对天然的对手**:缓存的前提是"同一模型的前缀可复用",而**中途换模型会打破缓存**——所以 Fusion 把切换点**对齐到 compaction 时刻**(压缩本来就重置缓存,此时切换"免费"),这是两条候选之间最锋利的连接点;**vs 09-17 候选 2(Agent Evals)** = 路由的决策信号来自评测(离线样本集 / 线上质量与延迟观测),evals 是它的**上游供给** |

**关键事实**

- **厂商一手口径:成本降幅是"逐基准"的,不是一句"省 39%"**:Cognition 官方表格(与 Artificial Analysis / Vals AI 联合评估)显示 Fusion(**lead + sidekick**)相对同 lead 单模型的价格——DeepSWE 1.1:63.1 分 @ $7.88(**−46%**);Terminal-Bench 4:56.1 @ $13.37(−23%);SWE-Atlas QnA:65.9 @ $5.00(−34%);Vals Code Migration:57.3 @ $42.00(−41%);FrontierCode 1.1(Extended):63.5 @ $1.67(−38%)。官方标题句是「**up to 39% more efficient**」。([Cognition — Introducing Fusion in Devin Desktop & CLI,2026-09-11](https://cognition.com/blog/local-fusion)) `[verified]`
- **质量几乎不变,但在"判断密集型"任务上会掉**:Artificial Analysis 的独立比较里,Fable 5.1 + SWE-2 = **61.7**(对比 Fable 5.1 在 Claude Code 中 62.2),**每任务 $7.90 vs $12.40**。但同一张表里 **Astra + SWE-2 在 Terminal-Bench 4 上从 55.6 掉到 50.0**(成本 $10.08→$6.06)——**这就是路由的失效模式:把"判断"本身外包出去,质量会崩。**([AI Primer — Cognition launched Devin Fusion](https://www.ai-primer.com/engineer/stories/devin-fusion-benchmark) · [Cognition 官方表](https://cognition.com/blog/local-fusion)) `[verified]`
- **Cognition 明确说了为什么"单次路由"不够——两个理由**:①「**初始 prompt 不足以判断任务难度**」——"修一下 xyz 这个 bug"可能是一行边缘情况,也可能要重架构整个产品,「**你只有在真正调查过代码之后才知道**」;②「**中途换模型会打破 prompt 缓存**,让前沿模型反而更贵,从而抵消路由的意义」。所以他们选择**跑两个并存的 agent、各自维持持久 context,只交换 brief / 结果 / 反馈**(而不是传整段对话)。([Cognition,2026-09-11](https://cognition.com/blog/local-fusion)) `[verified]`
- **切换点被设计成"免费"的**:第三方技术拆解指出,Fusion 用轻量分类器判断"子任务是否超出 sidekick 能力",并**把模型切换与 context compaction 事件同步**——因为压缩本来就触发缓存重置,**在这一刻换模型,缓存开销近乎为零**。([B Lab — Devin Fusion 拆解,2026-09-12](https://b-lab.team/en/content/6b8b0266-c4cb-4873-b062-f314c0b8ea6e)) `[verified]`
- **最反直觉、也最有价值的一条:「更贵的模型可能让整个系统更便宜」**——Cognition 报告把 lead 从 Opus 4.8 换成 **Fable 5**(名义单价**贵一倍**),同 sidekick 下**会话成本反而低 9%**,FrontierCode 得分更高;原因是 Fable **更早委派、给出更好的 brief**,而 Opus **事无巨细地微管理 sidekick、重做了很多工作**。同理,sidekick 从 GPT-5.6 Luna($0.20/Mtok)换成 SWE-2($0.75/Mtok,单价 **+275%**),总成本几乎不变(**$2.39 → $2.34**),因为更强的 sidekick 需要更少轮次与更少返工。([Cognition,2026-09-11](https://cognition.com/blog/local-fusion)) `[verified]`
- **商业口径也在往"按成果计费"移动**:有分析指出集中式路由层正在承载 **outcomes pricing**(按任务是否达成而非按 token 计费),并引基准称按复杂度匹配后 DeepSeek 场景可省 **88.3%**、OpenAI 场景 **84.9%**——⚠️ **这些数字来自单一分析页,转述链较长,建议只作为方向参考**。([The Next Gen Tech Insider — Centralized Router Platforms](https://www.thenextgentechinsider.com/pulse/centralized-router-platforms-drive-new-outcomes-pricing-in-ai-economics)) `[verified]`
