### 候选 10-31A ⭐⭐⭐ · 弃权的代价 —— 过度拒绝作为一种失效模式

| 项 | 内容 |
|---|---|
| **概念名** | 弃权的代价 / 双侧成本前沿上的过度拒绝 · **Cost-Sensitive Refusal / Over-Refusal as a Failure Mode** |
| **一句话定义** | 「不确定就拒绝」不是免费的安全默认 —— 拒绝本身有成本（漏掉真实请求），把它放进一个**非对称代价函数**后，朴素谨慎在多数部署下是**被支配策略**。 |
| **为什么当下最有价值** | 本库整套「阅读纪律」（`Provenance` / `CitationLock` / `Abstention`）把 **Abstention 当成无条件的好东西**：没有可溯源证据 ⇒ 拒绝。但这套纪律**从未给拒绝定价** —— `Abstention.md` 处理的是「什么时候该闭嘴」，却答不了「**闭嘴的代价多大、什么时候拒绝比做错更糟**」。这篇论文第一次给了这个价格。⇒ **缺口不在某句话，而在 `Abstention` 这一格从来只有收益项、没有成本项。** |
| **来源（全部 WebSearch 真实返回）** | `arXiv:2610.34535`（Yusuf, Aditi, Mazed；**2026-10-25 提交**，距今 **6 天，本期最新**）`[verified]` https://arxiv.org/abs/2610.34535 · https://arxiv.org/pdf/2610.34535 · https://doi.org/10.48550/arXiv.2610.34535 |
| **关键实测数字** | 3 个前沿模型 × 3 种防御 × **840 集**；**refuse-more 谨慎把两个模型的过度拒绝推到 100%**，而攻击成功率最多只变 **3.7 个百分点**，且**在所有模型上造成伤害都是最差的**；其 trust-gating 包装器支配整个前沿（每个模型伤害最低、过度拒绝 ≤ 基线、拦截率更高）。形式化：**朴素谨慎在「拒绝掉的真情求数 > 它避免掉的攻击伤害」时被伤害支配**；并证明**定向 trust gate 在干净输入上零过度拒绝**。另有一条方法论警告：**供应商内容过滤器会静默承担一部分防御，必须单独报告。** |
| **边界辨析要点** | vs **`Abstention`**（本库）：「该闭嘴」是**纪律**，「闭嘴值不值」是**代价** —— 前者是必要条件，后者才让它可部署；两者不是替代关系，是**给同一条纪律补上了收益的对立面**。<br>vs **`HumanInTheLoop`**：HITL 把成本算成**延迟与 automation / override / escape 率**；过度拒绝是这条链的**上游版本** —— 连人都不被通知到，因为闸门在走到 escape 那一环之前就先把请求丢了。<br>vs **`ToolHallucination`**（横向对照）：那边管「调用了不存在的工具」，这边管「**该调用的工具没调用**」—— 同一个 `resolve → authorize → gate → execute` 链条上的**反向失效**。<br>⚠️ **证据分级必须写清**：公共安全部署 + 真实调度电话转录为主要情景，**数字不可外推到一般工务 agent**；它引的是方向与定理，不是普适效应量。 |

### 候选 10-31B ⭐⭐⭐ · 权限修订的可消耗性 —— 安全与工作流保全是两回事

| 项 | 内容 |
|---|---|
| **概念名** | 权限修订的可消耗性 / 授权预算会先到先用 · **Consumable Authority & Workflow Preservation in Permission Revision** |
| **一句话定义** | 授权是**可消耗的**：一次调用先花掉额定耗费后，后面的调用就没得花了。因此**即便是扩权**也可能打断一条合法的工作流 —— **安全性（safety）与工作流保全（workflow preservation）是两个可分离的属性**。 |
| **为什么当下最有价值** | 正面填 `overview.md` 白纸黑字写成 **unwritten** 的那一格：*「what remains **unwritten** is a concrete cross-agent policy language or product」* —— 它不但是策略语言，还带 Lean 证明核，且 v2 修订就在 **2026-10-15**（16 天前）。⇒ 更深的缺口在于：本库 `AgentIdentity` 的 **per-hop attenuation** 只讲「子 agent 拿到的凭据只能更险」，**讲的是空间上的险化，从来没讲时间上的修订** —— 权限**随版本变化**这件事在本库里是空白。 |
| **来源（全部 WebSearch 真实返回）** | `arXiv:2608.22868v2`（Shivakumar, Priya, Gao；v1 **2026-08-24**，v2 **2026-10-15 修订**，本期打开的是 v2）`[verified]` https://arxiv.org/abs/2608.22868 · https://arxiv.org/pdf/2608.22868 · https://doi.org/10.48550/arXiv.2608.22868 |
| **关键实测数字** | 51 条人工构造的权限修订：检查**认证了全部 21 条确实保全了客户的**（workflow-preserving），**30 条未保全的一条都没误认证**，且每一个丢掉的工作流都由 replay 确认。另认证了某开源 agent 应用中**一次真实的配额上调**。反例板块：**某消息投递应用中上调发送配额保全了每一个客户，却允许了第二次已批准的发送** ⇒ **保全不意味着安全**（两属性真的可分）。 |
| **边界辨析要点** | vs **`AgentIdentity`**（本库）：本库管的是**一次性签发**时的收窄（scope / magnitude / validity / depth 只能变窄）；它管的是**跨版本修订**的后果。**两者相交但不可约** —— 本库回答「这一跳能不能这么给」，它回答「我明天把额度调高了，昨天能跑通的流程还跑不跑得通」。<br>vs **`ToolHallucination`** 的封闭世界消解：那道消解rung 只检查「这个工具存在吗」，而且是**单次单请求**的；如果配额在第 1 次调用就被花完，**第 5 次「存在且已授权」的调用依然救不回来** —— 单位是**整本 ledger**，不是单次请求。<br>⚠️ **作者的假设必须一起引**：假定串行调用、两种政策下服务结果相同、且信任 Python 翻译层。三条破坏任何一条，证明不成立。 |

      2026-10-25 ★最新      2026-09-28                   2026-10-15 v2

**三条不合并的理由**（承 10-29 / 10-30 的同名教训）：三件事的**被测量对象**完全不同 —— A 测的是**一次拒绝的代价**，B 测的是**一次权限修订的后果**，C 测的是**一条记忆对某个观察者的可见性**。若按一件结清，另外两件会在台账里永久消失。

**与上期（10-30）三条的关系**：10-30 三条的测量对象是 memories / 上下文 / 记录间关系 —— **是「测得准不准」**；本期三条的测量对象是拒绝 / 权限 / 可见性 —— **是「给不给做」**。
⇒ 判别规则延续并升级：**先问「它是新主张还是新仪器」，再问「它管的是质量轴还是许可轴」** —— 两期刚好各占一轴，互不重复。
