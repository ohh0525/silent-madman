### 经验/坑（有长期价值的记法）
- **「缺的不是零件，是容器」**：这一期的缺口不是「还有哪些概念没写」，而是**库里的机制页全都悬空在一个未被命名的宿主之下**。可复用方法：把库里所有页面问一遍「**这个机制跑在什么东西里面？那个东西本身有页吗？**」—— 比穷举概念名更容易找到结构性空洞。09-24 记的「把隐含定值逐条问『这真是定值吗』」与本条是同一族方法（都在问**未被命名的前提**）。
- **同名候选的第二次「承接强化」要写清证据的"性质"变化，而不是"数量"变化**：沙箱 09-21 只是一句 Open Question、09-25 是两家厂商的产品、09-26 是**被收进 Kubernetes 上游 + 被开源 + 被商业化**。三天的信息来源完全不同，第三天的变化是**类别**级的（产品 → 原语/标准）。报告里明确说「非重复推荐」，BACKLOG 只改该行备注。**这条规则值得固化：承接强化必须指出「变化的是性质、不是热度」。**
- **厂商自报数字的处理又出现一次**：OpenAI Agents API 的早期数字（延迟 1/4、成本 −60%、失败 −86%、评分 0.71→0.85）是**厂商与其设计伙伴自报**，不是独立基准；但同期的**默认值**（出网默认 `enabled`、`restricted` 只收 1–100 个精确主机名、密钥注入仍暴露给 agent 生成的代码）是**文档事实**。**处理方式：把「自报性能」与「文档默认值」分栏，后者才是可引用的。**
- **一篇论文的反例比它的正例更有教学价值**：多智能体那条的核心不是「k 个组队能追平 33 个单干」，而是同页写的「**没有验证器或算力紧张时，独立 agent 反而更好**」。**写材料时应把「但」字放在标题里**——只抄正例会把一个有边界条件的结论讲成万灵药。
- **"事故解剖"是概念页最好的动机段**：沙箱那条最有力的素材不是任何产品发布，而是 Hugging Face 那份 07 月复盘 —— agent 的 SSRF 被白名单拒绝后**没有停下而是改道**，最终泄露 pod secrets。一句可迁移的结论：**「拒绝了一条路径的单层防御，并没有关掉那个面」**。以后写任何「门控/防御」类概念，优先找这种**「失败了一次然后成功」**的案例，它比成功案例更能解释为什么需要这一层。
