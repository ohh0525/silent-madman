Agent Harness（智能体外壳）

「Agent = Model + Harness」的后半截 —— 2026 年 9 月，这层壳从「每个团队自己写一遍」变成了可以购买的基础设施 · 生成时间 2026-09-26

1 · 一句话定义

Agent Harness 是把「一次模型调用」变成「一个能干活的 agent」的那层工程外壳：组装提示词、检索并注入工具定义、执行工具、在上下文窗口将满时决定丢什么、崩溃后从哪里续起、把子智能体调度起来——它不是模型，也不是你的业务逻辑，而是模型与真实世界之间的那段循环代码。

2 · 个人解释

想象一支 F1 车队。车手（模型）天赋异禀，但比赛从来不是车手一个人跑完的：得有人造赛车、决定什么时候进站换胎、盯着遥测防止爆缸、出了事故把它拖回来修好再上场。车手决定「怎么开」；车队决定「这场比赛能不能被跑完」。

agent 也一样。你在 agent.html 里学过那个朴素的循环——观察 → 思考 → 行动 → 再观察——但那是循环的语义。总得有一段代码真的去跑这个循环：每轮把系统提示词和工具清单拼进上下文、把模型吐出的工具调用真的执行掉、把结果塞回历史、判断该停还是该继续；窗口快满时决定摘要掉哪一段；进程崩了从哪一步续起；任务太大时拆给几个子智能体分头跑。这段代码就是 harness。所以工程圈有个流传很广的拆法：Agent = Model + Harness。

为什么「当下」值得单独学它？因为 2026 年 9 月，这层壳本身变成了商品。OpenAI 在 09-10 把支撑 Codex 的那套 harness 开成了 Agents API 公测——你交「任务 + 模型 + 工具 + 环境」，它负责跑循环、自动压缩上下文、协调子智能体、把会话保活好几天；Anthropic 同一周用 Opus 5.5 打「托管编排」，builder 圈的反响是「别再过度优化了，让模型自己编排自己，又便宜又够用」。行业通讯 Agent Brief 直接把这一周命名为「Harness Wars（外壳战争）」，并给出定性：编排本身正在变成受管基础设施。

对你个人还有一层意义：你库里的那些机制页——压缩、工具幻觉、技能、上下文工程——其实都是 harness 内部的零件，只是那个「壳」一直没有被单独写出来。这一页补的就是那个壳。

3 · 核心机制

一个 harness 在每轮循环里大致做四件事，缺一件，agent 就从「能用」退回「演示」：

  1. 组装上下文：把系统提示词、工具定义、对话历史拼进本轮请求；现代 harness 用「工具检索」（tool search）按需取工具定义，而不是每轮把全部 schema 塞满窗口。
    为什么重要：窗口是稀缺资源，模型只能看见被放进去的东西——放什么、放多少，直接决定 agent 的视野与成本。
  2. 跑循环并判停：发请求 → 解析工具调用 → 执行 → 把观察结果回填历史 → 判断「完成 / 继续 / 放弃」。
    为什么重要：「自主」的全部含义就是这段循环；而没有终止条件的循环，就是一个无限烧钱的循环。
  3. 治理窗口：临近上下文上限时，自动把早先的上下文摘要压缩（automatic compaction），让任务跨越多个窗口继续，而不是在窗口边界上断掉。
    为什么重要：长任务的瓶颈从来不是模型智力，而是窗口大小——谁决定「满了丢什么」，谁就握着长任务的质量。
  4. 韧性与扩展：会话保活与崩溃恢复（真实任务以天计，单进程循环撑不住）；子智能体调度（harness 自己提供 create / message / wait / interrupt 四个工具，一个开关加并发上限即可打开）。
    为什么重要：这四件事加起来，就是「demo 能跑」和「生产能用」之间的全部距离。

4 · 应用场景

场景 1 · OpenAI Agents API：把 Codex 的壳租给你（2026-09-10 公测）

背景：小团队想做能连续跑几天的深度任务 agent，自己维护循环、压缩、恢复既费人又容易坏。

如何应用：创建 Agent（模型 + 指令 + 工具 + MCP server）与 Session；执行环境三选一（openai_hosted / self_hosted / none，不选环境就没有沙箱和文件系统，但循环与远程 MCP 工具照跑）；三个主力特性 automatic compaction / tool search / programmatic tool calling 开箱即用；子智能体用一个 flag 加 max_concurrent_subagents 打开。

结果：你不再写压缩逻辑、恢复逻辑、调度逻辑，只为 token 与工具付费；会话可保活数天，写到 /workspace/outputs 的产物自动发布为 artifact。

场景 2 · 上生产前先读默认值：托管不等于安全

背景：团队打算给 agent 挂上生产凭据，整体交给托管 harness。

如何应用：把「逐条核对默认值」当作上线检查单第一项——宿主沙箱出网 network.access 默认 enabled；收紧到 restricted 只接受 1–100 个精确主机名（不支持通配符、协议、路径、端口，子域与重定向目标都要单列）；文档明说「Agent 生成的代码可以访问其环境可用的文件、凭据与网络」，注入的密钥仍会暴露给 agent 代码，要改用 vault；并确认补丁节奏——同周披露的 Codex 沙箱逃逸 Heapjack / Overpatch 修复于 Desktop build 26.818.21641 与 CLI 0.149.0。

结果：认识到「托管 harness 不消除沙箱风险，只是把修补责任集中到厂商的发版节奏上」——安全工作从「我自己修」变成「我盯着厂商修、每版核对默认值」。

场景 3 · 自建还是托管：编排复杂度的去留

背景：一个步骤无法预先穷举的数据清洗 agent，团队在「用框架自己拼 harness」与「买托管」之间摇摆。

如何应用：按三条判据取舍——任务时长（以小时/天计 → 托管的保活与恢复更值钱）；合规边界（该公测仅美国数据驻留、不支持零数据保留 ZDR → 强监管负载先别上）；循环特殊性（毫秒级 SLA 或循环本身就是核心竞争力 → 自建）。同时留意 Anthropic 用 Opus 5.5（$4/$20 每百万 token，缓存读降 60% 至 $0.20）把「模型编排模型」打到很便宜，builder 圈的教训是「别在壳里过度工程，让模型自己编排往往又便宜又够用」。

结果：「谁跑循环」从应用代码里挪出去，团队只保留业务判断与验收——但托管约束（地域、数据驻留）成为新的采购条件。

5 · 边界辨析

5.1 不是什么

  • 不是 Agent 本身：agent.html 讲的是循环的语义（推理 → 选工具 → 执行 → 观察）；harness 是这段循环的具体实现——谁拼 prompt、谁管工具表、谁做压缩、谁管恢复。语义回答「agent 是什么」，壳回答「它靠什么跑起来」。
  • 不是任何一个机制页，而是装它们的容器：压缩（满了丢什么）、工具幻觉消解（调用先核对存在性）、Skill（知识按需加载）、上下文工程（每步放什么的原则）都是壳内的零件；harness 决定的是「何时调用哪个零件、用什么阈值」。一个佐证：OpenAI 这次主打的三个卖点——automatic compaction、tool search、子智能体——恰好就是你已经学过的概念。
  • 不是上下文工程：上下文工程是一套原则（每一步该往窗口里放什么）；harness 是执行这套原则的那个程序。原则可以写在纸上，壳必须跑在机器上。
  • 不是沙箱：harness 决定「谁编排」，沙箱决定「在哪跑、能碰到什么」。OpenAI 把两者显式拆成 Agent 与 Environment 两个对象——壳可以插在不同的执行环境上，环境也不非得配壳。

5.2 常见误解

  • 「不用框架就没有 harness」——不对。哪怕你手写 50 行 while 循环，那也是 harness，只是零件不全、没人替你运维。问题从来不是「有没有」，而是「零件谁补、漏洞谁修」。
  • 「交给托管就安全了」——默认值就是安全边界，而这套默认值是宽松的：出网默认开、注入的密钥仍暴露、逃逸补丁跟着厂商节奏走。托管改变的是责任分配，不是风险总量。
  • 「厂商给的效率数字可以当基准引用」——延迟约 1/4、单任务成本 −60%、失败响应 −86%、某客户评测 0.71 → 0.85，这些是 OpenAI 及其设计伙伴的自报数字，引用前必须打折扣并标注来源性质。

5.3 适用与不适用

适合托管 harness适合自己写壳
长时任务（小时 / 天级），需要保活与恢复毫秒级 SLA 的高频路径
多子智能体协作，不想自研调度强合规 / 零数据保留（ZDR）要求
团队小，想省掉循环 / 压缩 / 恢复的运维循环本身高度定制、构成核心竞争力
落手顺序建议：①先问「我的循环里现在缺哪个零件」（多数团队缺的是压缩与判停，不是更聪明的模型）；②若选托管，把「逐条读默认值」当作上线检查单第一项；③把沙箱选择与壳选择分开决策（OpenAI 已把两者拆成两个对象，你也应该拆）。
