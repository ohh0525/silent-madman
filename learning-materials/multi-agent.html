多智能体协作的工程化（Multi-Agent Orchestration）

k 个通气的 agent 能追平几十个单干的 —— 但前提是有可验证的进度；2026 年 9 月，「多智能体」第一次同时拿到可复现的实验结论与产品级的编排入口 · 生成时间 2026-09-26

1 · 一句话定义

多智能体协作是让多个各自拥有独立上下文窗口的 agent 围绕同一目标工作：通过共享工作区交换已验证的部分结果、失败路径与中间得分，用更少的总算力拿到比「大量独立采样取最好」更好的结果——前提是存在可验证的进度；没有验证器或算力紧张时，通信的开销会盖过收益，独立 agent 反而更好。

2 · 个人解释

想象 solving 一道很难的谜题，你有两种花预算的方式。方式一：33 个人各自关在房间里独立解题，最后取最好的一份（best@33）。方式二：5 个人坐在同一间工作室里，谁验证出一条走得通的路就喊出来，其他人立刻从那里继续，走过的死胡同也贴在墙上不再重试（team@5）。2026 年 9 月微软研究院与 UC Berkeley 的实验结论是：方式二追平方式一——5 个通气的 ≈ 33 个单干的，相当于 6.6 倍的独立算力。

为什么通气这么值钱？因为 agent 之间交换的不是闲聊，而是「已验证的突破」：一个人确认「这扇门后面有路」，其他人就不用再试那扇门和它旁边的一排死门。收益全部来自「建立在别人已确认的进展之上」——这不是分工（没有预设角色），也不是中央调度（没有指挥官），就是一张共享的白板。

但这份材料最想让你记住的是那个「但」字。同一篇论文明确给出反例：在没有验证器（无法判断谁真的进展了）或算力紧张（等别人验证太贵）时，通信带来的开销会盖过收益，独立 agent 反而更好。通信不是免费的——它需要「可验证的进度」作锚。没有这个锚，共享白板会退化成谣言板：一个人的错误结论被其他人当作已验证的前提继承下去。这就是多智能体独有的新失效面：互相污染。

为什么「当下」学它？因为这一周它凑齐了三种证据：论文（可复现的 team@k vs best@k 对比）、产品（Anthropic 把「协调者 → 并行线程 → 共享记忆」搬进 Claude Code Projects）、规模（微软 Agensh 在没有中央编排者的前提下扩到 1,024 个 agent）。问题已经从「多智能体能不能」变成「什么条件下值得、谁来承担协调成本」。

3 · 核心机制

  1. 交换的对象是「已验证的进度」，不是消息：k 个同目标、同算力预算的 agent 通过共享工作区交换部分结果、失败路径与代码；没有预设角色、没有中央编排者。
    为什么重要：这划清了它与「工作流编排」的界限——收益不来自流程设计，来自增量被验证后即可复用。
  2. 验证器是收益的前提条件：只有当「谁真的进展了」可以被便宜地判定时，「建立在别人进展之上」才成立。LP85 任务上 64 次独立尝试全部失败、team@5 却解出 65%，靠的正是进度可验证。
    为什么重要：它把「要不要上多智能体」从品味问题变成工程判据——先问任务有没有验证器，再问要不要组队。
  3. 反例与正例同在，边界即结论：ARC-AGI-3 上 team@3 追平 best@13、team@5 追平 best@33；polyomino packing 被 team@3 刷到 SOTA 0.945；但论文摘要同时写明方法「fails without verifier or low compute」。
    为什么重要：引用多智能体收益时必须连同它的边界条件一起引用，否则就是把有条件的结论讲成万灵药。
  4. 新失效面：互相污染：一个 agent 的未验证结论被同伴当作前提继承——这是单 agent 世界不存在的失败模式，而且恰好打在你已学的 [[Provenance]]（来源溯源）概念的延长线上。
    为什么重要：多智能体系统里的「信任」不只要管事实来源，还要管同伴结论的验证状态；共享记忆要当「可检视的工作上下文」，不能当权威真源。

4 · 应用场景

场景 1 · 难题攻坚：用 team@k 替代暴力采样

背景：一类任务的解可以通过程序自动判定对错（ARC-AGI-3 网格世界、LP85、polyomino packing、MNIST 分类器压缩）——天然自带验证器。

如何应用：把同一目标与同一算力预算发给 k 个 agent，共享一个工作区，让它们交换已验证的部分解与失败路径。实验结果：ARC-AGI-3 上 team@5 ≈ best@33（6.6× 等效算力）；LP85 上独立 64 次全败而 team@5 解出 65%；FT09 解出率约 26% → 90%；polyomino packing 0.894 → 0.945 创 SOTA；4-agent 团队写出仅 1,957 字节、99.4% 准确率的 MNIST 分类器，比人类最优还小 20%。

结果：在自带验证器的任务上，「通气的小团队」对「单干的大队伍」形成算力倍率优势——前提写进边界条件：无验证器或算力紧张时不要用。

场景 2 · 工程落地：Claude Code Projects 的协调者模式（beta 2026-09-17）

背景：一个工程目标（迁移、重构、多模块改造）单线程 agent 要跑很久，且上下文装不下整个仓库。

如何应用：一个 coordinator 会话把目标拆成并行线程——每条线程是一整个独立的云端 Claude Code 会话，自带分支与仓库副本，能跑测试、开 PR、还能再开子 agent；线程间共享项目记忆与资料库，让「改过的发布日、砍掉的功能」这类决定跨会话存续；重叠改动按普通 merge conflict 处理，不静默合并。同时接受它自陈的边界：线程各自消耗订阅配额（并行不免费）；launch 阶段线程只跑在云端；共享记忆是「可检视的工作上下文」而非权威真源；CI / 测试 / 人工评审仍是集成边界——即便协调者报告「全部完成」。

结果：多智能体从「实验设置」变成「产品里一个按需打开的模式」；协调成本从自研框架变成厂商托管，但验证与合并的最终责任仍在人。

场景 3 · 规模化：去掉中央编排者（微软 Agensh）

背景：中央协调者本身会成为规模瓶颈——1,000+ agent 时单点调度不可扩展。

如何应用：Agensh（微软研究院 Furu Wei 团队）用「共享工作区 + 消息接口 + 可复用发现的共享上下文」替代中央编排者，agent 异步自组织协作；在 pandoc 上把 agent 数从 1 扩到 1,024，通过率 33.89% → 55.06%；ProgramBench 最难五项在 1 → 128 agent 时平均通过率 19.31% → 28.78%。

结果：去中心化路线的规模证据（注：数字来自二手报道，未见一手发布；作方向与量级参考）。

5 · 边界辨析

5.1 不是什么

  • 不是子智能体（subagent）：子智能体是单 agent 内部开出的辅助线程（干完活把摘要交回主上下文）；多智能体是对等的团队，成员各自持有完整目标与独立窗口。Claude Code Projects 恰好把两者接起来：线程是团队，线程内部还能再开子 agent。
  • 不是共享记忆系统：长期记忆是单个 agent 跨会话的持久化（时间维度）；多智能体是多个 agent 同一时刻的共享状态（空间维度）。两者互补：团队共享的记忆怎么治理，正是两者交界处的开放问题。
  • 不是上下文工程的替代：上下文工程管单窗口内放什么；多智能体管多窗口间换什么。后者可以看作前者在跨窗口维度上的延伸——子 agent「干净窗口、只回 1–2k 高密度 token」正是这条路的缩影。
  • 不是「更多 agent 总是更好」：论文自带反例——无验证器或算力紧张时独立更好；产品自带成本——线程各自烧配额。多智能体是一个有边界条件的工具，不是免费午餐。

5.2 常见误解

  • 「多智能体 = 给每个 agent 分配一个角色」——实验里恰恰没有预设角色。收益来自「已验证进度的复用」，不是角色扮演的分工剧本。
  • 「组了队就该共享一切」——未验证的结论会被同伴当作前提继承（互相污染）。共享的对象要区分「已验证 ✅」与「推测」，这正是 [[Provenance]] 思想在多智能体里的延伸。
  • 「协调者说完成了就是完成了」——Claude Projects 自己写明：CI / 测试 / 人工评审仍是集成边界，「所有线程已完成」不是「集成正确」。

5.3 适用与不适用

值得组队先别组队
任务有便宜的验证器（测试、可执行判定、编译通过）没有验证器、进度无法判定
失败路径多且昂贵（别人试过错能省你大量算力）算力紧张、单次尝试很便宜
目标可拆成并行分支、冲突面可控强串行依赖、冲突面大（merge 成本吞掉并行收益）
落手顺序建议：①先找验证器——没有它，后面全部免谈；②从 k=2–5 的小团队开始，别上来就 1,024；③把「已验证 ✅ / 推测」的状态显式写进共享工作区，防互相污染；④预算按「线程各自计费」估算，别按「一个 agent 乘 N」低估；⑤集成边界（CI / 测试 / 人审）留在团队之外。
