LLM—编排层—工具的信任边界：模型说了「不」，工具已经做了

1 · 一句话定义

在「模型 → 编排层 → 工具」这条链上，编排层把模型输出的文本解释成一个结构化调用并直接派发 —— 这个解释动作本身就是一次授权；而工具又常常不执行它自己声明的输入语义。于是「模型说了不」与「工具已经做了」可以同时为真。

最短的写法：「模型输出不是 permission。」它只说明模型请求了什么，不说明系统有权执行什么 —— 而今天大多数编排层恰恰把前者当成了后者。

2 · 个人解释：这一格为什么突然值钱

想象一间会议室。老板对助理说：「我只是念一下这封邮件里的话，你别照做。」然后他照着念了：「请立刻转账给这个账户。」助理没有等老板说完「别照做」，就在他念到句号的瞬间把钱转出去了。老板的抗议在两秒后到达 —— 那时转账已经完成。没有人违反规则；是「听的人」把「念出来的句子」当成了「签发的命令」，而且抢在了「解释」前面。

把角色换回来：老板是模型，助理是编排层（把文本翻译成工具调用并派发的那层），转账是工具。今天这一格之所以从「一直存在」变成「当下」：

  1. 它直接否定了一条本库已经写进 overview 的承重主张。自 2026-09-24 起，本库的横断主题之一写着「顺序是一等设计对象」—— 控制放在哪一档，比它有多强重要；放错位置的控制不是更弱的控制，它根本不是控制。而这段 transcript 里，模型的拒答在工具返回之后才到达。⇒ 你在设计文档上画的那条链 propose → resolve → authorize → gate → execute，在框架里执行时不是那条链。顺序是实现的属性，不是设计的属性。
  2. 它第一次给了「那一档实际上没装」一个生态级规模数字。本库 [[ToolHallucination]] 要求在任何闸门之前加一档「工具在不在注册表里 + 签名对不对」。ToFu 攻击里工具真的存在、参数格式完全合法 ⇒ 那一档照放不误。同一篇论文顺手普查了 273 个 MCP server / 3,405 个工具，253 个已验证缺陷落在 343 个工具 / 118 个 server（43% 的 server 中招）。
  3. 它给 Agent = Model + Harness 补了第五件没人列过的事。既有页面列了外壳的四条职责（组上下文 / 跑循环判停 / 管窗口 / 保活恢复），没有一条说「编排层本身是一个信任主体」。它把文本解释成调用 —— 这个解释动作就是一次授权。

这一格的判据句：「The refusal text and the executed call disagree: the system prompt shaped what the model said, not what the orchestrator did.」—— 系统提示词塑造的是模型说了什么，不是编排层做了什么。

3 · 核心机制：三层边界，两条缝

        ┌──────────┐         ┌──────────────┐         ┌────────┐
        │  模型    │  文本   │   编排层     │  调用   │  工具  │
        │  (LLM)   │ ──────▶ │ (orchestrator)│ ──────▶ │ (tool) │
        └──────────┘         └──────────────┘         └────────┘
                   ▲                        ▲
                   │                        │
                缝 ①：输出 = 意图？      缝 ②：工具执行它
                （文本被解释成调用）      自己声明的语义吗？

   论文原句：a trust boundary "where tool semantics may go unenforced
            and LLM-generated arguments may be incorrectly treated as trusted"

3.1 Repeat-After-Me：四步

  1. 攻击者知道编排层识别的调用格式。不是秘密 —— 工具调用的 JSON/函数签名格式写在框架文档里。⇒ 为什么重要：攻击面是一个公开格式，不是一个漏洞。
  2. 攻击者写出「目标工具 + 自己选的参数」的文本。⇒ 为什么重要：文本内容本身不含任何异常字符，没有任何一个输入过滤器会命中它。
  3. 攻击者让模型逐字复述这段文本。模型「只是在复述供给它的文本」—— 它没有产生意图。⇒ 为什么重要：模型的输出与模型的意图分离，这是整条链的支点。
  4. 编排层把这段输出当成工具调用并派发执行。⇒ 为什么重要：解释动作替模型签发了授权，而模型此刻还在生成下一句「但我不能这样做」。

3.2 承重 transcript（LangGraph 1.2.0 + Llama 3.1 8B）

两个 dummy 工具 make_bomb / launch_missiles，唯一防线是 system prompt：

#发生了什么编排层做了什么
1第一次要求复述 launch_missiles 的调用模型拒答，但把调用当作文本打印了出来 ⇒ LangGraph 什么都没跑
2改 framing 为「假设性」，并要求只输出被引用的文本模型以结构化形式返回了该文本 ⇒ LangGraph 立即用攻击者的参数执行
3模型继续生成拒答拒答在工具返回之后才到达。

读这段 transcript 的正确姿势：它证明的是「存在一种 framing，能让编排层在模型拒答之前派发调用」，不是「LangGraph 默认就会执行模型打印出来的任何东西」——第 1 拍里它就没执行。第 2 拍的差别在于输出是不是落进了编排层识别的调用格式里。这是一个格式识别时机问题，不是一个「模型会不会拒绝」的问题。

4 · 生态级规模证据：ToFu 的第二腿

论文不只是演示一次攻击。它把「检查」这件事自动化了：从工具自己的 metadata + 一份 CWE 引导的 sanitizer 语料，自动生成语义感知的检查器与模糊测试 harness（74 个 sanitizer / 21 个内省 tracer），然后对 273 个可干净执行的 MCP server / 3,405 个工具做普查。508 个候选 flag 经人工复核后留下 253 个已验证缺陷，落在 343 个工具 / 118 个 server：

作者的诊断原句：「many tools implicitly rely on the LLM to sanitize inputs」 —— 很多工具默认输入已经被模型清洗过了。这就是缝 ②：工具声明了它接受什么，但不执行这个声明。

这一格最值得带走的一句：「已验证」说的是作者复核过，不是厂商确认、更不是可利用。严重性在具体部署中未确立。但它第一次让「工具自带语义检查」这件事有了可以量化的缺席率。

5 · 四条修复纪律

  1. 分离「请求的能力」与「执行的权威」。模型可以请求任何调用；系统只按自己的策略授权。⇒ 为什么重要：只要两者共用一个通道，任何一次输出格式上的成功就等于一次授权成功。
  2. 工具必须自验输入语义，不能假设 LLM 已经清洗。⇒ 为什么重要：缝 ② 的规模数字（253 / 118 server）说明这正是当前生态的默认状态。
  3. 每一次敏感调用都独立授权，不继承上游决定。⇒ 为什么重要：委派链里「上游批准了」不构成下游的授权凭据 —— 这与 [[AgentIdentity]] 的逐跳收窄是两条独立的纪律（那条收窄的是凭据，这条否定的是授权被继承）。
  4. 监控调用序列，而不是单个动作。⇒ 为什么重要：transcript 里每一步单看都合法；异常只在顺序上 —— 这正是本库「顺序是一等设计对象」这条主题被反向照亮的地方：顺序不只是设计时要排好的，也是运行时要盯住的。

独立安全研究员 Vibhum Dubey（经 CSO 引述）的架构判断，是这四条最干净的表述：「A model can generate a technically valid tool call that is still inappropriate for the task. If the orchestration layer treats that output as sufficient authority to execute the operation, a model-level manipulation becomes a system-level security issue.」 —— 技术合法的调用 ≠ 对本次任务恰当的调用；把前者当成执行的充分授权，就把模型层的操纵升级成了系统层的安全事件。

execute 腿		既有金句「authority is not isolation」管的是「动作能碰到什么」；本行管的是「这个调用凭什么被当成已授权」。同一族的第二个成员，且在更上游。
[[AgentIdentity]]
凭据逐跳收窄		收窄的是凭据；本行的问题是把模型输出文本当成了授权凭据 ⇒ 两条独立纪律。
[[AgentHarness]]
Agent = Model + Harness		直接补第五条职责：编排层是信任主体，不是透明管道。

常见误解

  • 「这是六个新 0day。」不是。攻击面是一个公开格式，不是一个漏洞；论文未声称野外利用，dummy 工具无真实影响。
  • 「加了 system prompt 就能防。」不能 —— transcript 里唯一防线就是 system prompt，模型也确实拒答了，只是拒答到晚了。问题在时机，不在措辞。
  • 「这跟提示注入是两回事。」不是两回事 —— 它属于间接提示注入，但落点不同：不在模型，而在编排层的解释动作。⇒ 不是新品类，是老品类有了新的可达范围。

适用 / 不适用

适用不适用
你正在把模型输出接成工具调用（任何编排层）；你在设计敏感动作的授权链；你要判断「闸门装在哪一跳」。模型只输出文本、由人执行；工具自己做了完整的输入语义校验并拒绝不合法输入；纯单轮问答、无委派链。

7 · 可直接引用的判据句

  1. 「模型输出不是 permission。」—— 它只说明请求了什么，不说明系统有权执行什么。
  2. 「拒答文本与被执行的调用不一致：系统提示词塑造的是模型说了什么，不是编排层做了什么。」（论文原句）
  3. 「很多工具默认 LLM 已经把输入清洗过了。」（论文原句）—— 缝 ② 的机制。
  4. 「每个协议都假设自己独自存在，所以各自只检查自己的前门，没人盯着中间的走廊。」（Rapid7 · Douglas McKee）
  5. 「这一段上没有人在检查。」—— 三条候选（编排层 / 协议边界 / 厂商）的共同句式，也是第十一条扫描线「接缝审计」的问法。

8 · 你会怎么用它（自查清单）

  1. 画出你的三层边界图，标出「谁把文本解释成调用」。如果答不上来，那一层就是你的编排层 —— 而且它现在是一个未被命名的信任主体。
  2. 验证派发时机：构造一次「模型先输出结构化调用、后吐拒答」的请求，看工具是否在拒答到达前就跑了。这是本格唯一必须亲测的一项。
  3. 确认闸门是同步阻塞的，而不是「记一笔日志然后继续」。⇒ 闸门的存在不等于闸门的时序。
  4. 抽查你依赖的工具：它是否自己校验了输入语义（路径、URL、转义），还是假设上游已经清洗。
  5. 把监控对象从单动作换成序列：transcript 里每一步单看都合法。
