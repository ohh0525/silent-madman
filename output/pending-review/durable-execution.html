持久化执行：让一场长跑活过崩溃

Durable Execution & the Agent Runtime —— 壳下面那一层负责什么、resume 在四家为什么不是同一个操作、以及“跑得完”与“跑得好”为什么必须分栏 · 生成时间 2026-10-11

1 · 一句话定义

持久化执行，是让一次 agent 运行在被 kill、被部署打断、或被人暂停数天之后，仍能在另一个进程里接着做完的那一层能力——它管的不是“模型聪不聪明”，而是“这场已经跑了 90 分钟的长跑，还剩什么”。它有三个彼此独立、常被混为一谈的问题：存的是什么（检查点 vs 记忆 vs 事件日志）、恢复时怎么重放（四家语义不同），以及副作用被交付了几次（at-least-once / at-most-once / effectively-once）。

2 · 个人解释

想象你把一件复杂工作交给一位助理：整理三百份合同、把每张的关键条款抽出来、做成一张表。他干了两个小时，做到第 90 分钟时——电脑蓝屏了。重开之后你最想知道的其实只有三件事：他做到第几份了、已经发出去的那几封确认邮件会不会再发一遍、以及他重开之后还记不记得自己原本要做什么。

多数 agent 系统在这三件事上是裸奔的。不是因为工程师不努力，而是因为“跑完”这件事此前一直被当成框架的实现细节，而不是一个需要被命名、被分类、被验收的东西。2026 年它终于有了一层名字。LangChain 的判据句把这条界线划得很清楚：造一个好 agent 需要好 harness，而部署一个好 agent 需要好 runtime——“the runtime is everything underneath: durable execution, memory, multi-tenancy, observability”。

为什么这一层的缺席在 2026 年变得致命？因为 agent 的工作时长变了。以前一次调用几秒，崩了重跑就是了；现在的 agent 会被派去“把整个仓库迁到新框架”“跑完一轮跨月对账”，单任务上限已经做到 7 天。一旦任务时长超过“一次进程能活多久”，崩溃就从异常情况变成必然事件——于是“一次没人安排的 kill 之后还剩什么”，从一句运维吐槽变成了选型的第一问。

更麻烦的是，这一层里最容易踩的三个坑，全都是看起来无害的同名事物：检查点不是记忆（一个说“当前任务哪几步已完成”，一个说“下次该怎么回答你”）；会话不是持久化执行（OpenAI Agents SDK 的 Session 是 memory continuity, not durable execution）；而“resume”这个词在 Temporal、DBOS、LangGraph 里指向的是三个不同的操作。把它们当成一件事，就会写出“以为已经恢复、实际把检查点用空列表覆盖掉”的代码——这类事故在实机崩溃对照里已经被复现过：四家框架全都活下来了，但 none of them holds by default。

所以这份材料把这一层拆成四问：谁调度（运行时管什么）、一次没人安排的 kill 之后还剩什么（恢复语义）、存的是什么（检查点 / 记忆 / 日志的边界）、副作用被交付了几次（交付语义）。最后补上一条此前一直没写清的分界：跑得完 ≠ 跑得好。

3 · 核心机制

  1. 先认层：harness 是壳，runtime 是壳下面那一层。工程圈的拆法一句话 —— Agent = Model + Harness；而 2026-04 起行业补上了后半句：把 agent 部署出去还需要 runtime。这一层被拆成四项关注点：durable runs（一次运行有 id、有状态机、可跨进程接管）、lifecycle controls（archive / unarchive / delete 这类生命周期动作及其可逆性）、streaming primitives（断线能从 Last-Event-ID 续传，而不是重来）、versioned APIs（客户端与服务端版本协商，旧 run 不被新代码悄悄改掉语义）。Anthropic 把它写成 “Any Harness instance can pick up any Session and continue from where it left off”；Thoughtworks 2026-04 雷达给的选型规则是“先用框架自带的 durable 支持，工作流变关键了再上独立平台”。
    为什么重要：这四项是可以逐条向厂商提问的验收清单，而不是一句“我们支持断点续跑”。
  2. “resume”在四家不是同一个操作。这是本层最反直觉的一点，也是最容易写错的地方：
    形态代表恢复时做了什么对你的硬约束
    事件溯源 / 全量重放Temporal、Azure Durable Functions、AWS Step Functions、GCP Workflows重放事件历史来重建状态编排函数必须确定性；副作用要用「run + step 身份」构成的稳定键
    持久状态库 / 代码优先Restate、DBOS、InngestDBOS 按持久化位点采纳已完成操作（写 PostgreSQL，无独立服务）；Restate journal 重放；Inngest 步骤记忆化停在外部信号上不耗算力，这是它相对重放派的省钱点
    框架超步检查点MS Agent Framework superstep 检查点按 superstep 粒度恢复粒度由框架定义，跨框架不可迁移
    线程快照LangGraph从被中断节点的开头恢复（含 pending writes）节点必须幂等；且需显式 durability="sync"、resume 传 None，否则空列表会覆盖检查点
    横评那句判据值得单独记下：“The 2026 dividing line is what happens when a two-hour agent run dies at minute 90.”
    为什么重要：同一个“resume”按钮，背后可能是重放、可能是位点采纳、可能是节点重跑——你对幂等性的义务完全不同。
  3. 存的是什么：checkpoint ≠ memory，也 ≠ durable execution。三句话把边界钉死：checkpoint ≠ memory（memory 帮 agent 回答下一个问题；checkpoint 说的是当前任务哪几步已完成）；session ≠ durable execution（OpenAI Agents SDK 的 Session 是 memory continuity，不是持久化执行）；checkpoint ≠ durable execution（检查点保留的是控制状态，不是下游副作用的 exactly-once）。
    为什么重要：把这三样混在一个“记忆库”里，就会得到最常见的生产事故——状态恢复了，但已经发出去的邮件又发了一遍。
  4. 副作用被交付了几次：交付语义三分。
    语义含义代价不对称（为什么这一栏是承重的）
    at-least-once至少一次，可能重复模型调用重复，只是多花 token；退款重复，就是一次客户事故。同一份“至少一次”，落在不同副作用上是两个数量级的代价
    at-most-once至多一次，可能丢失
    effectively-once靠幂等键 + 版本检查凑出恰好一次的效果
    必须同屏的裁决句：“True exactly-once delivery across a process and an external service is not generally possible.” ⇒ effectively-once 是上限，不是可选项；而并发恢复时还须做版本检查，防止两个恢复进程双写覆盖。
    为什么重要：这条把 [[HumanInTheLoop]] 那句“resume 必须幂等”从口号升级成了可验收的判据。
  5. 可靠性 ⊥ 质量：跑得完 ≠ 跑得好。这是本层与评测的分界线，此前一直被混记：
    “A run can finish reliably and still give a poor answer. It can also give an excellent answer once and fail to survive the next deploy. Both problems need measuring.”
    ⇒ 持久化执行（可靠性）与 evals（质量）是两个正交轴，不能互为替代指标。一个 agent 可以次次跑完却每次答错，也可以精彩一次却活不过下一次发版。
  6. 成本侧：检查点该多久打一次。此前所有讨论都停在“谁有哪种恢复语义”，2026-10 才第一次出现把这层开销显式计费的工作：LAM（Language Model Agent Machine，arXiv:2610.02488）固定语义模型、只对 harness 级资源计费，在可靠性一类中给出紧的阶段局部采样界、不完美验证的精确成本，以及 Young–Daly 型检查点定律与闭式最优验证间隔。
    为什么重要：它把问题从“要不要打检查点”推进到“检查点与验证该多久做一次才对得起成本”——频繁打点烧算力，稀疏打点则每次崩溃损失更多重放。

4 · 应用场景

场景 1 · 两小时任务在第 90 分钟被 kill

背景：一个迁移任务跑了 90 分钟，进程被 OOM killer 杀掉；重开后 agent 从零开始，把已经做完的 180 个文件又做了一遍，其中三个是不可逆的写操作。

如何应用：先问恢复语义而不是“有没有断点”：若走事件重放，编排代码必须是确定性的（随机数、时间戳、字典序都要进事件而非现场取）；若走 LangGraph 式节点恢复，每个节点必须幂等，且显式打开 durability="sync"。所有对外副作用统一用 run_id:step_id 稳定键提交，重放时命中即跳过。

结果：崩溃从“重跑一遍并祈祷”变成“从第 181 个文件继续，且已提交的三笔写操作不会被重复提交”。

场景 2 · 一次人工审批要等三天

背景：agent 在一个不可逆的付款动作前停下等人批；审批在 72 小时后才回来——此时最初那个进程早已不存在。

如何应用：这正是 [[HumanInTheLoop]] 反向指认本层的原因：该页要求 “pause must be persisted / resume idempotent”，而实现方在本层——检查点必须连同待批请求本身一起保存，并在恢复后重发。生命周期上要区分 archive（可撤销挂起） 与 delete（不可逆）；停在外部信号上应当是不耗算力的。

结果：“暂停三天”从不可能变成配置项；而归档与删除的语义差异，直接决定了误操作能不能挽回。

场景 3 · 恢复之后，客户收到了两笔退款

背景：状态恢复得很干净，但退款这一步在崩溃前已经提交、恢复后又跑了一次——因为它是外部服务的副作用，不在检查点的管辖范围内。

如何应用：把交付语义显式写进代码：at-least-once / at-most-once / effectively-once 三选一，并接受“跨进程与服务的真正 exactly-once 一般不可能” ⇒ 用幂等键 + 版本检查凑出 effectively-once；并发恢复路径上必须做版本检查防双写覆盖。

结果：判据落地为一句可检查的规则：模型调用重复只是多花 token，退款重复就是一次客户事故——代价不对称决定了哪些步骤必须做幂等、哪些可以偷懒。

5 · 边界辨析

5.1 不是什么

  • 不是 checkpoint（检查点）：检查点保留的是控制状态，不是下游副作用的 exactly-once。恢复成功且副作用重复执行一次，是本层最典型的事故形态。
  • 不是 memory（记忆）：checkpoint ≠ memory。memory 帮 agent 回答下一个问题，checkpoint 说的是当前任务哪几步已完成。两者的写入时机、生命周期、失效判据全都不同。
  • 不是 session（会话）：session ≠ durable execution。OpenAI Agents SDK 的 Session 是 memory continuity，不是持久化执行。会话可见不等于崩溃可恢复。
  • 不是 harness（外壳）：上下层关系。harness 是跑循环的那个壳，runtime 是壳下面那一层——LangChain 的原话是“造要 harness，部署要 runtime”。
  • 不是 evals（评测）：跑得完 ≠ 跑得好。一次运行可以可靠地跑完却给出糟糕答案，也可以给出一次精彩答案却活不过下一次部署——两者都要测，是两个正交轴。
  • 不是沙箱：本层管“状态能不能恢复”，沙箱管“做了也只碰得到这么多”。一个是时间维度的韧性，一个是空间维度的隔离。

5.2 常见误解

  • 「框架默认就是持久化的」——实机崩溃对照的结论是 none of them holds by default：LangGraph 需显式 durability="sync" 且 resume 传 None，否则空列表会覆盖检查点。
  • 「exactly-once 可以买到」——跨进程与外部服务的真正 exactly-once 一般不可能；能做到的是靠幂等键与版本检查凑出的 effectively-once。
  • 「有了持久化就等于可靠」——可靠性与质量正交；跑得完的系统同样可以稳定地给出错误答案。
  • 「resume 就是 resume」——四家是四个不同的操作（重放 / 位点采纳 / 超步检查点 / 节点快照），对幂等性的要求完全不同。
  • 「已 GA 的产品就是安全边界」——MXC 官方警告其 SDK 生成的策略在某些地方过于宽松；已 GA ≠ 已是边界。

5.3 适用与不适用

值得上持久化执行这一整套不必上这套复杂度
单任务时长超过一次进程寿命（分钟级→天级）秒级、一次调用完成的问答
存在不可逆副作用（付款 / 发信 / 下单）纯只读、重跑无害
中间要等人审批，且等待跨越进程生命周期全程无人介入、同步返回
崩溃重跑的代价高于维护检查点的代价重跑成本低于一次存储写入
需要多客户端 / 多实例接管同一 run单进程、单客户端

7 · 一句话回顾

持久化执行管的不是“模型聪不聪明”，而是“这场已经跑了 90 分钟的长跑，在一次没人安排的 kill 之后还剩什么”——要回答它，得分清三件事：存的是检查点、记忆还是事件日志；resume 在你的框架里是重放、位点采纳还是节点重跑；以及那个不可逆的副作用，究竟被交付了几次。而最后一问必须与评测分栏：跑得完不等于跑得好，两者都要测。
