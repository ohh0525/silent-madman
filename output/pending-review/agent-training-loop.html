训练—部署错配：你优化的那个 agent，是部署的那个吗？

Train–Deploy Mismatch & Harnessed Agentic RL —— 重写版 vs 部署版逐项对照 × 被抽掉的约束清单 × 代理层怎么接 · 生成时间 2026-10-11

1 · 一句话定义

训练—部署错配，指的是训练回路里的那个 agent 与真正上线的那个 agent 不是同一个东西：为了接入训练框架，交互循环被重写了一遍，而重写时顺手丢掉的那些工程细节（超时兜底、脏数据清洗、system prompt 拼接顺序、历史压缩长度）恰恰是定义任务难度的约束本身。于是模型学到的是一个被移除约束后的环境里的最优解——这不是 reward hacking，是环境错配；而错配的代价，通常被记在「模型泛化不行」的账上。修法不是调奖励，而是让部署用的那个 harness 原样参加训练。

2 · 个人解释

设想你要训练一位厨师。你在训练场里给他搭了一个厨房：食材永远新鲜、灶火从不熄、订单一条一条来、没有客人催。他在这个厨房里练得极好，出餐速度快、味道稳定。然后你把他送进真实餐厅——食材偶尔不新鲜、高峰期三个锅同时糊、订单会插队、客人会改单。他表现崩了。你会怎么归因？

大多数团队的归因是「他泛化能力不行」。但真正的问题在更早的地方：你训练他的那个厨房，和他要工作的那个厨房，不是同一个厨房。你不是在训练他，你是在训练一个活在简化世界里的他。

agent 训练里这件事更隐蔽，因为那个厨房不是别人搭的，是你自己重写一遍搭出来的。主流 RL 框架（verl / AReaL / slime）要接管交互循环才能发 rollout，于是每换一个 agent，就要在训练框架里重新实现一遍它的循环。而重写时，那些「不算核心逻辑」的东西最先被砍掉：接口超时的兜底重试、工具返回脏数据的清洗、system prompt 各段的拼接顺序、历史消息压缩到多长。它们看起来都是工程细节——但正是它们决定了模型能看见什么（观测空间）和能做什么（动作空间）。

这就接上了本库此前已有的那条判断：[[AgentHarness]] 列出 harness 做哪四件事（组装上下文 / 跑循环并判停 / 治理窗口 / 保活与调度），而 09-24 立的教义是「模型不是唯一可以放控制的地方」。把两者合起来会得到一个此前没人写下的推论：既然控制不在模型里，那训练就不能只喂模型——你必须把那个承载控制的 harness 一起放进训练回路。中文报道把这句话说得最锋利：「harness 是策略的一部分，不是外挂」。

2026-10 出现了第一个把这件事做成可用工具的开源实现：Agent Lightning v1.0（微软亚洲研究院，2026-10-07/08 开源，约 3,500 行）。它的思路简单到近乎狡猾——不去重写 harness，而是在 harness 与模型之间插一个 OpenAI 兼容的 LLM 代理：harness 以为自己还在正常调模型，一行代码都不用改；代理在旁边把 prompt、response、logprob 全部记下来喂给训练器。部署用的那个 harness，原样参加了训练。

3 · 核心机制

  1. 重写版 vs 部署版：逐项对照。这是本页的骨架——把「重写一遍」究竟丢了什么摊开来看：
    环节部署版里它长什么样重写版里通常被砍成什么样被抽掉的约束是什么
    工具调用有超时、有重试、有降级兜底直接同步调用，超时即失败时间成本与失败恢复——模型学不会「这一步可能要等」
    工具返回脏数据清洗、截断、结构化原样塞回上下文观测空间的信噪比——模型没见过真实噪声
    system prompt多段按固定顺序拼接（规则 / 工具 / 记忆）简化成一段指令优先级结构——冲突时听谁的，训练里从未发生
    历史消息压缩到某个长度、有取舍策略不压缩或随便截断记忆衰减曲线——这正是 [[Compaction]] 管的那件事
    判停条件步数 / 预算 / 验证器多重判停固定步数动作空间的终止结构
    为什么重要：这五行里没有一行是「模型能力」，但每一行都在改变模型面对的那个环境。在训练框架里重写 agent，不是在复刻它，是在造一个约束更少的新世界。
  2. 为什么这不是 reward hacking，而是环境错配。可引原文把两者的区别钉得很死：「这不算是 reward hacking，更准确的叫法是环境错配。而错配的代价，通常被记在『模型泛化不行』的账上。」
    • reward hacking：奖励函数被钻了空子，环境是对的、目标错了 ⇒ 修法是改奖励。
    • 环境错配：目标是对的，环境被换了 ⇒ 改奖励毫无用处，必须把环境换回来。
    为什么重要：两者的修法方向相反。误判成 reward hacking 的团队会去调奖励、加惩罚，越调越远，而真正的病灶在训练回路之外。
  3. 代理层怎么接：三部件，harness 一行不改。Agent Lightning 的结构是：API 网关（对 harness 伪装成一个 OpenAI 兼容的模型端点）+ Rollout 控制器（编排批量任务）+ 定制训练器（基于 verl）。harness 照常发请求，网关转发给真实模型并把prompt / response / logprob 全部落盘；harness 全程不知道自己在被训练。原生 Kubernetes 批量跑任务，不依赖付费商业沙箱。
    为什么重要：“零侵入”是这件事能不能落地的关键——只要要求改 harness，每换一个 agent 就要重写一次的原病就会复发。
  4. 遥测即训练 substrate：与可观测是同一份数据的两个消费者。代理记录的 prompt / response / logprob，正是 trace。也就是说：给可观测系统装的那一套埋点，和给 RL 训练器喂的那一批数据，是同一份东西。
    为什么重要：它把两条此前分开的线合成一条——可观测不只是运维工具，它同时是训练数据的采集层；反过来说，你在可观测上偷的懒，会直接变成训练数据的缺口。
  5. 它同时是「自进化智能体」的第一份硬证据。台账里「从自身轨迹中学习 / 自进化智能体」这一格挂了 18 天、零证据——此前它只是一个名字：agent 能不能从自己跑出来的轨迹里变好？本条给出了可验证的形态：轨迹来自真实部署的 harness，而不是重写版，这正是「从自身经验学习」能否成立的前提条件。⇒ 两条合并，不并列：没有 harness 保真，「自进化」只是把错配固化得更快。
  6. 一点成本侧的工程增益（非核心，但解释了它为什么现在才出现）。Agent Lightning 的 Collocated Async RL 端到端约为同步 RL 的 2 倍，且用卡少于完全异步——训练长轨迹 agent 的算力门槛，是这件事此前不划算的主要原因之一。

4 · 应用场景

场景 1 · 编码 agent 训完了，一上线就崩

背景：团队用 RL 把编码 agent 在离线环境里训到指标很好，换进生产 harness 后表现明显下滑，复盘结论写的是「模型泛化能力不足」。

如何应用：先做逐项对照而不是换模型：把重写版与部署版的五处差异（超时兜底 / 脏数据清洗 / prompt 拼接顺序 / 压缩长度 / 判停条件）列成表，逐项确认训练回路里是否缺失。若缺失项 ≥1，先归因环境错配，再谈调奖励。

结果：归因从「模型不行」改成「训练世界与部署世界不同」——修法从调超参变成接代理层，两者的工作量与人月完全不是一个量级。

场景 2 · 想让 agent 从自己的轨迹里变好

背景：「自进化智能体」很长一段时间只是个愿望：线上轨迹攒了几百万条，拿去微调却越训越差。

如何应用：先问轨迹的来源保真度——这些 trace 是生产 harness 跑出来的，还是某个评测脚本跑出来的？用代理层在生产链路上采集（prompt / response / logprob 全留），保证「优化对象 == 部署对象」。

结果：「自进化」的前提被写成了可检查的一句断言：assert optimize_target is deploy_target。不满足它，越努力训练，错配固化得越快。

场景 3 · 可观测埋点该做到多细

背景：团队在争论要不要为 agent 上完整的 trace 埋点，理由是「运维用得上，但短期看不到收益」。

如何应用：把埋点同时算成训练数据采集层：代理层记录的正是 trace，两者共用同一份基础设施。缺了 logprob，未来做策略梯度就没有可用的数据；缺了工具返回原文，观测空间就还原不出来。

结果：可观测从成本项变成双用途资产——这也解释了为什么“遥测即训练 substrate”是本库两条线索的接缝，而不是巧合。

5 · 边界辨析

5.1 不是什么

  • 不是 reward hacking：reward hacking 是环境对、目标错；本条是目标对、环境被换了。修法方向相反——一个改奖励，一个改回路。
  • 不是上下文工程：上下文工程回答「每一步往窗口里放什么」；本条回答「你优化时看到的那个窗口，是不是部署时的那个窗口」。前者是取舍方法，后者是一致性前提。
  • 不是 [[Compaction]] 的重复：压缩长度的差异只是被抽掉的约束之一。但这一条把上下文治理的性质改了——它从「工程细节」升级为「训练正确性前提」。
  • 不是持久化执行：那一层管「长跑能不能活过崩溃」（时间维度），本条管「训练与部署是不是同一个世界」（一致性维度）。两者族不同，不合并。
  • 不是评测：评测测「跑得好不好」，本条问「你在优化的那个东西存不存在于生产里」。评测做得再扎实，也无法发现环境错配。

5.2 常见误解

  • 「只要奖励设计得好就行」——奖励再好也救不了被换掉的环境；这是环境错配与 reward hacking 最关键的分野。
  • 「重写一遍是为了跑得快，逻辑一样就行」——被砍掉的那些「非核心逻辑」恰恰定义了动作空间与观测空间；它们不是装饰。
  • 「harness 是外挂，训练只管模型」——「harness 是策略的一部分，不是外挂」。控制不在模型里，训练就不能只喂模型。
  • 「+14.6 pp 说明这条路已经通了」——单模型、单基准、自报、early-stage、样本可比性未说明；它证明方向可行，不证明方案可用。
  • 「解决了训练错配，部署后就稳了」——它不解决部署后的漂移；环境上线之后继续变化，是另一个独立问题。

5.3 适用与不适用

值得先做训练—部署一致性审计可以先不做
要用 RL / 微调让 agent 变好，且已有生产 harnessagent 完全靠 prompt，不做任何训练
训练环境与生产环境由两套代码维护训练与部署共用同一条代码路径
出现「离线指标好、上线就退化」且归因为泛化离线与线上指标本来就一致
agent 依赖大量工具返回与历史压缩单轮、无工具、无历史
长轨迹任务（步数多、环境交互密集）一步出结果的短任务

7 · 一句话回顾

每次开始训练之前，先问一句：「我们优化的那个对象，和被部署的那个对象，是同一个吗？」——为了接入训练框架而重写的那个 agent，已经被抽掉了超时兜底、脏数据清洗、prompt 拼接顺序和压缩长度，而正是这些「工程细节」定义了动作空间与观测空间。所以harness 是策略的一部分，不是外挂；训得好、上线崩的账单，不该记在「模型泛化不行」头上。
